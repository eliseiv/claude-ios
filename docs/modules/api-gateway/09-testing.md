# API Gateway — Testing

## Unit
- JWT verify: валидный/просроченный/неверная подпись/неверный aud/iss → 200/401.
- Size-валидаторы: на границе и выше лимита → 413/422.
- Error mapping: исключения → корректный код и формат ошибки.

## Integration
- Rate limit (реальный Redis): N+1 запрос → 429; раздельные счётчики user/device/IP.
- `userId != sub` → 403.
- Correlation id: `X-Request-Id` пробрасывается/генерируется и присутствует в логах.
- `/ready`: при недоступном Redis/PG → 503.
- Redaction: `Authorization` и поля с секретами отсутствуют в логах.

## Integration — transport-лимит тела ([ADR-089](../../adr/ADR-089-attachment-limits-and-error-taxonomy.md))
- **Сквозной тест «`413`, а не разрыв»:** запрос с телом больше лимита роута получает **HTTP-ответ** `413` с телом `{"error":{"code":"payload_too_large",…}}`; клиент дочитывает ответ без ошибки транспорта. Тест обязан **падать** на реализации, которая отвечает, не вычитывая тело (регрессия к прежнему `BaseHTTPMiddleware`).
- **Chunked без `Content-Length`:** тело больше лимита отклоняется `413` (до ADR-089 проверка молча пропускалась — [TD-017](../../100-known-tech-debt.md)). Тест обязан падать на реализации, читающей только заголовок.
- **Drain-бюджет:** тело, превышающее лимит на величину больше `SIZE_LIMIT_DRAIN_BYTES`, не читается целиком (проверяется по объёму, дошедшему до приложения/счётчика), ответ всё равно отправлен.
- **`message` несёт действующий лимит:** число в тексте совпадает с `_limit_for(path)` из `Settings`, а не с литералом теста.
- **Тест-детектор карты лимитов:** для каждого роута приложения, чьё тело — `ChatRunRequest` или подкласс, `_limit_for(path)` возвращает `attachment_request_body_limit`. Тест ловит и сегодняшний пропуск `/v1/chat/v2/run/stream`, и любой будущий роут с вложениями.
- Роуты **без** вложений (обе версии `tool-result`, `capabilities`, прочие `/v1/*`) остаются на `SIZE_LIMIT_BODY` — проверяется обеими сторонами (не подняли лишнего).
