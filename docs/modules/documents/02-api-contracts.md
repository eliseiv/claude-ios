# Documents — API Contracts

Реализация — [ADR-090](../../adr/ADR-090-chat-documents.md). Поле ответа хода — [ADR-101](../../adr/ADR-101-chat-response-documents.md) (**код не написан**).

Все маршруты: префикс `/v1/chats/{session_id}/documents`, тег `Documents`, `Authorization: Bearer <JWT>` обязателен, ограничение частоты применяется на **каждом** (включая `/download`). Изоляция владельца — на каждом пути: чужое и несуществующее дают `404`.

> **Этот раздел — то, что раньше узнавалось только чтением кода.** Каждое утверждение ниже сверено с реализацией; якоря `файл:строка` даны там, где правило нельзя вывести из схемы ответа.

---

## Объект документа

```json
{
  "documentId": "uuid",
  "filename": "отчёт.md",
  "mediaType": "text/markdown",
  "size": 4096,
  "version": 2,
  "createdBy": "assistant",
  "createdAt": "2026-09-08T10:00:00Z",
  "updatedAt": "2026-09-08T10:05:00Z",
  "content": "base64 | null"
}
```

| Поле | Тип | Прим. |
|---|---|---|
| `documentId` | `uuid` | идентификатор в пределах чата |
| `filename` | `string` | **фактическое** имя после нормализации (см. §Нормализация имени) |
| `mediaType` | `text/markdown` \| `text/plain` \| `text/csv` \| `application/json` | только текстовые форматы; бинарных нет ([ADR-090 §1](../../adr/ADR-090-chat-documents.md)) |
| `size` | `int` | размер содержимого в **байтах UTF-8** (не в символах) |
| `version` | `int` | 1 при создании, +1 на каждой замене содержимого |
| `createdBy` | `user` \| `assistant` | происхождение, **не право** (см. §`createdBy`) |
| `createdAt` / `updatedAt` | `timestamptz` | моменты создания и последнего изменения |
| `content` | `string` \| `null` | base64 содержимого. **Непусто только в ответе на запрос ОДНОГО документа**; в списке всегда `null` |

## Маршруты

### POST /v1/chats/{session_id}/documents — загрузить документ
**Request:** `{ "filename": "string", "mediaType": "…", "content": "base64" }` — все три поля **обязательны**, схема строгая (лишний ключ → `422`).
- `filename`: 1..200 символов;
- `mediaType`: строго один из четырёх;
- `content`: base64, декодируется в UTF-8. Не base64 → `422 validation_error` («document data is not valid base64»); не UTF-8 после декодирования → `422 validation_error` («document content is not valid UTF-8»).

**Проверка сессии — только здесь и в списке:** несуществующий или чужой `session_id` → `404 session_not_found`. У остальных маршрутов роль проверки играет сама пара (владелец, сессия) в запросе, и они отвечают `404 document_not_found`.

**Response 201:** объект документа, `content = null`, `version = 1`, `createdBy = "user"`.

> **Пустое содержимое здесь ПРОХОДИТ.** У `content` нет `min_length`, поэтому пустая строка base64 создаёт документ размера 0. Это **асимметрия с инструментом** `document.create`, который пустое содержимое отвергает (см. §Обязательность непустого содержимого). Обе стороны помечены намеренно: правило одного пути на другой не переносить, пока это не изменено отдельным решением.

### GET /v1/chats/{session_id}/documents — список
**Response 200:** `{ "documents": [ …объект без содержимого… ] }`. Порядок — `created_at ASC` (старые первыми). Чужая/несуществующая сессия → `404 session_not_found`.

### GET /v1/chats/{session_id}/documents/{document_id} — документ с содержимым
**Response 200:** объект документа, `content` — base64 содержимого.

### PATCH /v1/chats/{session_id}/documents/{document_id} — заменить содержимое
**Request:** `{ "content": "base64" }` — единственное поле.

**`PATCH` заменяет содержимое ЦЕЛИКОМ; патч-семантики нет.** Глагол `PATCH` выбран потому, что запрос не несёт остальных полей объекта, — а не потому, что применяется дельта. Ни диапазонов строк, ни replace-подстроки, ни JSON-patch не поддерживается: присылайте **полный новый текст**. Причина — [ADR-090 §3](../../adr/ADR-090-chat-documents.md): патч требует от отправителя точного знания текущего текста и молча портит документ при расхождении.

Не меняются: `filename`, `mediaType`, `createdBy`, `createdAt`. Меняются: `content`, `size`, `version` (+1), `updatedAt`.

**Response 200:** объект документа, `content = null`.

### GET /v1/chats/{session_id}/documents/{document_id}/download — файлом
**Response 200:** тело — содержимое в UTF-8, `Content-Type` = `mediaType` документа, `Cache-Control: private, no-store`, `Content-Disposition: attachment` с **двумя** параметрами: `filename="…"` (ASCII-остаток, при полностью не-ASCII имени — запасное `document`) и `filename*=UTF-8''…` (percent-encoded настоящее имя, RFC 5987). Кириллическое имя приезжает во втором параметре.

> **Скачивание требует `Authorization`, поэтому URL нельзя отдать компоненту предпросмотра.** Подписанного URL у документов нет: подпись введена для медиа ([ADR-085](../../adr/ADR-085-media-asset-download-proxy.md)) потому, что ассет тянет webview без заголовков авторизации; документ забирает само приложение, у которого токен уже есть ([ADR-090 §4](../../adr/ADR-090-chat-documents.md)). **Практическое следствие для клиента:** подставить этот URL в `WKWebView`, `QLPreviewController`, `UIDocumentInteractionController`, `AsyncImage`, `SFSafariViewController` или в любой другой компонент, который сам ходит по ссылке, **нельзя** — он пойдёт без заголовка и получит `401`. Приложение обязано скачать байты своим HTTP-клиентом с заголовком и передать компоненту **локальный файл**. Правило «ассет отдаётся по подписи» с медиа на документы **не переносится**; обратное правило — «документ отдаётся по JWT» — на медиа-ассеты **тоже не переносится**.

### DELETE /v1/chats/{session_id}/documents/{document_id}
**Response 200:** `{ "deleted": true }`. Повторное удаление → `404 document_not_found`.

## Нормализация имени: имя, которое отправили, — не имя, которое вернулось

`filename` из запроса и из аргументов инструмента проходит через `_normalize_filename` (`src/app/documents/service.py:239-254`). Правила применяются **в этом порядке**; результат — то, что попадёт в объект ответа, в `Content-Disposition` и в строку системного промта.

1. **Пустое или отсутствующее имя → `document`.** Пустая строка, `null` (у инструмента) и имя из одних пробелов дают базу `document`.
2. **Обратные слэши приводятся к прямым**, затем берётся **последний** сегмент пути: `C:\Users\x\отчёт.md` → `отчёт.md`, `../../etc/passwd` → `passwd`. Причина — имя уходит в `Content-Disposition`, и `../` там означает обход каталога на машине **клиента**, сохраняющего файл.
3. **Обрезаются ведущие и хвостовые пробелы.** Если после обрезки не осталось ничего — база `document`.
4. **Расширение приводится к `mediaType`.** Ожидаемое расширение: `text/markdown → .md`, `text/plain → .txt`, `text/csv → .csv`, `application/json → .json`. Если имя (в нижнем регистре) уже оканчивается на ожидаемое — оно **не трогается**, регистр сохраняется: `ОТЧЁТ.MD` при `text/markdown` остаётся `ОТЧЁТ.MD`.
5. **Сначала снимается ЧУЖОЕ текстовое расширение, потом добавляется своё.** Если имя оканчивается на одно из **четырёх известных** расширений (`.md`, `.txt`, `.csv`, `.json`), это расширение отбрасывается, и только затем приписывается ожидаемое: `список.txt` при `mediaType=text/markdown` → **`список.md`**, а не `список.txt.md`. Правило добавлено по факту с прода 2026-08-24.
   - **Только известные.** Любое другое расширение — не расширение для этой логики, оно остаётся частью имени: `договор.docx` при `text/markdown` → **`договор.docx.md`**; `v1.2` → `v1.2.md`.
   - **Имя из одного расширения** (`.md` при `mediaType=text/csv`) не теряет основу: получается `.md.csv` (снятие не выполняется, когда после точки не осталось основы).
6. **Итог усекается до 200 символов.** Усечение — **последнее** действие, уже после добавления расширения: имя в 200 символов плюс `.md` даёт 203 и режется до 200, то есть **теряет хвост расширения**. У REST-пути `filename` ограничен 200 символами схемой, поэтому случай достижим именно там; у инструмента длина имени схемой не ограничена вовсе.

**Следствие, которое обязан учесть клиент:** имя в тексте ответа модели («сохранил в `список.txt`») и `filename` объекта могут **не совпадать**. Показывать и подписывать файл следует значением `filename` из ответа API, а не тем, что модель назвала словами.

## `version` — признак изменения, а не механизм конкурентности

`version` начинается с 1 и увеличивается на единицу при каждой замене содержимого (`src/app/documents/service.py:152`). Назначение — дать UI признак «документ изменился».

**Оптимистической конкурентности нет и не подразумевается:**
- заголовок `If-Match` не читается ни одним маршрутом; `ETag` не отдаётся;
- в теле `PATCH` поля `version` **нет** — схема строгая, прислать его нельзя (лишний ключ → `422`);
- обновление не выполняет условной проверки версии: читает строку, заменяет содержимое, увеличивает счётчик. Два одновременных обновления одного документа **оба применятся**, победит записавший последним, `version` вырастет на 2, и промежуточное содержимое будет потеряно без ошибки;
- кода `409 conflict` у этого модуля нет.

Клиент, которому нужна защита от потери правок, обязан обеспечивать её сам (например, не давать редактировать документ, пока не завершён ход, который его пишет). Введение `If-Match` потребует отдельного решения и нового кода ответа — молча полагаться на `version` **нельзя**.

## `createdBy` — происхождение, а не право

`createdBy` принимает `user` (создано через `POST`) или `assistant` (создано инструментом `document.create`, `src/app/chat/global_tools.py:396`) и после создания **не меняется** — в том числе когда документ правит другая сторона.

Это **факт для отображения**, а не признак доступа ([ADR-090 §5](../../adr/ADR-090-chat-documents.md)):
- модель может читать, править и удалять документ с `createdBy = "user"`;
- пользователь может читать, править и удалять документ с `createdBy = "assistant"`;
- ни один маршрут и ни один инструмент не ветвится по этому полю.

Единственный контроль доступа — владение парой (пользователь, сессия). Клиенту `createdBy` годится для значка «создано ассистентом» и **не годится** как основание скрыть кнопку правки или удаления.

## Обязательность непустого содержимого у `document.create`

`document.create` отвергает пустое содержимое: `content`, отсутствующий или пустой, даёт tool-result ошибку `invalid_document_request` («content is required and must not be empty», `src/app/chat/global_tools.py:384-388`). Причина: пустой документ бесполезен и запутывает пользователя в списке файлов.

**Правило действует только на этом пути** — оно не выражено ни в схеме аргументов инструмента, ни в схеме REST-запроса, и потому проверяемо только здесь:

| Путь | Пустое содержимое |
|---|---|
| `document.create` (инструмент) | **отвергается** → tool-result ошибка `invalid_document_request` |
| `document.update` (инструмент) | **принимается** → документ становится пустым, `version` +1 |
| `POST …/documents` (REST) | **принимается** → документ размера 0 |
| `PATCH …/documents/{id}` (REST) | **принимается** → документ становится пустым, `version` +1 |

Асимметрия «create строг, update нет» относится **и** к инструменту, **и** к REST: опустошить документ можно, создать пустым — нельзя (кроме REST-создания). Обе стороны помечены; правило одной строки таблицы на другую не переносить.

> Отдельно про аргументы инструмента: у `DocumentUpdateArgs` поле `content` необязательное, и пропущенный аргумент трактуется как пустая строка — то есть **вызов `document.update` без `content` стирает документ**. Это следствие того же правила «кривые аргументы вырождаются в мягкий отказ, а не роняют ход» ([ADR-090 §3](../../adr/ADR-090-chat-documents.md), реестр `ARGS_DEGRADE_TOOLS`), и оно не компенсируется проверкой в обработчике.

## Инструменты модели (server-side, global)

Исполняет backend внутри tool-loop, без round-trip к устройству ([ADR-026](../../adr/ADR-026-global-server-side-tools-and-time-now.md)). В `toolCalls[]` наружу **не** попадают; факт выполнения виден в `serverTools[]`. Полные каталожные признаки — [chat-orchestrator/02-api-contracts §Каталог](../chat-orchestrator/02-api-contracts.md).

| Инструмент | Аргументы (все необязательные) | Результат при успехе |
|---|---|---|
| `document.create` | `filename` (деф. `document`), `mediaType` (деф. `text/markdown`), `content` | `{ documentId, filename, mediaType, size, version }` |
| `document.list` | — | `{ documents: [ { documentId, filename, mediaType, size, version } ] }` |
| `document.read` | `documentId` | `{ documentId, filename, mediaType, size, version, content }` |
| `document.update` | `documentId`, `content` | `{ documentId, filename, mediaType, size, version }` |

**Все аргументы необязательны намеренно:** пропущенный или кривой аргумент обязан вырождаться в tool-result ошибку, а не ронять весь ход `422` (прод 2026-08-24: модель, не приславшая `mediaType`, роняла ответ целиком). Создание и обновление входят в `MUTATING_TOOLS` (аудит), но **не** в `CONFIRM_TOOLS` — подтверждать нечего, изменение происходит на бэкенде по прямой просьбе пользователя.

**Отказы приходят tool-result ошибкой, ход не падает:** `invalid_document_request` (кривые аргументы, не-uuid `documentId`, пустое содержимое у `create`, несуществующий/чужой документ), `document_too_large`, `too_many_documents`, `documents_total_too_large`, `unsupported_media_type`, `documents_not_available` (документы не подключены в этом контексте).

**Осведомлённость модели.** Когда в сессии есть хотя бы один документ, к системному промту добавляется одна строка со списком `filename (id=…)`, усечённая до `DOCUMENT_CONTEXT_MAX_CHARS`. Содержимое в промт **не** попадает — для чтения есть `document.read` ([ADR-090 §6](../../adr/ADR-090-chat-documents.md)).

## `ChatResponse.documents[]` — ход возвращает затронутые документы ([ADR-101](../../adr/ADR-101-chat-response-documents.md))

> **Статус: спроектировано, код не написан.** Ниже — нормативный контракт для backend и iOS; на сегодняшних инстансах поля в ответе ещё нет.

Поле ответа генерации — во всех ответах `POST /v1/chat/run`, `POST /v1/chat/tool-result`, `POST /v1/chat/v2/run`, `POST /v1/chat/v2/tool-result` и в SSE-событии `done`:

```json
"documents": [
  { "documentId": "uuid", "filename": "отчёт.md", "mediaType": "text/markdown", "size": 4096, "version": 2 }
]
```

- **Что попадает:** только успешные `document.create` и `document.update` этого **хода** (`messageStepId`). `document.read` и `document.list` — **нет** (ход ничего не изменил); tool-result ошибка — **нет** (документа не появилось).
- **Содержимого нет.** `content` в элемент не входит: документ персистентен и адресуем, содержимое отдают `GET …/documents/{documentId}` и `/download`.
- **Скоуп — ход, не вызов.** Документ, созданный на раннем витке tool-loop, приходит и в последующих ответах того же `messageStepId`, включая идемпотентный повтор и `blocked` + `blockReason=max_tokens`. Это **противоположно** `serverTools[]` (индикатор за один вызов, на повторе пустой) — правило одного поля на другое не переносить.
- **Одна запись на `documentId`.** Если ход тронул документ дважды (`create`, затем `update`), запись одна, с **последними** `size`/`version`; позиция — по первому появлению. Это **противоположно** `mediaJobs`, который накапливает: у каждой media-задачи свой `jobId`, а документ повторяется.
- **`null`, а не `[]`,** когда успешных создания/замены в ходе не было — включая policy-`blocked` (хода нет).
- **Аддитивно.** Существующие поля, коды и пути не меняются; старые клиенты игнорируют. Отдельного якоря в истории (`GET /v1/chats/{id}` → `steps[].payload`) **не вводится** — холодный старт закрывает `GET /v1/chats/{sessionId}/documents`.

## Ограничения

### Лимиты ([ADR-090 §7](../../adr/ADR-090-chat-documents.md))
| Ключ | Дефолт | Что ограничивает |
|---|---|---|
| `DOCUMENT_MAX_BYTES` | `262144` (256 KiB) | размер одного документа (байты UTF-8) |
| `DOCUMENT_MAX_COUNT` | `20` | число документов **на сессию** |
| `DOCUMENT_TOTAL_BYTES` | `1048576` (1 MiB) | суммарный размер документов **на сессию** |
| `DOCUMENT_CONTEXT_MAX_CHARS` | `2000` | срез строки о документах в системном промте |

Потолки заданы **на сессию**, потому что скоуп документа — сессия. При обновлении заменяемый документ выбывает из суммы (иначе правка на один байт упиралась бы в потолок, который сама же и занимает), а проверка числа документов при обновлении не выполняется вовсе — новых строк не появляется.

### Ограничение частоты — **включая скачивание**
Каждый маршрут модуля, первым действием, проходит общий пользовательский лимит «прочих» операций: ключ `rl:other:{userId}`, дефолт `RATE_LIMIT_OTHER_PER_USER=60` за окно `RATE_LIMIT_WINDOW_SECONDS=60`. Превышение → `429 rate_limited`.

**Скачивание из-под лимита не выведено** (`src/app/api_gateway/routers/documents.py:204`) — в отличие от статики и медиа-прокси, это обычный `/v1/*`-маршрут. Практические следствия для клиента:
- бакет **общий** с другими «прочими» маршрутами (`/v1/chats*`, `/v1/models`, `/v1/memory`, `/v1/byok*`, `/v1/billing/cloudpayments/checkout` и др.) — частые скачивания отнимают бюджет у остальных экранов, вплоть до `429` на оплате;
- массовая выгрузка всех документов чата в цикле упирается в лимит; выгружать следует по требованию пользователя, а не пачкой;
- при недоступности Redis лимит **пропускает** запрос (fail-open) и пишет предупреждение в лог — на поведение клиента полагаться нельзя в обе стороны.

### Модерация — не применяется
Ни содержимое документа, ни имя не проходят проверку модерации: документ не отображается приложением как медиа и не становится промптом или референсом платной генерации — оба критерия [ADR-086 §2](../../adr/ADR-086-ugc-moderation.md) дают «нет», тот же вердикт и по той же причине, что у файлов-знаний workspace. Кода `content_policy_violation` на этих маршрутах не бывает.

**Контраст (обе стороны помечены):** ход **с вложениями** модерируется до генерации ([ADR-086 §3](../../adr/ADR-086-ugc-moderation.md)) — вложения рендерятся как медиа **и** уходят в генерацию; документы не делают ни того, ни другого. Правило вложений на документы **не переносится**. Если документ когда-нибудь начнёт уходить в генерацию, вердикт обязан пересматриваться вместе с этим изменением.

### Удаление чата уносит документы
`chat_documents.session_id` — FK на `chat_sessions.id` с `ON DELETE CASCADE`; `DELETE /v1/chats/{id}` удаляет строку сессии физически, поэтому документы чата исчезают вместе с ней **безвозвратно** — корзины, soft-delete и восстановления нет. То же по `user_id` при удалении пользователя.

Это следствие выбранного скоупа, а не оптимизация ([ADR-090 §2](../../adr/ADR-090-chat-documents.md)). **Обязанность клиента:** предупреждать при удалении чата, в котором есть документы, и предлагать скачать их до удаления. Отдельного эндпоинта «перенести документ в другой чат» нет.

## Коды ответа

| Код | Когда |
|---|---|
| `200` | успех `GET` / `PATCH` / `DELETE` / `download` |
| `201` | создан документ (`POST`) |
| `401` | нет/невалидный JWT |
| `404 session_not_found` | чужая или несуществующая сессия — **только** `POST` и `GET` (список) |
| `404 document_not_found` | чужой или несуществующий документ (неотличимы) — остальные маршруты |
| `422 unsupported_media_type` | `mediaType` вне четырёх допустимых |
| `422 document_too_large` | документ больше `DOCUMENT_MAX_BYTES` |
| `422 too_many_documents` | в сессии уже `DOCUMENT_MAX_COUNT` документов (проверяется только при создании) |
| `422 documents_total_too_large` | суммарный размер документов сессии превысил `DOCUMENT_TOTAL_BYTES` |
| `422 validation_error` | схема запроса, лишний ключ, невалидный base64, содержимое не UTF-8 |
| `429 rate_limited` | превышен общий лимит «прочих» операций (действует и на `/download`) |
| `5xx` | внутренняя ошибка |

`403` на этих маршрутах не встречается: несоответствие владельца выражается через `404`, а не через «доступ запрещён».
