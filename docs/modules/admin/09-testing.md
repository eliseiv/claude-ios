# Admin — Testing

## Unit
- `require_admin`: валидный `X-Admin-Token` → проходит; неверный/отсутствует → `401`; сравнение constant-time (по контракту,
  не таймингом). Совпадение с `ADMIN_API_SECRET_PREV` (ротация) → проходит. Пустые секреты в конфиге не матчатся.
- Pydantic-схема grant: `amount<=0` → `422`; пустой/отсутствующий `reason` → `422`; лишнее поле (`extra='forbid'`) → `422`.

## Integration (реальный PostgreSQL)
- `grant` на существующем `userId` → `ledger_transactions(type=credit)`, баланс += amount, `idempotentReplay=false`.
- Повторный `grant` тот же `idempotencyKey` + payload → `idempotentReplay=true`, баланс не меняется, тот же `ledgerTxId`.
- Тот же `idempotencyKey`, другой `amount` → `409`, без начисления.
- Несуществующий `userId` → `404 user_not_found`, строка `users` **не** создана, баланс не появился.
- `require_admin` не создаёт `users` для actor (нет provisioning): после серии admin-запросов нет «admin»-строки в `users`.
- `users.trial_used` не изменяется admin-операциями.
- audit: успешный `grant` создаёт **и** `billing_credit` (Wallet), **и** `admin_grant` (Admin). Секрет в payload отсутствует.
- `GET /v1/admin/wallet/{userId}`: корректные `balance` + `lastTransactions` (DESC); несуществующий → `404`.

## Integration — subscription/grant ([ADR-048](../../adr/ADR-048-admin-subscription-grant.md))
- `POST /v1/admin/subscription/grant` на существующем `userId` (нет строки `subscriptions`) → **создаёт** строку `status='active'`, `plan`, `expires_at`; ответ `status='active'`, `expiresAt`, `plan`.
- Повторный вызов на существующей подписке (upsert) **идемпотентен по PK `user_id`**: перезаписывает те же значения, второй строки не появляется.
- `credits` **опущен** → начислено `SUBSCRIPTION_CREDITS_PER_PERIOD` (default); ответ `creditsGranted=SUBSCRIPTION_CREDITS_PER_PERIOD`, `newBalance`/`ledgerTxId`/`idempotentReplay` присутствуют.
- `credits=0` → активация **без** начисления: `ledger_transactions` не растёт, `creditsGranted=0`, `newBalance`/`ledgerTxId`/`idempotentReplay` = `null`.
- `credits=N` (N>0) → начислено ровно N; `creditsGranted=N`.
- **Namespace ledger-ключа:** начисление идёт по `admin-sub-grant:{idempotencyKey}` и **НЕ коллидирует** с `wallet/grant` (raw `idempotencyKey`), с `sub-grant:{transaction_id}` (реальный период) и `adapty-txn:{...}` (Adapty): один и тот же человекочитаемый `idempotencyKey`, использованный на `wallet/grant` и на `subscription/grant`, порождает **две разные** ledger-транзакции.
- Повтор `subscription/grant` с тем же `idempotencyKey` + тот же `credits` → `idempotentReplay=true`, баланс не меняется, тот же `ledgerTxId`.
- Тот же `idempotencyKey`, **другой** `credits` → `409` (из `WalletService.grant`); **ни** подписка **не** активирована повторно с иными полями сверх upsert, **ни** кредиты не начислены (одна транзакция откатывается целиком).
- Несуществующий `userId` → `404 user_not_found`, строка `users` **не** создана, `subscriptions` не появилась, баланс не появился (нет provisioning).
- **Одна транзакция (нет частичного применения):** при сбое начисления (`409`/insufficient) upsert подписки **не** коммитится — состояние `subscriptions`/`wallets`/`ledger` не меняется.

## Policy / E2E — root-cause ([ADR-002](../../adr/ADR-002-access-policy-state-machine.md))
- Пользователь с `subscription_status=none` и `trial_used=true`, баланс `>0`: `/v1/chat/run` (или `/v1/policy/effective`) → **blocked** (`trial_used`) **до** гранта.
- После `POST /v1/admin/subscription/grant` (expiresAt в будущем, `credits` по умолчанию): тот же пользователь **проходит** policy (`allow`) — сняты `trial_used` и `credits_empty`; подписка `active` + баланс `>0`.
- **lazy-expiry:** грант с `expiresAt <= now()` был бы отклонён валидацией (`422`), поэтому кейс «active с прошлой датой → всё равно expired» не достижим через endpoint (регресс-защита `_effective_subscription_status`).

## Validation — subscription/grant
- `expiresAt` в прошлом → `422`; `expiresAt` без tzinfo (naive) → `422`.
- `days <= 0` → `422`.
- Заданы **оба** `expiresAt` и `days` → `422`; **ни одного** → `422`.
- `credits < 0` → `422`; лишнее поле (`extra='forbid'`) → `422`; отсутствует `userId`/`idempotencyKey` → `422`.

## Integration — `GET /v1/admin/costs/daily` ([ADR-092](../../adr/ADR-092-crm-daily-costs-endpoint.md))

> **Статус: покрыто** — `tests/integration/test_crm_daily_costs_adr092.py`, **32** кейса
> (21 тест-функция, две параметризованы на 7 и 6 входов); сверка 2026-08-26. Перечень ниже —
> одновременно ТЗ и карта покрытия.

- **Форма ответа и порядок:** два дня × два провайдера → `total` = 4, `items` отсортированы
  `date ASC, provider ASC`; `date` в формате `YYYY-MM-DD`; `provider` — **сырой** ключ (`"OpenAI"` /
  `"Anthropic"` / `"Fal"`), не нормализованный.
- **`requests` считает ВЫЗОВЫ, а не ходы:** один `message_step_id` с тремя assistant-шагами, у
  каждого непустой `usage` → `requests = 3` в клетке дня, **не** `1`.
- **Шаг без `usage` в счёт не входит:** ход медиа-визарда (assistant-шаг «Generation started …»
  **без** `usage` + строка `media_jobs`) → клетка `Fal` даёт `requests = 1`, а не `2`; клетки чата от
  этого шага не появляется вовсе (регресс-защита от двойного счёта генерации).
- **Кэш OpenAI не считается дважды:** шаг с `inputTokens = 1000`, `cacheReadTokens = 800` на модели
  с `cache_read_in_input` → `tokens` клетки посчитаны по конвенции прайса, и `spend_usd` той же
  клетки с ними согласован (не `input + cache_read`).
- **`Fal` отдаёт `tokens = 0.0`, а не `null`:** день только с media-генерациями → клетка `Fal` несёт
  `tokens = 0.0` и непустой `spend_usd`.
- **`null` только при нуле оценённых вызовов:** день, где **все** chat-шаги на модели без строки
  прайса → клетка есть, `requests > 0`, `spend_usd = null`, `tokens = null`.
- **Частично оценённая клетка занижает честно:** день из двух вызовов, один на известной модели,
  другой на неизвестной → `requests = 2`, `spend_usd` = стоимость **только** известного (не `null` и
  не сумма с нулём за неизвестный).
- **«Нет строки» ≠ нулевая строка:** день без трафика внутри периода → клетки за этот день в ответе
  **нет** (нулевых строк не отдаём).
- **Границы периода включительные, календарь UTC:** шаг ровно в `date_from 00:00:00Z` и шаг в
  `date_to 23:59:59Z` **входят**; шаг в `00:00:00Z` следующих за `date_to` суток — **нет**.
- **Пагинация:** `limit=1&offset=1` → `items` длиной 1 = вторая клетка глобального порядка, `total`
  = число клеток за **весь** период (не размер страницы).
- **Коды отказа:**
  - отсутствует `date_from` (или `date_to`) → **`422`**;
  - `limit=0` / `limit=1001` / `offset=-1` → **`422`**;
  - `date_from=2026-8-1` (не `YYYY-MM-DD`) → **`400`**;
  - `date_from > date_to` → **`400`**;
  - период 93 дня → **`400`**, ровно 92 дня → **`200`** (граница проверяется с обеих сторон);
  - **`404` не возвращается ни на одном из перечисленных входов** — регресс-защита: `404` на этом
    пути означает для CRM «расширение v1.3 не реализовано» и выключил бы опрос бэка целиком.
  - нет ни одного admin-заголовка → **`403`**; заголовок передан с неверным значением → **`401`**.
- **Клетка `Unknown` ([ADR-092 §6](../../adr/ADR-092-crm-daily-costs-endpoint.md)):** день, шаги
  которого несут `usage` **без** строкового `model` → клетка `provider = "Unknown"`, `requests = N`,
  `spend_usd = null`, `tokens = null`; клетки других провайдеров за тот же день остаются
  **неизменными** (неатрибутируемый вызов в них не подмешивается).
- **Конвенция Anthropic:** у модели **без** `cache_read_in_input` кэш-чтение к входу
  **прибавляется** (вход его не включает) — зеркало кейса OpenAI, чтобы конвенция не была
  «проверена» одной стороной.
- **Датированный снапшот прайса** оценивается по цене своего алиаса (побеждает длиннейший алиас), а
  не проваливается в «неизвестную модель».
- **Вызов без счётчиков токенов** попадает в `requests`, но не в `spend_usd`/`tokens`: обращение к
  провайдеру было, умножать на цену нечего.
- **Период в один день** = целые UTC-сутки от `00:00:00Z` до `23:59:59Z`.

## Security
- Пользовательский JWT на `/v1/admin/*` (без `X-Admin-Token`) → `401` (JWT не авторизует admin).
- `X-Admin-Token` на пользовательском роуте (`/v1/wallet`) не даёт доступа (там нужен JWT).
- `X-Admin-Token` не попадает в логи/audit (redaction).
- Rate limit `/v1/admin/*`: превышение дефолта → `429`, изолировано от пользовательских лимитов.
- Size-лимит admin-grant: тело > 8 KB → `413` (действует и на `subscription/grant`).
- audit: успешный `subscription/grant` создаёт `admin_subscription_grant` (actor=admin, `plan`/`status`/`expiresAt`/`creditsGranted`), при начислении — **и** `billing_credit`. Секрет `X-Admin-Token` в payload **отсутствует**.

## Integration — экономика и настройки инстанса ([ADR-099](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md))

Дом сценариев обеих поверхностей (`/products`, `/pricing`, `/capabilities`, `/settings`). Модульные
`09-testing.md` затронутых модулей ссылаются сюда и добавляют только свой путь.

### Регрессионный барьер: пустой оверлей = поведение до выката

- **Параметризованный кейс по КАЖДОЙ строке `GET /v1/admin/pricing`** при пустых таблицах: значение
  `tokens` строки равно тому, что списывает действующий код (`run_price()` для медиа,
  `CHAT_CREDIT_COST_GENERAL` для чата). Тест обязан **падать**, если дефолт строки разошёлся с
  формулой, — фикстура не имеет права содержать константу, скопированную из документа.
- **Параметризованный кейс по каждому из пяти платёжных путей** при пустых таблицах: начисленное
  число кредитов равно сегодняшнему (StoreKit consumable → `TOKEN_PRODUCTS`; CloudPayments
  `one_time` → `TOKEN_PRODUCTS`; CloudPayments `subscription` → карта канала/фиксированный грант;
  Adapty → карта канала/фиксированный грант; StoreKit-подписка → `SUBSCRIPTION_CREDITS_PER_PERIOD`).
- **Diff-проверка:** откат резолвера к прямому чтению env обязан **не ронять** эти кейсы (они про
  равенство), но ронять кейсы раздела «оверлей побеждает env» ниже. Оба направления проверяются.

### Порядок разрешения значения

- Оверлей есть → возвращается он, **даже если env задан другим значением** (кейс обязателен: это
  единственная защита от «оверлей молча игнорируется»).
- Оверлея нет, env задан → env. Нет ни того ни другого → дефолт кода.
- Строка `admin_settings`, которую нельзя применить, игнорируется, инстанс продолжает работать на
  env/дефолте, эмитится `admin_override_value_ignored` — **и для значения не по типу, и для
  строки-сироты** (`setting_id` снят с этого инстанса); различает их `reason`, а не поведение.

### Сквозная цепь «правка → применение» (объявлено ≠ подключено)

- `PATCH /v1/admin/pricing/{tariff_id}` → обновление снимка → **реальный** `POST /v1/chat/v2/run`
  списывает новое значение (и балансовый гейт считает по нему же).
- `PATCH /v1/admin/pricing/{tariff_id}` фото/видео → **реальный** `POST /v1/media/images|videos`
  списывает `creditsCharged`, равный ячейке.
- `PATCH /v1/admin/settings/{setting_id}` → соответствующая **пользовательская** ручка фактически
  меняет ответ: по кейсу на **каждую величину реестра** (`chat.characters_enabled` → `GET /v1/characters`;
  `chat.models_offered` → состав `GET /v1/models`; `chat.advertised_generation_modes` → состав
  `generationModes[]`; `moderation.enabled` → поведение гейта модерации; и т. д.).
- ⚠️ **«Каждая величина» значит КАЖДУЮ ЕЁ ТОЧКУ ПРИМЕНЕНИЯ, а не по одной на величину.** Реестр
  точек — колонка «Точка применения» [ADR-099 §8.1](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md);
  величина с несколькими потребителями требует кейса на **каждого**. Именно на этом шве
  потребители и терялись, поэтому названы явно: `chat.characters_enabled` → **и** `GET /v1/characters`,
  **и** голос ответа в `POST /v1/chat/speech` (выключение флага снимает голос персонажа —
  резолв проваливается на следующую ступень); `catalog.presets_default_locale` → **и**
  `GET /v1/presets`, **и** `GET /v1/characters`, **и** `GET /v1/voices`;
  `chat.disabled_tool_families` → **и** каталог `GET /v1/tools`, **и** набор инструментов хода.
- **Видимость нормализации `general`** ([§8.1](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)):
  `PATCH chat.advertised_generation_modes` списком **без** `general` → `200`, и `general`
  присутствует **в ответе** `PATCH`, **в последующем `GET /v1/admin/settings`** и **в строке
  оверлея** (нормализация на записи). Diff-проверка: снятие добавления `DEFAULT_GENERATION_MODE`
  на записи обязано ронять кейс; кейс, читающий только `values.advertised_generation_modes()`,
  его **не** заменяет — он проверяет read-time барьер, а не то, что видит оператор.
- ⚠️ **Компонентный тест резолвера этих кейсов не заменяет** — он сам конструирует снимок и
  доказывает только устройство потребителя, а не поставку данных ему.

### Тариф чата — функция модели

- Две сессии на разных моделях с разной ценой → разные списания; **один и тот же режим** генерации.
- Один и тот же `model` в режимах `general`/`research`/`reasoning`/`study_learn` → **одинаковое**
  списание (регрессия на возврат надбавки за режим).
- Балансовый гейт, фактическое списание и `creditCost` берут значение из **одного** источника:
  кейс, где цена модели поднята, обязан одновременно изменить и `blockReason=credits_empty`-порог,
  и списанную сумму, и ответ `capabilities` (мост один — [ADR-064 §9](../../adr/ADR-064-study-learn-quiz-generation-mode.md)).
- `GET /v1/chat/v2/capabilities` **без** `?model=` → `creditCost` = максимум по каталогу и одинаков
  у всех элементов; **с** `?model=` → точная цена модели; неизвестная модель → `422`.
- Оверлей `tokens = 0` невозможен: `PATCH` отвечает `422`, БД-CHECK не пропускает.

### Медиа: ячейки и согласованность с пользовательским каталогом

- `prices[]` в `GET /v1/media/models` **совпадает** со списанием: для каждой комбинации ответ
  `POST /v1/media/*` даёт `creditsCharged`, равный соответствующей ячейке.
- **Дефолтная (представимая) таблица:** легаси-поля `credits`/`resolutionMultipliers`/
  `audioMultiplier` равны сегодняшним значениям **точно** (тест-снапшот).
- **Непредставимая таблица** (поднят только `4k`): цена, посчитанная по легаси-полям, **≥**
  фактического списания для **каждой** комбинации (проверяется перебором), и эмитится
  `media_price_legacy_overquote{model}`. Кейс обязан падать при замене округления вверх на вниз.

### Каналы начисления: у каждого своя пара «карта → фолбэк»

- **Параметризация по четырём каналам** (`cloudpayments` / `adapty` / `manual` / `storekit`): при
  пустом оверлее и продукте, отсутствующем в карте канала, начисляется **фолбэк ИМЕННО ЭТОГО
  канала**. Кейс обязан **падать** при подмене одного фолбэка другим — и фикстура обязана задать
  `CLOUDPAYMENTS_SUBSCRIPTION_TOKENS_GRANT`, `ADAPTY_SUBSCRIPTION_TOKENS_GRANT` и
  `SUBSCRIPTION_CREDITS_PER_PERIOD` **разными** числами: на совпадающих дефолтах (все 1000) подмена
  не видна, и тест прошёл бы при неверной реализации.
- **Ручная выдача плана (`manual`)** отдельным кейсом: продукт из `TOKEN_PRODUCTS`, которого нет в
  `CLOUDPAYMENTS_PRODUCT_TOKENS`, выдаётся с `SUBSCRIPTION_CREDITS_PER_PERIOD` — как сегодня, а не
  с `CLOUDPAYMENTS_SUBSCRIPTION_TOKENS_GRANT`.

### Продукты

- `POST /v1/admin/products` → продукт появляется в `GET /v1/admin/products`, начисляет по своему
  пути и виден в `GET /v1/tokens/products` (ветки 2 и 3) — **три** проверки, а не одна: «создан» ≠
  «начисляет» ≠ «в витрине».
- Дубликат `product_id` (в env-карте или уже созданный) → **`400`**, не `409` и не `500`.
- `avatar_tokens` в теле `POST`/`PATCH` → `400`; в ответах поле всегда `null`; **ключа
  `product_avatar_tokens_max` в `limits` НЕТ** (ассерт на отсутствие ключа, не на значение `0`:
  ключ с нулём объявил бы вторую валюту существующей, и CRM нарисовала бы неработающее поле).
  `limits` содержит ровно три ключа.
- `PATCH` неизвестного `product_id` → `400`; `PATCH` **не создаёт** продукт.
- `archived: true` → продукт исчезает из `GET /v1/tokens/products` **во всех трёх ветках**, но
  (а) вебхук/StoreKit по нему **начисляют**, (б) `POST /v1/admin/users/{id}/subscription` его
  **принимает**, (в) строка остаётся в `GET /v1/admin/products` с `archived: true`. Все три
  проверяются отдельными кейсами — правило витрины регулярно копируют на них «по аналогии».
- ⛔ **Archived-правка строки с НЕПОЛНЫМ источником — параметризованный кейс по классу, а не один
  пример** ([ADR-099 §6.1](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)).
  `PATCH {"archived": true}` на строке `PRODUCTS_CATALOG` **без `kind`**, **без `credits`**, с
  `credits: 0` и с `credits` **выше** `product_tokens_max` — все четыре ⇒ **`200`**, ни одного
  отказа. Кейс обязан **падать** при возврате на этот путь любой проверки класса или числа: именно
  такая проверка (стоявшая до разбора `archived`) и была дефектом. Отдельным ассертом — что после
  такой правки **не изменились** начисления по продукту и его отображение в каталоге: строка
  оверлея несёт только `archived`, а `name`/`tokens`/`purchase_kind` продолжают резолвиться из
  источника (диф-проверка: подмена значения в источнике обязана быть видна в `GET`).
- Правка, **несущая `tokens`**, на строке без класса покупки ⇒ **`400`** + лейбл
  `source_kind_missing` (соседнее правило с противоположным требованием — оба кейса обязательны,
  иначе одно перенесут на другое «по аналогии»).
- `tokens` строки с неизвестным классом отдаётся в `GET`/ответах как **`null`** (ассерт на `null`,
  а не на число источника): непустое значение заставило бы CRM отрисовать карандаш правки, которую
  мы обязаны отвергнуть.
- `if_updated_at` не совпал → `409`; совпал → `200`; повтор того же значения → `changed: false`.

### Настройки

- ⛔ **Ассерт на ЧИСЛО элементов запрещён — оно зависит от инстанса.** В реестре 14 величин, но
  ответ несёт только применимые к этому инстансу: `chat.anthropic_thinking_display` объявляется
  **только на Anthropic-инстансах** ([ADR-099 §8.1](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md),
  сноска ¹), поэтому Anthropic отдаёт **14**, а OpenAI — **13**. Константа в тесте протухла бы на
  половине флота, а не упала бы честно: она зелена ровно там, где её писали.
  **Проверяется предикат:** состав ответа равен реестру, отфильтрованному по применимости к
  конфигурации инстанса — по кейсу на каждый провайдер, с явной проверкой присутствия/отсутствия
  провайдер-зависимой строки. У каждого элемента — непустые `setting_id`/`type`/`label` и `value`,
  соответствующий `type`.
- **Негативный контракт-тест поверхности (обязателен):** ни один `setting_id` ответа не
  соответствует величине класса «секрет / инфраструктура / ресурсный лимит / денежная величина» —
  проверяется по перечню [ADR-099 §8.2](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md),
  включая `*_API_KEY`, `JWT_PRIVATE_KEY`, `KMS_LOCAL_MASTER_KEY`, `ADMIN_API_*`, `DATABASE_URL`,
  `TOKEN_PRODUCTS`, `CHAT_CREDIT_COST_*`. Тест обязан падать при добавлении такой величины в
  реестр настроек.
- **Коды отказа — по кейсу на каждый, без «или»** (предикат — [ADR-099 §11](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)):
  - значение не по `type` / вне `options` → **`422`**;
  - `chat.models_offered` = `[]` → **`422`** (нарушен объявленный `min_items: 1`);
  - `chat.advertised_generation_modes` = `[]` → **`422`**, и **не** трактуется как «сброс к
    fail-closed набору» — кейс обязан падать, если реализация перенесла на оверлей правило пустого
    env ([ADR-065](../../adr/ADR-065-study-learn-advertisement-gate-and-history-spoiler-strip.md) §1);
  - инвариант «дефолт ∈ витрине» — **`400`** (межэлементный, в объявлении невыразим), **двумя
    отдельными кейсами, в обе стороны**: `PATCH chat.models_offered` без текущей дефолтной модели
    и `PATCH chat.default_model` на модель вне витрины;
  - во **всех** случаях значение **не** меняется, аудит-события **нет**.
- **`options` выводятся из кода, а не из литерала в тесте:** ассерт сравнивает `options` строки с
  соответствующей константой (`SUPPORTED_PRESET_LOCALES`, `GENERATION_MODE_ORDER`,
  `DISABLEABLE_TOOL_FAMILIES`, `allowed_models_union()`). Кейс обязан **падать** при добавлении
  значения в константу без появления его в `options` — иначе перечень протухнет молча
  (`zh-Hans` — уже существующий пример).
- **Модельные строки ограничены включёнными провайдерами:** на инстансе `LLM_PROVIDER=openai` без
  `LLM_PROVIDERS` в `options` `chat.default_model`/`chat.models_offered` **нет ни одной**
  Anthropic-модели.
- `moderation.block_categories` имеет `type: "string"` (не `multi_enum`) и `constraints.max_length`;
  значение длиннее объявленного → **`422`**;
  при **любом** значении, включая пустую строку, `sexual/minors` остаётся заблокированной.
- Неизвестный `setting_id` → `400`; `PATCH` настроек не создаёт.

### `capabilities`, коды и аудит

- `features` содержит **ровно перечень [ADR-099 §7](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)** (на дату решения — восемь значений; ассерт сверяется с перечнем, а не с числом); каждое соответствует **реализованному**
  пути (кейс-детектор: удаление роутера обязано ронять тест).
- `cache_effective_after_seconds` == `effective_after_seconds` ответов `PATCH`/`POST` ==
  настроенное окно обновления снимка.
- **Ни один вход не даёт `404`** на восьми путях (сводный регресс-кейс — образец
  [ADR-092](../../adr/ADR-092-crm-daily-costs-endpoint.md)); `403`/`401` — как у прочих admin-путей.
- Аудит: успешная правка создаёт событие **своего** действия (`admin_product_created` /
  `admin_product_updated` / `admin_product_archived` / `admin_tariff_updated` /
  `admin_setting_updated`) с дельтой; отказ (`400`/`409`/`422`) **не** создаёт события; секрет
  `X-Admin-Key` в аудит и логи не попадает; `X-Admin-Actor` пишется как заявление.
- **Rate limit — позитивный кейс на КАЖДОМ из восьми путей:** превышение корзины
  `rl:admin_econ` → **`429`**. Это единственный кейс, который ловит забытый вызов лимитера в
  хендлере; проверка «страница из 6 вызовов не даёт `429`» проходит и при полностью отсутствующем
  лимитере, поэтому **сама по себе не засчитывается**.
- **Изоляция корзин:** исчерпание `rl:admin_econ` не влияет на `POST /v1/admin/wallet/grant`
  (корзина `rl:admin:`) и наоборот.
- **Дефолт применяется без правки `.env`:** при **отсутствующей** переменной
  `ADMIN_ECONOMICS_RATE_LIMIT_PER_MIN` потолок равен 120, и страница CRM (6 вызовов + 14 правок)
  не даёт `429`. Кейс закрывает ровно тот сценарий, ради которого заведена отдельная корзина.

### Наблюдаемость (достижимость, а не наличие)

- Удаление строки эмиссии любой метрики [ADR-099 §10](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)
  обязано ронять тест; серия обязана присутствовать в экспозиции `/metrics` **после реального
  вызова**, а не только в юните продюсера.
- **То же требование — к каждому из ШЕСТИ лог-событий** [§10](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md).
  Перечень задан **признаком** («всякий `log_event` в `src/app/instance_config/` и в
  `src/app/admin/economics_service.py`»), а не составом, и число датировано: событие, прошедшее
  признак, но не покрытое кейсом, — пробел покрытия, а не «новое событие».
- **`admin_overrides_snapshot_changed` — отдельный кейс на ОБЕ стороны перехода.** Правка через
  `PATCH`, меняющая состав оверлеев, ⇒ событие пишется (поля `products`/`tariffs`/`settings`);
  следующее обновление снимка **без** изменения состава ⇒ событие **не** пишется. Кейс «событие
  когда-нибудь появилось» формой не считается — он проходит и при эмиссии на каждом тике окна,
  то есть ровно при том дефекте, ради которого запись сделана на изменении состава.
- Отказ обновления снимка: значения остаются прежними (**не** откатываются к env),
  `admin_overrides_refresh_failures_total` растёт, `admin_overrides_snapshot_age_seconds` растёт.
- **Лейбл `reason` проверяется ПО ПРЕДИКАТУ, а не по факту инкремента**
  ([ADR-099 §10.0](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)) — кейс на
  **каждое** значение обоих перечней, и каждый обязан падать при подмене лейбла соседним:
  - `admin_overrides_refresh_failures_total`: `ProgrammingError` (таблиц нет) → `schema_mismatch`;
    прочий `SQLAlchemyError` (соединение/таймаут) → `db_error`; исключение, **не** являющееся
    ошибкой БД (падение на разборе строк или установке снимка) → **`unexpected`**. Последний —
    ловушка, ради которой кейс и написан: прежде эта ветка писала `db_error` и посылала дежурного
    в БД при дефекте нашего кода. ⚠️ **Кейс обязан падать при возврате к `db_error`** — «счётчик
    вырос» проходит при любом лейбле и ловушкой не является;
  - `admin_override_rejected_total` (**семь** значений, кейс на каждое): нарушение **объявленной**
    границы (`chat.models_offered` = `[]`, `moderation.block_categories` длиннее `max_length`,
    `tokens` **выше** `limits`, дробный `tokens` тарифа) → `out_of_range` **при `422`**; нарушение
    **необъявленной** нижней границы (`tokens: 0` на `one_time`; `tokens: 0` у тарифа) →
    **`undeclared_bound` при `400`** — ловушка кейса именно `out_of_range` + `422`, к которым
    лейбл и код обязаны **не** откатываться; нарушение **типа или `options`**, а также `PATCH`
    продукта с пустым телом → `type_mismatch`; неизвестный идентификатор → `unknown_id`; версия и
    межэлементный инвариант → `conflict`; непустой `avatar_tokens` → `unsupported_field`;
    **правка `tokens` у продукта из `PRODUCTS_CATALOG` без `kind`** → **`source_kind_missing`**
    (ловушка — `unsupported_field`, к которому лейбл не должен откатываться).
    ⛔ **`source_tokens_missing` из перечня СНЯТ, и кейса у него быть не может:** после
    [ADR-099 §6.1](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md) достижимой
    ветки-producer'а не остаётся, а archived-правка строки без `credits` обязана отвечать `200`
    (кейс выше). Появление этой серии на проде = откат §6.1;
  - `admin_override_value_ignored` (**три** достижимых значения того же словаря): строка
    `admin_settings` с `setting_id`, которого нет в реестре инстанса → **`unknown_id`**; значение,
    нарушающее `constraints` → `out_of_range`; значение не того типа или вне `options` →
    `type_mismatch`. Во **всех трёх** строка игнорируется, а инстанс продолжает работать на
    env/дефолте — кейс проверяет **и** лейбл, **и** неизменность разрешённого значения;
  - **разность множеств** «значения, объявленные [ADR-099 §10.0](../../adr/ADR-099-crm-admin-economics-and-instance-settings.md)»
    ↔ «значения, реально эмитируемые кодом» пуста **в обе стороны**: объявленное без producer —
    мёртвый лейбл, эмитируемое без объявления — второй словарь;
  - **пара** `media_price_table_non_representable` / `media_price_table_representable_again`:
    событие пишется **только на переходе** — повторный вызов с тем же состоянием строки **не**
    добавляет; обратный переход пишет второе событие. Кейс на **обе** стороны: половина пары,
    проверенная в одиночку, проходит и тогда, когда возврат не логируется вовсе.
