# ADR-118 — Голосовой WS: висящий client tool-call закрывается до следующего хода (дополнение ADR-114)

- **Статус:** Accepted. **Состояние реализации:** код закрытия в реплее — [ADR-114](ADR-114-superseded-client-tool-calls-in-history-replay.md) (в дереве: `_neutral_history_from_steps`); **нормативное дополнение этого ADR и voice-покрытие тестами — не реализованы этим проходом** (зона `backend` / `qa`).
- **Дата:** 2026-09-28
- **Связано:** [ADR-114](ADR-114-superseded-client-tool-calls-in-history-replay.md) (закрытие вытесненных вызовов в `_build_messages`), [ADR-104](ADR-104-voice-mode-websocket.md) (сокет, барьер, `tool.result`, turn lock), [ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md) (барьер хода — **не ослабляется**), [ADR-008](ADR-008-provider-tool-use-id.md).
- **Характер:** уточнение границы транспорта голосового режима и обязательного покрытия. Миграций нет. Новых кодов ошибок нет. Барьер ADR-025 для штатного `tool.result` **не меняется**.

## Контекст

**Прод-симптом (iOS, клиент 2.1):** в голосовом режиме модель вызывает `calendar.*` / телефонные client-tools; приложение из стора `tool.result` **не шлёт**; следующие ходы (и voice, и text в ту же сессию) → `502` / `upstream_error` (провайдер `400 No tool output found` → наш `502`).

### Замер по коду (этот проход, рабочее дерево)

1. **ADR-114 уже закрывает вытесненный вызов в общей сборке истории.** `_build_messages` → `_neutral_history_from_steps` вставляет синтетический `role=tool` с `error.code=tool_result_missing` без записи в БД. Голосовой ход исполняется `ChatOrchestrator.run` / `tool_result` с `generation_backend="v2"` (`src/app/api_gateway/routers/chat_voice.py`) — тот же путь, что HTTP v2. В тексте ADR-114 §2 уже сказано «включая голосовой ход».
2. **Turn lock / `_turn_task` не держат окно ожидания `tool.result`.** После ноги `done {status:"tool_call"}` задача ноги завершается, межпроцессный замок отпускается (`_run_leg` `finally`); ADR-104 §13.14 прямо: ожидание на барьере замком не покрывается. Следующий `utterance.end` / `text` проходит `_claim_turn`, если локальная нога не идёт.
3. **Пробел:** нормативное покрытие ADR-114 в [09-testing](../modules/chat-orchestrator/09-testing.md) и E2E заказано для HTTP `/chat/run` и `/chat/v2/run`, **без** сценария WS `/v1/chat/voice`. Транспортный инвариант «следующая реплика не блокируется ожиданием `tool.result`» в ADR-104 назван косвенно (замок), но **не** связан с ADR-114 как обязательное «перед следующим ходом висящий вызов закрыт». Клиент 2.1 эти tools не исполняет — барьер ADR-025 сам по себе хода не закроет никогда.

**Решение владельца (принято):** перед следующим ходом висящий вызов обязан закрываться ошибкой (клиент 2.1 эти tools не обрабатывает). Барьер ADR-025 для нормального `tool.result` не ослаблять.

## Решение

### §1. Закрытие — то же, что ADR-114; транспорт не вводит второй механизм

- Перед провайдерским вызовом **следующего** хода (новый `user`-шаг: кадр `utterance.end` / `text` на сокете **или** HTTP `/v1/chat/run` / `/v1/chat/v2/run` в ту же сессию) любой вытесненный по [ADR-114 §1](ADR-114-superseded-client-tool-calls-in-history-replay.md) вызов закрывается синтетическим `tool_result_missing` в реплее.
- **Не** вводится: авто-`tool.result` от транспорта, таймаут барьера, запись `tool_calls.status=errored` при новом ходе, отказ нового хода с `409 turn_in_progress` **только потому**, что предыдущий ждёт `tool.result`.
- Штатный путь: клиент прислал `tool.result` → барьер [ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md) и continuation **без изменений**. Запоздалый результат после нового `user`-шага → `409 conflict` ([ADR-114 §3](ADR-114-superseded-client-tool-calls-in-history-replay.md)), в том числе кадр `tool.result` на сокете.

### §2. Инвариант голосового транспорта (явная норма)

После кадра `done` с `status="tool_call"`:

1. Соединение **остаётся** открытым; сервер **не** считает ожидание `tool.result` «идущей ногой» для `_claim_turn` / turn lock (уже так в коде — закрепить тестом).
2. Следующая пользовательская реплика (`utterance.end` / `text`) **обязана** быть принята как новый ход (при прочих правилах §3/§13 ADR-104: не два одновременных хода, очередь после `interrupt` и т.д.) и **обязана** завершиться по обычному контракту хода, а не `502` из-за осиротевшего `tool_use` в реплее.
3. Если клиент так и не прислал `tool.result`, закрытие — исключительно через ADR-114 при сборке истории нового хода.

### §3. Покрытие (обязательное)

Минимум один integration/E2E-кейс на WS (или эквивалент с тем же оркестраторным входом, что `_VoiceSession._execute_turn`):

- ход голоса вернул client `tool_call` (`calendar.*` или любой client-side) → `tool.result` **не** отправлен → новый `text` или `utterance` в ту же сессию → ответ не `502`; fake-провайдер видит парный синтетический результат с `tool_result_missing`;
- контраст: тот же ход, но `tool.result` пришёл вовремя → continuation по ADR-025, без синтетики на этих `providerToolUseId`.

Кейсы 1–3 ADR-114 в HTTP **сохраняются**; voice — дополнительный носитель той же нормы, не замена.

### §4. Что не меняется

Набор инструментов голосового режима ([ADR-104](ADR-104-voice-mode-websocket.md): шестая ось гейтинга не вводится), биллинг, схема кадров, ADR-025 A2/B, TD-067.

## Последствия

- Документированная обязанность: voice + text после брошенного client tool-call не «отравляют» сессию, как только ADR-114 в проде и покрыт voice-кейсом.
- Исполнителю не изобретать отдельный closer в `chat_voice.py`, если `_build_messages` уже закрывает; обязанность — не регрессировать §2 и добавить §3.

## Альтернативы

- **Авто-закрывать pending в БД при `done{tool_call}`, если клиент «старый»** — отклонено: нет надёжного признака версии; ломает клиентов, которые шлют `tool.result` с задержкой; ослабляет ADR-025.
- **Сузить tools в voice (не отдавать calendar/phone)** — отклонено владельцем ранее в ADR-104 («набор не сужается»); чинится закрытие, не каталог.
- **Блокировать следующую реплику до `tool.result`** — отклонено: клиент 2.1 результата не пришлёт → вечный `turn_in_progress`.
