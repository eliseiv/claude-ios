# ADR-094: Инструменты работы с кодом — аналог Codex поверх существующего tool-loop

- **Статус:** Accepted
- **Дата:** 2026-08-29
- **Контекст запроса:** «нужно реализовать дополнительный функционал для инстанса, чтобы он смог быть аналогом Codex (генерация кода, изменения файлов, создание файлов, коммит и тд), чтобы пользователь с помощью данного инстанса через MacOS смог использовать ии для написания кода». Уточнение владельца: «Граница дозволенного полная, модель может запускать что угодно… подтверждение на каждый шаг и кнопка типа "Всегда доверять". Ограничений одним каталогом нет, можно пушить с --force по запросу клиента». Целевой инстанс — `fanappsnew.shop`.

## Контекст

В реестре уже есть `files.read` / `files.write` / `files.list` / `files.mkdir` — клиентские инструменты, исполняемые устройством и возвращающие результат через `/v1/chat/tool-result` ([ADR-011](ADR-011-tools.md)). Их достаточно, чтобы прочитать файл и записать файл, и **недостаточно**, чтобы вести работу над кодом:

| Чего не хватало | Почему без этого не обойтись |
|---|---|
| поиска по дереву | модель не знает раскладку чужого проекта и вынуждена угадывать пути; неверная догадка тратит ход |
| точечной правки | `files.write` переписывает файл целиком — значит модель обязана удержать в ответе весь файл, включая места, которых не касалась. Файл на 800 строк либо не поместится, либо будет воспроизведён по памяти с искажениями |
| удаления и перемещения | рефакторинг — это в том числе «файла больше нет» и «файл теперь здесь» |
| git | «сделай коммит» — половина запроса; без `status`/`diff` модель коммитит вслепую, не видя, что именно попадёт в коммит |

Существующие `files.*` дополнительно ограничены песочницей: `_PathModel` отклоняет абсолютные пути и `..`. Для помощника по коду это ограничение неприменимо — проект лежит там, где лежит.

## Решение

### 1. Десять инструментов, две группы

| Инструмент | Читает / меняет | Подтверждение |
|---|---|---|
| `files.search` | читает | нет |
| `files.patch` | меняет | **да** |
| `files.delete` | меняет | **да** |
| `files.move` | меняет | **да** |
| `git.status` | читает | нет |
| `git.diff` | читает | нет |
| `git.log` | читает | нет |
| `git.commit` | меняет | **да** |
| `git.branch` | меняет | **да** |
| `git.push` | меняет | **да** |

Исполнение — **клиентское**: файлы и репозиторий лежат на машине человека, бэкенд их не видит. Это та же схема, что у `calendar.*` / `reminders.*`, и она же объясняет, почему инструменты нельзя включить на инстансе, чей клиент их не реализует (см. §3).

### 2. `files.patch`, а не только `files.write`

Правка задаётся заменой фрагмента, а не целым файлом. Причина не в экономии токенов, а в точности: переписывая файл целиком, модель воспроизводит по памяти и те строки, которые менять не собиралась, — и незаметно меняет их. Системный промпт кодового режима предписывает предпочитать `files.patch`, а `files.write` оставить за созданием новых файлов.

### 3. Ось D — `CODE_TOOLS_ENABLED`, по умолчанию **выключено**

Флаг инстанса. Выключенный — инструменты не предлагаются модели вовсе.

Почему не «включить везде»: инструмент, который модель позвала, а клиент исполнить не умеет, оставляет ход незавершённым — tool-loop ждёт `tool-result`, которого не будет. Пока приложение под macOS в разработке, включение на iOS-инстансе ломало бы работающие сценарии. Флаг снимается по мере готовности клиента, инстанс за инстансом.

Ось D складывается с осью B (`assistant_mode`): инструменты предлагаются, только когда флаг включён **и** сессия в режиме `code`. Обычный чат на том же инстансе их не видит.

**Каталог `GET /v1/tools` осями не фильтруется** — он остаётся полным техническим реестром (как `quiz.generate`, доступный только в `study_learn`). Клиент по нему узнаёт, что вообще существует и что требует подтверждения, ещё до первого вызова.

### 4. Подтверждение задаёт сервер, а не клиент

`requiresConfirmation` едет двумя путями: в каталоге `GET /v1/tools` (чтобы приложение отрисовало «Всегда доверять» заранее) и в каждом `toolCall` ответа `/v1/chat/run`.

Почему не оставить решение клиенту: если приложение выводит «спрашивать ли» из имени инструмента, то первый же инструмент, нарушающий догадку, исполнится без диалога. Догадка ломается сразу — `files.search` только читает, `git.branch` меняет состояние, и оба начинаются с «безопасного» префикса. Признак принадлежит серверу, где и объявлен `CONFIRM_TOOLS`.

**Читающие инструменты подтверждения не требуют намеренно.** Диалог на каждый просмотр файла приучает нажимать «да» не глядя — и обесценивает тот единственный диалог, который действительно важен: перед `git.push --force`.

### 5. Границы сняты осознанно

- **Пути.** `_CodePathModel` принимает абсолютные пути и `..`. Это отдельная модель, а не послабление в `_PathModel`: `files.read` / `files.write` остаются в песочнице, и тест закрепляет, что послабление на них **не протекло**.
- **`force` при `git.push`** — отдельное булево поле, а не часть строки аргументов. Спрятанный внутри строки флаг человек в диалоге не увидит, а «отправить» и «отправить с перезаписью истории» — разные по последствиям действия.
- **`shell.run` в это решение не входит.** Произвольное исполнение команд — не расширение файловых инструментов, а другой класс возможности, и вводить его попутно, одной строкой в том же реестре, неправильно. Отдельный вопрос: [Q-094-1](../99-open-questions.md).

## Последствия

- Инструментов в реестре стало вдвое больше; каждый объявляется в пяти местах (`ALL_TOOL_NAMES`, `_ARGS_BY_TOOL`, `TOOL_DESCRIPTIONS`, карта имён Anthropic, при необходимости `MUTATING_TOOLS`/`CONFIRM_TOOLS`). Пропуск любого из них не виден при чтении кода, поэтому полнота регистрации проверяется параметризованным тестом по всему `CODE_TOOLS`, а не примером.
- Имена содержат точку, Anthropic точку в `tool.name` отклоняет (400 → наружу 502). Отображение в подчёркивание на транспортной границе распространено на новые инструменты и закреплено тестом.
- Клиент под macOS обязан реализовать все десять исполнителей до включения флага на его инстансе.

## Альтернативы

- **Серверное исполнение (репозиторий на бэкенде).** Отвергнуто: человек работает над своим локальным проектом, а не над копией на сервере; синхронизация в обе стороны — отдельная система, и она не то, о чём просили.
- **Один инструмент `code.do` со свободной строкой команды.** Отвергнуто: диалог подтверждения тогда показывает человеку строку, смысл которой ему надо разобрать самому, и сервер не может отличить чтение от записи — то есть §4 становится нереализуемым.
