## Контекст

Продукту нужен обучающий сценарий Study & Learn: пользователь просит объяснить тему, а ответ содержит **интерактивный квиз** — пул вопросов с вариантами ответов, которые iOS рендерит карточками. Пользователь отвечает локально, результат считается на клиенте.

Уже существующий v2-flow (`/v1/chat/v2/*`, [10-generation-modes-implementation.md](../modules/chat-orchestrator/10-generation-modes-implementation.md)) даёт готовую ось **`generationMode`** (`general | research | reasoning`) с per-turn выбором, mode-specific ценой и эндпоинтом `GET /v1/chat/v2/capabilities` для UI-переключателя. Квизу нужен ровно такой же гейт: включается пользователем на конкретный ход, имеет свою цену, объявляется клиенту заранее.

Ограничения контекста, влияющие на решение:

1. **Провайдерского strict-режима у нас нет.** Tool-definitions строятся `neutral_tool_definitions()` и сериализуются per-provider ([ADR-033 §4](ADR-033-llm-provider-abstraction.md)); OpenAI Responses-клиент выставляет инструментам `strict: False`, Anthropic strict вообще не поддерживает. Значит структура аргументов, которые модель кладёт в `quiz.generate`, **ничем не гарантирована** — ни типы, ни межполевые инварианты (`correctIndex < len(options)`).
2. **Невалидные args инструмента сейчас роняют ход.** `validate_tool_args()` в `_handle_tool_use` бросает `ValidationFailedError` → `422` на весь ход. Для инструмента, чьи ограничения провайдер не обеспечивает, это означало бы регулярную потерю уже выполненной работы (объяснение темы сгенерировано, ход отброшен).
3. **Прецедент мягкой деградации в этом же коде уже есть:** `time.now` с невалидным `tz` возвращает tool-result error `invalid_timezone`, ход выживает ([ADR-026 §6](ADR-026-global-server-side-tools-and-time-now.md)).

## Решение

### 1. Гейт — четвёртое значение оси `generationMode`, отдельной оси `dialogMode` нет

`generationMode` расширяется до `general | research | reasoning | **study_learn**` в `ChatV2RunRequest` (`/v1/chat/v2/run`). Отдельная ось «режим диалога» **не вводится**: у продукта уже есть один пользовательский переключатель режима хода со своей ценой и своим capabilities-контрактом; второй переключатель означал бы вторую матрицу цен, второй список в capabilities и неопределённость на пересечениях (`research` + `study_learn`?).

Режим **turn-scoped**, как остальные значения оси: в одной сессии ход может быть `study_learn`, следующий — `general`. Выбранное значение персистится в user-шаге (`chat_steps.payload.generationMode`) и читается continuation-ом.

**Не меняются:** ось `mode` (`credits|byok`), ось `assistantMode` (`chat|code`), legacy `POST /v1/chat/run` и `POST /v1/chat/tool-result` (см. §11).

### 2. Квиз выдаётся моделью через global server-side tool `quiz.generate`

Инструмент `quiz.generate` — **server-side global** ([ADR-026](ADR-026-global-server-side-tools-and-time-now.md)): исполняется backend'ом прямо в tool-loop, проекта не требует, в `toolCalls[]` наружу не отдаётся, отдельных списаний не вводит. «Исполнение» = **валидация аргументов + эхо-возврат** пула как tool-result. Модель за один ход и пишет обучающий текст, и вызывает инструмент; loop продолжается, ход завершается обычным финальным assistant-шагом.

Почему инструмент, а не «форсировать формат всего ответа»: форматом ответа (`response_format`/`text.format`) нельзя получить одновременно свободный текст и строгий объект, а у нас strict на tools и так выключен (см. §5) — выигрыш формата ответа был бы куплен потерей текста.

Почему server-side, а не client-side tool: iOS ничего не вычисляет для квиза — пул порождает модель. Client-side означал бы лишний round-trip и участие клиента в tool-loop ради эха.

### 3. Ось C гейтинга tool-набора: инструмент, доступный только в своём режиме

Вводится **третья ось** гейтинга набора инструментов, предлагаемого модели (в дополнение к оси A «наличие проекта», [ADR-022](ADR-022-optional-project-and-tool-gating.md), и оси B «assistant_mode», [Q-012-1](../99-open-questions.md) Open):

> **Ось C (режим генерации):** инструмент, объявленный mode-gated, предлагается модели **тогда и только тогда**, когда эффективный режим хода входит в его набор режимов.

Реестр — `TOOL_GENERATION_MODES: dict[tool_name, frozenset[mode]]` в `src/app/chat/tools.py` (SSOT инструментов, рядом с `SERVER_SIDE_TOOLS`/`GLOBAL_SERVER_SIDE_TOOLS`). Единственная запись на сегодня: `quiz.generate → {"study_learn"}`. Инструмент, отсутствующий в реестре, не гейтится по режиму (все прочие 14 — как раньше).

**Инвариант «эффективный режим — одна величина».** Гейт оси C вычисляется по **тому же** значению режима, которое уходит провайдеру и в биллинг (`generation_mode if use_generation_v2 else "general"`), а не по полю запроса. Отсюда следствие, важное для legacy: legacy-path подставляет `general` → `quiz.generate` на legacy **не предлагается никогда**, без отдельной ветки-исключения.

**Sweep по всем 15 инструментам** (какая ось на что действует) — таблица в [03-architecture.md §Оси гейтинга tool-набора](../modules/chat-orchestrator/03-architecture.md); проверено, что ось C не задевает ни один существующий инструмент.

### 4. Контракт аргументов `quiz.generate` — пул вопросов в одном вызове

```json
{
  "questions": [
    {
      "question": "…",
      "options": ["…", "…"],
      "correctIndex": 0,
      "explanation": "…"
    }
  ]
}
```

- `questions` — **3..10** вопросов. Нижняя граница 3 = осмысленный пул, верхняя 10 = потолок по токенам/латентности.
- `question` ≤ 1000 символов; `options` — **2..10** вариантов, каждый ≤ 400; `correctIndex` — целое 0-based, `0 ≤ correctIndex < len(options)` (**bool не принимается** — в Python `bool` является подтипом `int`); `explanation` ≤ 2000.
- Все поля обязательны, `extra='forbid'` на обёртке и на каждом вопросе.

**Пул в ОДНОМ вызове, а не N вызовов инструмента.** Каждый вызов расходует server-side раунд tool-loop'а ([ADR-011 §2](ADR-011-server-side-tools.md)); N вызовов дают недетерминированное число вопросов, лишние раунды и латентность. Один вызов = детерминированно «сразу пул», простой клиент (`quiz.questions[]`) и простой аккумулятор.

**Схема, уходящая провайдеру, обязана быть self-contained** — без `$ref`/`$defs`: вложенная модель вопроса инлайнится в `inputSchema`. Причина: `input_schema`/`parameters` уходят двум разным провайдерам, и опираться на их поддержку `$ref` мы не обязаны. Ограничивающие ключи (`minItems`/`maxItems`/`maxLength`) в схеме **остаются** (strict у нас выключен, провайдер их не отвергает) и работают как подсказка модели; нормативная проверка — всё равно серверная (§5).

### 5. Режим отказа — graceful degrade, а не `422` (новый реестр `ARGS_DEGRADE_TOOLS`)

Поскольку ни один провайдер в этой интеграции не гарантирует ни типы, ни межполевые инварианты аргументов, **нарушение ограничений квиза — ожидаемый сценарий, а не аномалия**. Поэтому:

Вводится реестр **`ARGS_DEGRADE_TOOLS`** (`tools.py`) — инструменты, у которых провал валидации аргументов **деградирует**, а не роняет ход. Единственная запись: `quiz.generate`.

Нормативное поведение в `_handle_tool_use` при `validate_tool_args(...)` → ошибка валидации:

| Инструмент | Поведение (нормативно) |
|---|---|
| `tool_name ∈ ARGS_DEGRADE_TOOLS` (`quiz.generate`) | **НЕ** `ValidationFailedError`. Создать `tool_calls` (сырой `input` модели в `args`), сразу перевести в `status=errored`, персистировать tool-шаг с `error = {"code":"invalid_quiz","message":…}`, добавить запись в `serverTools[]` (`status=errored`, `summary="invalid_quiz"`), **продолжить loop** — модель видит ошибку в том же ходе и перегенерирует пул. |
| любой другой инструмент | Прежнее поведение — `ValidationFailedError` → `422`. Изменений нет. |

**Контраст (обязателен к сохранению в коде и docs):** две соседние ветки одного `except` ведут себя **противоположно**. Ветка `quiz.generate` деградирует потому, что её ограничения физически не может обеспечить провайдер; ветка прочих инструментов роняет ход потому, что их args приходят из фиксированных схем, и кривой args там — реальная аномалия. Перенос поведения «по аналогии» с одной ветки на другую в обе стороны — ошибка.

**All-or-nothing.** Любое нарушение делает невалидным **весь** пул (вопросов вне `3..10`, пустой список, у любого вопроса вариантов вне `2..10`, over-length поле, `correctIndex` булев/отрицательный/вне диапазона) → один `invalid_quiz`, модель перегенерирует весь пул. Частичное принятие (выкинуть плохой вопрос) отклонено: молча ужимает пул ниже запрошенного и лишает модель обратной связи.

**Content-free сообщение.** `message` ошибки строится из `loc` + типа ошибки Pydantic (например `questions.2.correctIndex: out of range; expected 3-10 questions, 2-10 options, 0-based correctIndex < len(options)`) — **без значений полей**: текст квиза не должен утекать в tool-result-эхо логов/audit сверх того, что уже хранится в шаге.

**Граница.** Каждая неудачная попытка расходует server-side раунд; упорство модели упирается в существующий общий guard `MAX_SERVER_TOOL_ROUNDS` (дефолт 16) → audit `max_server_tool_rounds_exceeded`, `UpstreamError → 502`, **без биллинга** ([ADR-011 §2](ADR-011-server-side-tools.md)). Квиз-специфичной «мягкой посадки» не вводится: исчерпание 16 раундов на квизе патологично, а отдельная ветка добавила бы второй путь завершения хода.

### 6. Defensive guard: `quiz.generate` вне `study_learn` — деградирует, а не роняет ход

Если модель вернёт `tool_use` с именем `quiz.generate` в ходе, где инструмент не предлагался (upstream-аномалия), backend **не исполняет** инструмент: tool-call сразу `errored` с `error.code = "tool_not_available"`, ход продолжается, `quiz` в ответе остаётся `null`.

**Приоритет двух веток отказа (нормативно).** Ветки могут пересечься: инструмент вызван **вне режима** И с невалидными args. Проверка режима выполняется **ПЕРВОЙ**, до валидации аргументов, поэтому побеждает `tool_not_available`; `invalid_quiz` в таком ходе не возникает. Обоснование: аргументы инструмента, который вообще не предлагался, валидировать бессмысленно, а сообщение `invalid_quiz` увело бы модель чинить пул и повторно упираться в недоступный инструмент (лишние server-side раунды до `MAX_SERVER_TOOL_ROUNDS`). Порядок обязан быть зафиксирован в коде явно, а не следовать из случайного расположения веток.

**Контраст с [ADR-022 §guard](ADR-022-optional-project-and-tool-gating.md) (обязателен, поведение противоположно):** `site.*` в сессии без проекта → `UpstreamError` (жёсткий отказ хода), потому что там исполнение потребовало бы **резолва проекта** — это граница изоляции пользовательских данных (IDOR). `quiz.generate` побочных эффектов не имеет вообще (валидация + эхо), исполнять его безопасно — но не нужно, поэтому мягкий отказ дешевле жёсткого. Не переносить поведение между этими двумя guard'ами.

### 7. Отдача клиенту: поле `quiz` в `ChatResponse`; при непустом `quiz` — `assistantMessage = null`

**`ChatResponse.quiz: QuizSchema | null`** — аддитивное nullable-поле, присутствует всегда; значение `null` означает «квиза не было **в этом ходе** (`messageStepId`)», а не «не было в этом вызове» (см. turn-scope ниже):

```json
{ "questions": [ { "question": "…", "options": ["…","…"], "correctIndex": 0, "explanation": "…" } ] }
```

- **Семантика поля — TURN-scoped, а не per-call (нормативно).** `quiz` любого ответа хода = **последний валидный пул ЭТОГО ХОДА** (`messageStepId`), а не «пул, произведённый в этом HTTP-вызове». Правило одинаково для **всех** ног хода: `/v1/chat/v2/run`, каждый `/v1/chat/v2/tool-result`-continuation, идемпотентный реплей закрытого хода и `blocked+max_tokens`.
  - **Producer:** аккумулятор текущего вызова (last-wins, если модель вызвала инструмент несколько раз; склейка пулов отклонена — недетерминированный размер и дубли вопросов).
  - **Фолбэк-producer:** если аккумулятор этого вызова пуст **и** эффективный режим хода = `study_learn` → прочитать последний tool-шаг хода с `toolName = quiz.generate` и непустым `result`. Нет такого шага → `null`. Предикат `study_learn` обязателен: он держит дополнительную выборку строго на квиз-ходах, вне их (все прочие режимы и весь legacy) лишнего запроса нет.
- **Почему turn-scoped, а не per-call (это и есть носитель гарантии §7).** Подавление `assistantMessage` ключевано на непустом `quiz`. При per-call-семантике штатный многовызовный ход ломает гарантию: модель в одном assistant-шаге вызывает `quiz.generate` **и** client-side инструмент → `/v1/chat/v2/run` отдаёт `tool_call` с пулом (текст подавлен), а следующая нога `/v1/chat/v2/tool-result` завершает ход финальным `assistant_message`, где аккумулятор пуст → `quiz=null` → подавление не срабатывает → пользователь получает ровно тот дубль вопросов и раскрытые ответы, от которых защищает §7. Turn-scoped-правило закрывает **все** ноги одним предикатом; идемпотентный реплей перестаёт быть отдельным случаем и становится частным случаем фолбэка.
- **Клиент трактует `quiz` как содержимое ХОДА, а не дельту:** один и тот же пул может прийти в нескольких ответах одного `messageStepId` — это ожидаемо; карточки заменяются (идемпотентно), не накапливаются. Разные ходы → разные пулы.
  > **Контраст с `serverTools[]` (поведение противоположно, намеренно):** `serverTools[]` — **per-call** и при реплее **пустой `[]`** ([ADR-028](ADR-028-projectid-in-chat-list-and-server-tools-in-chat-response.md)), потому что это **индикатор выполнения в ЭТОМ вызове**: реконструировать его значило бы утверждать, что инструменты отработали в вызове, где tool-loop не запускался. `quiz` — **контент хода**, а не индикатор, и его потеря на любой ноге хода немедленно ломает анти-спойлерную гарантию. Правило одного поля **не переносить** на другое ни в одну сторону.

**`assistantMessage = null` при непустом `quiz` (детерминированная гарантия).** Проблема «модель дублирует вопросы в тексте и сразу раскрывает правильный ответ» — текстовая; надёжно вырезать спойлер из свободного текста семантически невозможно. Поэтому два уровня:

- **мягкий:** описание `quiz.generate` и статичный системный суффикс режима `study_learn` предписывают задавать вопросы **только** через инструмент, не повторять их в тексте и не раскрывать правильные варианты;
- **жёсткий (нормативный):** в единственной точке маппинга `ChatRunOut → ChatResponse` (`_to_response`, роутер чата) при непустом `quiz` поле `assistantMessage` принудительно выставляется в `null` — **при любом статусе** (`assistant_message`, `tool_call`, `blocked`+`max_tokens`: подавляется и частичный текст обрыва). Прочие правила `max_tokens` ([ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md): `usage`/`messageStepId`/`stepId` присутствуют, кредит не списывается) не меняются.

Правило ключевано **на присутствии `quiz`**, а не на endpoint'е или режиме, поэтому оно физически не может сработать на legacy-ходе (там `quiz` всегда `null`). Это **частично переопределяет [ADR-024 п.3](ADR-024-history-payload-domain-normalization.md)** («сопутствующий текст пробрасывается в `assistantMessage`») — **только** для ходов с квизом; все прочие ходы не затронуты.

**Осознанное следствие, не долг:** `chat_steps` хранит assistant-шаг **как есть** (с текстом, если модель его написала), и `GET /v1/chats/{id}` отдаёт его без изменений. Read-time strip текста в истории (по образцу [ADR-042](ADR-042-hide-context-block-from-user-facing-history.md)) **отклонён**: спойлер вреден в момент прохождения квиза (живой ход, где `assistantMessage` уже подавлен), а повторное открытие чата происходит после прохождения; ради краевого случая усложнять чтение соседнего модуля `chats` не оправдано. Мягкий уровень (промпт) держит персистируемый текст коротким.

### 8. Проверка ответов — на клиенте; серверного эндпоинта нет (нормативно)

`correctIndex` и `explanation` уходят клиенту в составе `quiz.questions[]`; iOS проверяет ответы локально и **ничего не отправляет назад**. Эндпоинта проверки/продолжения по результатам квиза **нет** и не планируется этим ADR. Это осознанный компромисс: квиз — обучающий инструмент, а не экзамен с античитом; серверная проверка потребовала бы хранить состояние квиза и вводить новый эндпоинт. «Скрытый» правильный ответ — отдельная будущая фича с серверным состоянием, а не долг этого решения.

### 9. Ценообразование — тем же механизмом, что у остальных режимов

Новая env **`CHAT_CREDIT_COST_STUDY_LEARN`**, дефолт **`2`**; `Settings.chat_generation_credit_cost("study_learn")` возвращает её.

**Инвариант положительности (обязателен, легко потерять).** У трёх существующих цен режимов есть общий field-валидатор, клампящий `≤ 0` к `1` (мис-конфиг env не делает генерацию бесплатной). Новое поле **обязано** попасть в **тот же** валидатор — не в собственный и не мимо: цена `0`/отрицательная на инстансе тихо сделала бы режим бесплатным (нет ни ошибки старта, ни блокировки — балансовый гейт пропустит, дебит спишет ноль). Это ошибка того же класса, что «объявлено, но не подключено»: поле есть, защита к нему не применена. Требование продублировано в [10-generation-modes-implementation.md §Config](../modules/chat-orchestrator/10-generation-modes-implementation.md#config), [07-deployment.md §env](../07-deployment.md#конфигурация-env) и покрыто unit-требованием в [09-testing.md](../modules/chat-orchestrator/09-testing.md#integration--study--learn-квиз-adr-064).

Второго механизма цены не вводится: это тот же единственный мост «режим → сумма списания», который используется и для pre-generation balance-гейта, и для финального идемпотентного дебита — режим не может быть допущен по одной цене и списан по другой.

Обоснование дефолта `2` (между `general=1` и `research=3`/`reasoning=3`): ход `study_learn` **детерминированно** делает минимум два upstream-вызова (вызов инструмента + продолжение) и генерирует объёмный output (3..10 вопросов с пояснениями), но **не** включает ни hosted web search, ни thinking-бюджет — то есть дешевле `research`/`reasoning`. Значение перекрывается per-instance через env, как и у соседей.

Биллинг в остальном не меняется: списание — один раз на финальном `assistant_message`, идемпотентно по `messageStepId` ([ADR-006](ADR-006-credit-billing-and-subscription-grant.md)); server-side раунды (включая `quiz.generate`) списаний не добавляют; BYOK и trial внутренние кредиты не тратят.

### 10. Объявление режима клиенту: `GET /v1/chat/v2/capabilities`

В `generationModes[]` добавляется **четвёртым** элементом `{"mode":"study_learn","creditCost":<из env>,"available":true}`. Позиция — в конец списка (существующий порядок `general, research, reasoning` не сдвигается). `available: true` на всех инстансах и обоих провайдерах: режим не требует провайдер-специфичных возможностей. Per-instance выключатель режима **не проектируется** (не требуется продуктом); операторская ручка на сегодня — только цена.

### 11. Обратная совместимость

- **Legacy `POST /v1/chat/run` / `POST /v1/chat/tool-result` — без изменений:** `ChatRunRequest` по-прежнему **не имеет** поля `generationMode` (лишнее поле → `422`, `StrictModel`), цена фиксированная, `quiz.generate` не предлагается (§3, инвариант эффективного режима), `quiz` в ответе всегда `null`.
- **v2-клиенты, не знающие о режиме:** не присылают `generationMode` → `general` (дефолт), поведение прежнее; в capabilities получают неизвестный им элемент списка и обязаны его игнорировать (обычная forward-compat семантика перечня).
- **Поле `quiz`** аддитивно и nullable: старые клиенты его игнорируют. Форма существующих полей не меняется, новых статусов и `blockReason` не вводится.
- **Схема ответа общая** для legacy и v2 (`ChatResponse`, один маппинг `_to_response`) — отдельная v2-модель ответа не вводится (форк схемы ради одного nullable-поля дороже, чем аддитивное поле).
- **Миграции БД нет**, новых таблиц нет: пул живёт в `chat_steps.payload` tool-шага, режим — в user-шаге.

### 12. Проверка подключения объявленного (declared ≠ wired)

Для каждого вводимого артефакта — точка производства и потребитель (иначе артефакт мёртв):

| Артефакт | Producer (рабочий путь) | Consumer |
|---|---|---|
| значение `study_learn` оси `generationMode` | `ChatV2RunRequest` ← тело `/v1/chat/v2/run` | `orchestrator.run(generation_mode=…)` → гейт оси C + цена + persist в user-шаг |
| `chat_steps.payload.generationMode = "study_learn"` | user-шаг v2-хода | `generation_mode_for_message_step()` на `/v1/chat/v2/tool-result` (**обязан принимать 4-е значение**, иначе continuation молча падает на `general`: и цена, и tool-набор) |
| `TOOL_GENERATION_MODES` | `neutral_tool_definitions(generation_mode=…)` в `_generate_loop` | tool-набор, уходящий провайдеру |
| `quiz.generate` в `_ARGS_BY_TOOL`/`GLOBAL_SERVER_SIDE_TOOLS`/`TOOL_DESCRIPTIONS` | `_handle_tool_use` → `GlobalToolHandlers.execute` | tool-шаг, `serverTools[]`, аккумулятор пула |
| `ARGS_DEGRADE_TOOLS` | ветка обработки ошибки `validate_tool_args` | tool-result `invalid_quiz` → модель в том же ходе |
| `ChatRunOut.quiz` (turn-scoped) | аккумулятор в `_generate_loop` (терминальные ветки: `assistant_message`, `tool_call`, `max_tokens`) **+ единый фолбэк** «аккумулятор пуст и режим хода = `study_learn` → последний валидный quiz-шаг хода», применяемый на ВСЕХ ногах, включая `_render_saved_step` | `_to_response` → `ChatResponse.quiz` + подавление `assistantMessage` |

## Альтернативы

- **Отдельная ось `dialogMode` (как в референсной реализации другого сервиса).** Отклонено (решение владельца продукта, зафиксировано здесь): у продукта уже есть per-turn ось режима с ценой и capabilities; вторая ось означает вторую матрицу цен, второй список для UI и неопределённое поведение на пересечениях осей.
- **Форсировать структурированный вывод всего ответа (`response_format`/`text.format`, strict).** Отклонено: strict делает **весь** ответ квиз-JSON — свободному объяснению места не остаётся; к тому же strict на tools в этой интеграции выключен для обоих провайдеров, то есть выигрыш был бы куплен потерей текста без гарантий взамен.
- **Свободный JSON в тексте ответа без инструмента.** Отклонено: парсинг хрупок, нет ни схемы, ни точки серверной валидации, ни детерминированного места для degrade.
- **Одна карточка вместо пула (первоначальная форма референса).** Отклонено: продукту нужен пул сразу; одна карточка вынуждает либо N вызовов, либо N ходов.
- **N вызовов `quiz.generate` с аккумуляцией в пул.** Отклонено: недетерминированное число вопросов, лишние server-side раунды и латентность, риск спойлер-текста между вызовами.
- **`422` на невалидные args квиза (текущее общее поведение).** Отклонено: провайдер не обеспечивает межполевые инварианты, поэтому такой отказ был бы штатным и терял бы уже сгенерированное объяснение. Degrade — прямой прецедент `time.now`/`invalid_timezone`.
- **Частичное принятие пула (drop плохого вопроса).** Отклонено: молча ужимает пул, усложняет аккумулятор, лишает модель обратной связи.
- **Жёсткий guard (`UpstreamError`/502) на вызов `quiz.generate` вне режима — по аналогии с `site.*`.** Отклонено: аналогия ложная, у квиза нет побочных эффектов и границы изоляции данных; мягкий отказ сохраняет ход.
- **Отдельная таблица `quizzes` + эндпоинт проверки ответов.** Отклонено: клиентская проверка достаточна для обучающего сценария; серверное состояние и новый эндпоинт — отдельная фича при реальной потребности в античите.
- **Client-side tool (квиз исполняет iOS).** Отклонено: клиенту нечего вычислять, это лишний round-trip и участие в барьере хода.
- **Отдельная response-модель для v2 вместо аддитивного `quiz` в `ChatResponse`.** Отклонено: форк схемы ответа ради одного nullable-поля дороже, чем поле; маппинг остаётся один (и потому правило подавления `assistantMessage` имеет ровно одну точку применения).
- **Per-call-семантика `quiz` (пул только того HTTP-вызова, где он произведён; на реплее — `null`, по симметрии с `serverTools=[]`).** Отклонено (§7): симметрия ложная — `serverTools[]` это индикатор выполнения в текущем вызове, а `quiz` — контент хода. Per-call-правило рвёт анти-спойлерную гарантию на **двух** штатных путях: (а) многовызовный ход (квиз выдан в ноге `run`, финальный текст приходит в ноге `tool-result` → `quiz=null` → подавление не срабатывает); (б) сетевой ретрай закрытого хода. Turn-scoped-правило закрывает оба одним предикатом.
- **Точечная заплатка «реконструировать `quiz` только в `_render_saved_step`».** Отклонено: чинит лишь путь (б) и оставляет путь (а) — то есть ровно тот класс ошибки, ради которого правило вводилось, просто в другом месте. Предикат обязан вычисляться на **всех** ногах хода, а не в том месте, где дефект заметили.
- **Подавлять `assistantMessage` по режиму хода (`generationMode == study_learn`), а не по присутствию `quiz`.** Отклонено: это глушит текст и в ходах `study_learn`, где модель квиз **не** выдала (пользователь остался бы вообще без ответа), и требует знания режима в точке маппинга ответа. Ключ на присутствии `quiz` вместе с turn-scoped-семантикой даёт ту же полноту без этого побочного эффекта.
- **Оставить `assistantMessage` как есть, полагаясь только на промпт.** Отклонено: текстовое поведение модели ненадёжно (дубль вопроса и спойлер ответа — воспроизводимая жалоба на такой же реализации); нужна детерминированная гарантия.
- **Per-instance флаг включения режима.** Не проектируется — не запрошено; включать/выключать фичу деплоем сейчас незачем, а мёртвый флаг был бы объявлением без потребителя.

## Последствия

- **Положительные:** квиз-пул приходит одним ходом, без нового эндпоинта, без БД-миграции и без второго механизма цены; переиспользованы три существующих механизма (global server-side tools, degrade tool-result, mode-specific цена + capabilities); детерминированно нет спойлера в живом ходе; legacy-контракт неизменен по построению, а не по договорённости.
- **Цена:** новый инструмент и две новые записи-реестра в `tools.py` (`TOOL_GENERATION_MODES`, `ARGS_DEGRADE_TOOLS`); третья ось гейтинга tool-набора (усложнение правил набора инструментов); переопределение [ADR-024 п.3](ADR-024-history-payload-domain-normalization.md) для квиз-хода; каталог `/v1/tools` вырастает с 14 до 15 инструментов; system-prompt для `study_learn` отличается статичным суффиксом → у этого режима отдельная запись prompt-кэша (внутри режима префикс стабилен, кэш не ломается).
- **Безопасность/приватность:** новых данных пользователя не хранится; `correctIndex` намеренно клиентский (обучение, не экзамен); инструмент не мутирует (нет `tool_mutation` audit) и не резолвит проект (нет IDOR-поверхности); `serverTools[].summary` квиза — `"ok"`/`invalid_quiz`, без содержимого; текст квиза не попадает в audit (там только id/имя/статус).
