# ADR-112 — Серверное чтение результата задачи (подготовка аватара) идёт по списку хостов результата, а не по fal-only списку

- **Дата:** 2026-09-24
- **Тип:** fix-ADR (модуль [media-generation](../modules/media-generation/README.md)); закрывает [TD-063](../100-known-tech-debt.md).
- **Пересматривает:** один элемент [ADR-108 §7](ADR-108-media-generation-via-proxy.md) п.(3) — `download_asset` в перечне путей, остающихся на fal-only списке. ## Контекст

- [ADR-108 §7](ADR-108-media-generation-via-proxy.md) оставил `download_asset` на fal-only списке с обоснованием «куда результат чужого вендора попадать не должен». **Уточнение факта:** обоснование ложно — тот же §7 фиксирует факт пилота: прокси отдаёт файлы результата со своего relay-хоста (`relay2.mediabackender.com`) **в том числе для маршрута `fal`**. `download_asset` читает `assets[0].url` задачи, т.е. результат задачи, и на инстансе на прокси это relay-URL.
- Следствие: на инстансе на прокси подготовка аватара получает `untrusted_asset_url` (`UpstreamError`), completion handler падает транзиентно, задача повторяется до дедлайна и закрывается `failed` с возвратом ([TD-063](../100-known-tech-debt.md)). Живым прогоном не проверено.

## Решение

1. **Инвариант (по форме, а не по месту):** любое серверное ЧТЕНИЕ URL, который является РЕЗУЛЬТАТОМ задачи генерации (`media_jobs` → ассеты задачи), проверяет хост дефолтным списком результата `FAL_UPLOAD_HOST_SUFFIXES ∪ MEDIA_RESULT_HOST_SUFFIXES` (`fal_asset_host_allowed(url)` без явного `suffixes`). Fal-only список допустим только там, где URL по построению выдан хранилищем fal (слот загрузки) или где за чтением следует ЗАПИСЬ в хранилище fal.
2. **`download_asset` переводится на дефолтный список.** Граница SSRF не ослабляется: проверка хоста — ДО запроса; только `https`; без редиректов (httpx по умолчанию их не следует, явного `follow_redirects=True` быть не должно); ключ fal не отправляется; лимит размера `_MAX_REFERENCE_DOWNLOAD_BYTES` и отказ на пустом теле — как сегодня. Код отказа при неразрешённом хосте — прежний (`untrusted_asset_url`).
3. **Контраст — пути, остающиеся на fal-only списке (помечены с обеих сторон):**
   - `upload` — `upload_url` (цель `PUT` с байтами пользователя) и `file_url` выдаёт хранилище fal (`POST …/storage/upload/initiate`); чужой хост там — признак подмены, поэтому только fal-хосты. Это ЗАПИСЬ, не чтение результата.
   - `rehost_reference_image` — читает кадр только затем, чтобы ЗАПИСАТЬ его в хранилище fal; URL вне fal-списка отдаётся как есть, fal скачивает его сам ([ADR-108 §7](ADR-108-media-generation-via-proxy.md), «Следствие для `rehost_reference_image`»). Отказа нет, долга нет; поведение не меняется.
4. **Свип по признаку «серверный читатель URL результата задачи»** (поиск по имени функции `fal_asset_host_allowed` и по `_upload_host_allowed`/`download_asset` по `src/`, снимок 2026-09-24; вызывающий, найденный позже, — тот же пункт): `stream_fal_asset` (`asset_proxy.py`) — объединение, соответствует; `public_asset_url` (`signed_url.py`) — объединение, соответствует; фильтр ассетов колбэка (`service.py`) — объединение, соответствует; `AssetStore` (`asset_store.py`, [ADR-109](ADR-109-media-asset-local-storage-30d.md)) — объединение, соответствует; `download_asset` — fal-only, **нарушает → п.2**; `upload`, `rehost_reference_image` — не читатели результата (п.3).
5. **Уточнение факта в [ADR-108 §7](ADR-108-media-generation-via-proxy.md) п.(3) и заголовке** — перечень «через него идут `upload`, `rehost_reference_image`, `download_asset`» верен для кода на 2026-09-23; с реализацией этого ADR `download_asset` из него выходит.

## Альтернативы

- **Оставить fal-only и перехостить результат** — отклонено: лишний круг в хранилище fal, которого на инстансе на прокси может не быть.
- **Читать результат из своей копии [ADR-109](ADR-109-media-asset-local-storage-30d.md)** — не отклонено как оптимизация, но не нормируется: копия пишется фоновым циклом и к моменту completion hook может отсутствовать; allowlist нужен в любом случае.

## Тесты

- Подготовка аватара с ассетом на хосте из `MEDIA_RESULT_HOST_SUFFIXES` → завершается, аватар подготовлен (сквозной путь через completion hook, не прямой вызов клиента).
- Хост вне объединения → `untrusted_asset_url`, исходящего запроса нет.
- `http://` на разрешённом хосте → отказ.
- `upload` со слотом на relay-хосте → по-прежнему `untrusted_upload_url` (контраст п.3).
- Diff-стойкость: возврат `download_asset` на fal-only роняет первый кейс.
- Зона: код — `backend`, тесты — `qa`.
