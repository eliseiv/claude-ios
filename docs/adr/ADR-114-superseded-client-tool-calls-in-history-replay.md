# ADR-114 — Вызов инструмента, оставшийся без результата к новому сообщению пользователя, закрывается при сборке истории

- **Статус:** Accepted. **Состояние реализации, поэлементно, снято 2026-09-25:** (1) **код** — не измеряется этим проходом: реализацию пишет `backend` параллельно, дерево `src/` движется; (2) **слит в `origin/main`** — нет: `git log --oneline origin/main -i --grep='ADR-114' | wc -l` → `0`; (3) **выкачен** — нет (следует из (2)); (4) **автотесты** — не измеряется этим проходом (кейсы — [09-testing.md §Брошенный вызов](../modules/chat-orchestrator/09-testing.md#брошенный-клиентский-вызов-и-новое-сообщение-adr-114)); (5) **ревью** — не измеряется.
- **Дата:** 2026-09-25
- **Связано:** [ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md) (барьер хода — **не меняется**; формулировка A2 «обрезанные `tool_use` исключаются из continuation-реплея» **уточняется** §5), [ADR-008](ADR-008-provider-tool-use-id.md) (`provider_tool_use_id` — ключ пары вызов↔результат), [ADR-033](ADR-033-llm-provider-abstraction.md) (провайдер-нейтральная история), [ADR-040 §4б](ADR-040-edit-message-and-regenerate.md) (редактирование уже сбрасывает зависший вызов усечением — не меняется), [ADR-102](ADR-102-mapkit-client-tools.md) (клиентские `maps.*`), [TD-032](../100-known-tech-debt.md) (v2/OpenAI — полный реплей), [TD-067](../100-known-tech-debt.md) (остаточное окно гонки §4).
- **Характер изменения:** уточнение сборки провайдерского ввода и одного правила `/tool-result`. Миграций нет, записи в БД при сборке истории нет, новых кодов ошибок нет. Наблюдаемое изменение публичного контракта — §3 и «Последствия».

## Контекст

**Прод-факты (сняты main chat 2026-09-25 на инстансе `backrewio`, переданы в задании):** OpenAI ответил `400 No tool output found for function call call_…` на `POST /v1/responses`, наружу — `502` на `POST /v1/chat/v2/run`. В `chat_steps` сессии: seq 264 `user`; seq 265 `assistant` с блоком `tool_use` (`maps_geocode`, клиентский инструмент); шага с ролью `tool` нет; seq 266 `user` (повтор вопроса); seq 267 `assistant` `turnFailed: UpstreamError`. За сутки на `backrewio` нет ни одного `POST /v1/chat/v2/tool-result` (измерено только на этом инстансе). По флоту за 24 ч — 12 таких ошибок на 2 инстансах (backrewio 1, elvarixa 11); 4 ответа `502` на 1820 запросов чата.

**Механизм — проверен по коду `HEAD` (`aa223a6`):**
- `_build_messages` (`git show HEAD:src/app/chat/orchestrator.py`, строки 3050–3078) реконструирует историю из ВСЕХ `chat_steps` сессии подряд и ничем не закрывает `tool_use` без парного шага `tool`.
- OpenAI Responses-клиент реплеит каждый `tool_use` как `function_call` (`src/app/chat/openai_responses_client.py`, `_responses_assistant_items_from_blocks` / `append_function_call`), а шаг `tool` — как `function_call_output` (`_responses_tool_output`, `:284-291`). Вызов без шага `tool` даёт `function_call` без `function_call_output` → `400`.
- Барьер хода ([ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md)) держит `pending` до прихода результата; таймаута и сборщика нет ([ADR-102](ADR-102-mapkit-client-tools.md), довод про висящий ход). Пользователь, не дождавшись, пишет новое сообщение → реплей несёт осиротевший вызов → каждый следующий ход сессии падает так же («отравленный» чат).
- Та же ФОРМА — «`tool_use`, который реплей отправляет провайдеру, без парного результата» — есть не только у брошенного клиентского вызова: обрезанный по `max_tokens` assistant-шаг персистится с полным `content` (`HEAD:src/app/chat/orchestrator.py:3635-3643`, «we do NOT call `_handle_tool_use`» — `tool_calls` не создаются, результатов не будет), а фильтра обрезанных блоков в `HEAD`-версии `_build_messages` нет. Та же форма у любого assistant-шага, прерванного до записи результатов (server-side вызов, ход, упавший между шагами).

## Решение

### §1. Определение «вытесненного» вызова — по свойству, а не по классу инструмента

Вызов **вытеснен**, если выполнены оба условия, вычисляемые только из `chat_steps` сессии:
- (а) это `tool_use`-блок assistant-шага, который реплей отправляет провайдеру (блок с непустыми строковыми `id` и `name` после общего распознавателя `to_domain_blocks`, [ADR-105 §A3](ADR-105-provider-failure-input-shape-and-media-deadline.md)) — **независимо** от класса инструмента (клиентский, server-side), от причины незакрытости (брошен пользователем, обрезан по `max_tokens`, ход прерван) и от бэкенда (legacy/v2);
- (б) после этого assistant-шага (по `seq`, [ADR-021](ADR-021-deterministic-step-order-and-block-normalization.md)) есть шаг `user`, а между assistant-шагом и ближайшим следующим `user`-шагом нет шага `tool` с тем же `providerToolUseId` ([ADR-008](ADR-008-provider-tool-use-id.md)).

Контраст (обе стороны предиката): вызов **текущего** хода — после его assistant-шага `user`-шага нет — вытесненным **не является** и не трогается: его закрывает только настоящий `/tool-result` через барьер [ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md). Вызов, чей настоящий результат лежит до следующего `user`-шага, реплеится как прежде.

**Почему не только клиентские.** Сужение до клиентских оставило бы тот же `400` на обрезанных по `max_tokens` и прерванных ходах: провайдеру безразлично, кто должен был дать результат, — у него есть вызов без пары.

### §2. Сервер закрывает вытесненный вызов синтетическим результатом-ошибкой при сборке истории

- При сборке нейтральной истории (`_build_messages` — единая точка для legacy `/v1/chat/*` и v2 `/v1/chat/v2/*`, для Anthropic и OpenAI, включая голосовой ход, исполняемый путём v2) для **каждого** вытесненного вызова вставляется нейтральное сообщение `role=tool` с `provider_tool_use_id` этого вызова и `error = {"code": "tool_result_missing", "message": "Результат инструмента не получен."}`. Место — сразу после assistant-шага и настоящих результатов того же хода, перед следующим не-`tool` шагом.
- Синтетическое сообщение идёт через тот же путь перевода, что настоящий результат (OpenAI — `function_call_output`; Anthropic — блок `tool_result` с `is_error`), поэтому провайдерский ввод валиден. Для Anthropic блоки `tool_result` обязаны стоять в начале ближайшего user-сообщения, перед его содержимым; если перевод дал бы два user-сообщения подряд, они сливаются в одно в этом порядке.
- **Шаг `tool` вытесненного вызова, лежащий ПОСЛЕ более позднего `user`-шага, из реплея ОТБРАСЫВАЕТСЯ** — одинаково для обоих провайдеров. Такой вызов уже закрыт синтетическим результатом; реплей настоящего дал бы второй `function_call_output` на тот же `call_id` (OpenAI) или `tool_result` не сразу после своего `tool_use` (Anthropic) — снова `400`. Перестановка отклонена: она переписывает порядок, который видел пользователь, и для Anthropic разрывает пару «ход ассистента → его результаты» с промежуточным user-сообщением. Такой шаг возникает только в окне гонки §4 либо был записан до §3.
- **В БД ничего не пишется:** ни шага `tool`, ни смены `tool_calls.status` (у клиентских остаётся `pending`), ни аудита, ни биллинга. Закрытие — свойство реплея, поэтому идемпотентно (каждая сборка даёт тот же ввод) и чинит уже «отравленные» чаты без миграции и бэкофилла.
- **Промежуточный assistant-шаг** между вызовом и следующим `user`-шагом (напр. seq 267 `turnFailed` из прод-фактов при повторных сообщениях): синтетический результат встаёт перед ним — сразу после хода с вызовом (`src/app/chat/orchestrator.py`, `_neutral_history_from_steps`: закрытие выполняется на границе и `user`-, и `assistant`-шага).
- **Слияние user-сообщений у Anthropic касается и прежнего пути** (`src/app/chat/anthropic_client.py`, `_build_provider_messages`, `append_user`): несколько подряд идущих шагов `tool` одного хода (параллельные результаты, [ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md)) теперь уходят одним user-сообщением с несколькими блоками `tool_result`, а не отдельными user-сообщениями.
- История для клиента (`GET /v1/chats/{id}`) не меняется: синтетический результат наружу не отдаётся, в `serverTools[]`/`toolCalls[]` не попадает.

**Почему синтетический результат, а не исключение блока.** Исключение `tool_use` оставляет пустое assistant-сообщение, если шаг состоял только из вызова (как seq 265), и стирает из контекста модели факт, что она просила инструмент. Синтетическая ошибка сохраняет пару вызов↔результат одинаково для обоих провайдеров и даёт модели верный сигнал «результата нет». Запись статуса `errored` в БД при новом `run` отклонена: не чинит уже отравленные чаты без бэкофилла и открывает continuation вытесненного хода запоздалым результатом (§3).

### §3. Запоздалый `/tool-result` на вытесненный ход

Проверено по коду `HEAD`: `tool_result` (`HEAD:src/app/chat/orchestrator.py`, метод начинается на строке 2381) пропускает только вызовы в статусе `completed`/`errored`; вызов в `pending` принимает, пишет шаг `tool` и при закрытом барьере выполняет continuation. Для вытесненного хода это шаг `tool` после более позднего `user`-шага и continuation хода, который пользователь оставил.

Норма (`POST /v1/chat/tool-result` и `POST /v1/chat/v2/tool-result` одинаково):
- **Проверка 1 — до записи.** Если ход батча **ещё не закрыт барьером** (есть client-side вызов хода со статусом не `completed`/`errored`) и после его assistant-шага есть `user`-шаг → `409`, `error.code = "conflict"` (существующий `ConflictError`, `src/app/errors.py`); ничего не пишется, провайдер не вызывается, биллинга нет.
- **Проверка 2 — после записи результатов, перед continuation.** Барьер закрылся этим запросом → перед сборкой истории continuation свежим чтением шагов проверяется предикат **хода**, а не §1: «после assistant-шага этого хода есть хотя бы один `user`-шаг» — **независимо от того, где лежат шаги `tool` хода** (записанный этим же запросом шаг `tool` стоит ДО вставленного позже `user`-шага, и по §1 (б) вызов вытесненным не был бы — поэтому §1 здесь не применяется). Предикат выполнен → continuation НЕ выполняется, ответ `409 conflict`; запись этого запроса (шаг `tool`, переходы `tool_calls`) **откатывается вместе с ним**: HTTP-путь — `session_scope` делает `rollback` при исключении (`src/app/db.py`, `session_scope`), голосовой путь выходит из `session_scope` без коммита (`src/app/api_gateway/routers/chat_voice.py`, `_run_leg`), а между записью и проверкой 2 коммита нет. Вызовы остаются `pending`, повтор того же `/tool-result` снова получает `409` уже на проверке 1. На следующем ходе вызов закрывается синтетическим результатом (§2).
- **Ретрай уже `completed` вызова вытесненного хода, у которого другой вызов ещё `pending`** (ход открыт) → тоже `409`: идемпотентный ответ «оставшиеся `toolCalls[]`» просил бы клиента исполнить вызов хода, который пользователь бросил. Это осознанное следствие проверки 1.
- Ход, барьер которого уже закрыт (все client-side вызовы `completed`/`errored`) до прихода запроса, идёт по существующей идемпотентности [ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md) без изменений, даже если после него есть новые `user`-шаги.

### §4. Гонка `/tool-result` ∥ `/run` — принятый исход

Блокировки сессии в чат-пути нет (`grep -n -i "advisory\|for_update\|with_for_update\|FOR UPDATE\|asyncio.Lock" src/app/chat/orchestrator.py src/app/chat/repository.py` → пусто, 2026-09-25). Норма не вводит её: сериализация `/run` по сессии держала бы транзакцию на всё время вызова провайдера.
- **Моменты считаются по ВИДИМОСТИ, а не по вставке.** `/run` вставляет `user`-шаг (`add_step`, `src/app/chat/orchestrator.py`, путь `run`) и коммитит его позже — первым `commit()` перед сетевым вызовом провайдера («commit the persisted steps + audit BEFORE the network call»); до коммита шаг другой транзакции не виден. `seq` при этом назначается в момент вставки ([ADR-021](ADR-021-deterministic-step-order-and-block-normalization.md)).
- **`user`-шаг `/run` ЗАКОММИЧЕН до проверки 2** → проверка 2 (предикат хода) его видит, continuation нет, `409`, запись запроса откатывается (проверка 2 выше); на следующем ходе вызов закрыт синтетически. Провайдер не получает невалидный ввод ни в одном из запросов.
- **Остаточное окно — `user`-шаг `/run` ещё НЕ закоммичен к проверке 2** (вставлен до неё или после — неважно) → проверка 2 его не видит, оба запроса генерируют ответ; возможны два assistant-ответа и два списания (разные `messageStepId`). Если `user`-шаг был вставлен раньше шага `tool` этого запроса, его `seq` меньше, и реплей continuation отбросит собственный настоящий шаг `tool` (§2), закрыв вызов синтетически. Провайдерский ввод в обоих запросах валиден. Исход принят как редкий: он требует, чтобы клиент отправил результат инструмента и новое сообщение одновременно, а клиент обязан не слать результат после нового сообщения («Последствия»). Закрытие окна — [TD-067](../100-known-tech-debt.md).

### §5. Отношение к ADR-025 A2 (обрезка по `max_tokens`)

[ADR-025 A2](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md) гласит «обрезанные `tool_use`-блоки исключаются из continuation-реплея». Уточнение ФАКТА, решение A2 не меняется: re-entry по обрезанному ходу по-прежнему не предусмотрен (`tool_calls` не создаются, `HEAD:src/app/chat/orchestrator.py:3635-3643`), но фильтра обрезанных блоков в реплее СЛЕДУЮЩИХ ходов в коде `HEAD` нет — обрезанный шаг реплеится целиком. Норма реплея для них — §1–§2 настоящего ADR: на следующем `user`-шаге обрезанные вызовы закрываются синтетическим результатом, как любые вытесненные. Отдельный фильтр не вводится — одна точка закрытия для всех причин незакрытости.

### §6. Что не меняется

Барьер хода, биллинг ([ADR-006](ADR-006-credit-billing-and-subscription-grant.md)), идемпотентность закрытого хода, усечение при редактировании ([ADR-040 §4б](ADR-040-edit-message-and-regenerate.md)), гейтинг и guard `maps.*` ([ADR-102](ADR-102-mapkit-client-tools.md)), схема `ChatResponse`.

## Последствия

- `POST /v1/chat/run` / `POST /v1/chat/v2/run` после брошенного, обрезанного или прерванного вызова отвечают по обычному контракту вместо `502`; «отравленные» сессии оживают на следующем сообщении.
- **Наблюдаемое изменение публичного контракта:** `/tool-result` на вытесненный незакрытый ход получает `409 conflict` вместо прежнего приёма ([API-REFERENCE](../API-REFERENCE.md#post-v1chattool-result)). **Поведение клиента:** отправив новое сообщение, результаты вызовов прежнего хода НЕ слать; получив `409 conflict` на `/tool-result`, результат ОТБРОСИТЬ, запрос НЕ ретраить, пользователю ничего не показывать — ход уже продолжен новым сообщением.
- `tool_calls` вытесненных клиентских вызовов остаются `pending` навсегда — осознанно: статус читает только барьер, а барьер вытесненного хода закрыт §3.

## Альтернативы

- **Исключать осиротевший блок из реплея** — отклонено (§2: пустое assistant-сообщение, потеря контекста).
- **Помечать вызовы `errored` в БД при новом `run`** — отклонено (§2).
- **Отвергать новое сообщение, пока ход открыт** (`409 turn_in_progress`) — отклонено: чат заблокирован, пока приложение не пришлёт результат, которого оно может не прислать никогда (прод-факт, снятый main chat на `backrewio`: 0 `POST /v1/chat/v2/tool-result` за сутки на этом инстансе; по флоту не измерялось).
- **Блокировка сессии на `/run` и `/tool-result`** — отклонено для этой правки (§4), вынесено в TD-067.
- **Таймаут/сборщик протухших вызовов** — отклонено: закрытие по событию «новое сообщение» покрывает наблюдаемый отказ без фонового процесса.
