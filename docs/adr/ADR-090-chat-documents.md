# ADR-090: Документы чата — создание, чтение и обновление моделью, отдача клиенту

- **Статус:** Accepted
- **Дата:** 2026-08-24
- **Контекст запроса:** запрос iOS-разработчика: «добавить возможность создания файлов на бэке и отдаче их клиенту, ИИ должен уметь работать с документами, читать их и обновлять».

## Контекст

Сегодня в сервисе есть четыре разных «файла», и ни один не решает задачу:

| Что | Кто пишет | Кто читает | Почему не подходит |
|---|---|---|---|
| `files.*` (`read`/`write`/`list`/`mkdir`) | модель | **устройство пользователя** | исполняется клиентом локально (как `calendar`/`reminders`), бэкенда не касается |
| `site.*` (`write_file`/`read`/…) | модель | preview-страница | website-builder: результат — HTML-сайт, а не документ |
| Вложения (`attachments[]`, [ADR-020](ADR-020-inline-base64-attachments-mvp.md)) | пользователь | модель, в пределах хода | не персистятся, изменению не подлежат |
| Файлы-знания workspace ([ADR-036](ADR-036-workspaces-implementation.md)) | пользователь | модель, как контекст | наружу отдаются только метаданные; модель их не меняет |

Отсутствует ровно то, что просили: **персистентный текстовый документ, который модель создаёт или правит, а клиент скачивает.**

Отдельно проверено и **работы не требует**: код в ответе уже приходит с markdown-ограждением и языковым тегом (` ```python … ``` ` в `assistantMessage`, проверено live на livonexa 2026-08-24). Моношрифт — вопрос рендеринга на клиенте.

## Решение

### 1. Формат — только текстовые

`text/markdown`, `text/plain`, `text/csv`, `application/json`. Хранение — колонка `TEXT`, не `BYTEA`.

Почему не PDF/docx: модель порождает текст напрямую, поэтому текстовый документ — это ровно то, что она умеет и создавать, и **править**. Бинарный формат потребовал бы слоя конвертации в обе стороны, а «обновить PDF» означало бы перегенерацию из исходного markdown — то есть тот же текстовый документ, просто спрятанный. Рендер в PDF/docx — надстройка над этим решением, а не альтернатива ему ([Q-090-1](../99-open-questions.md)).

### 2. Скоуп — чат

Документ принадлежит паре (владелец, сессия) и удаляется вместе с сессией (`ON DELETE CASCADE`). Модель адресует документ по `id` в пределах текущей сессии; документ чужой сессии для неё не существует.

**Контраст с workspace-файлами (обе стороны помечены):** файлы-знания живут в проекте и переживают чаты; документы живут в чате и умирают с ним. Правило «файл переживает сессию» на документы **не переносится**, правило «модель может изменить» на файлы-знания **не переносится**.

### 3. Инструменты модели — серверные, project-independent

Четыре инструмента в `GLOBAL_SERVER_SIDE_TOOLS` (исполняет бэкенд внутри tool-loop, без round-trip к iOS — как `time.now`, [ADR-026](ADR-026-global-server-side-tools.md)):

| Инструмент | Аргументы | Результат |
|---|---|---|
| `document.create` | `filename`, `mediaType`, `content` | `{documentId, filename, size, version}` |
| `document.list` | — | `{documents: [{documentId, filename, mediaType, size, version}]}` |
| `document.read` | `documentId` | `{documentId, filename, mediaType, content, version}` |
| `document.update` | `documentId`, `content` | `{documentId, version, size}` |

**`update` заменяет содержимое целиком, а не патчем.** Патч (диапазон строк, replace-подстрока) требует от модели точного знания текущего текста и молча портит документ при расхождении. Полная замена делает контракт проверяемым: модель обязана сначала `read`, затем `update` — и мы всегда знаем, из чего получен результат. `version` инкрементируется на каждом `update` и отдаётся клиенту, чтобы он видел, что документ изменился.

**Семейство `document` НЕ входит в `DISABLEABLE_TOOL_FAMILIES`** ([ADR-081](ADR-081-disabled-tool-families.md)): оно не дублирует локальные возможности устройства и не зависит от внешнего провайдера, поэтому per-instance выключателя не требует.

### 4. REST-поверхность

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/v1/chats/{sessionId}/documents` | загрузка пользователем (base64, как workspace-файлы) |
| `GET` | `/v1/chats/{sessionId}/documents` | список документов сессии |
| `GET` | `/v1/chats/{sessionId}/documents/{documentId}` | метаданные + содержимое |
| `GET` | `/v1/chats/{sessionId}/documents/{documentId}/download` | файл с `Content-Disposition: attachment` |
| `DELETE` | `/v1/chats/{sessionId}/documents/{documentId}` | удалить |

**Скачивание — по JWT, а не по подписанному URL.** Подписанные URL введены для медиа ([ADR-085](ADR-085-media-asset-download-proxy.md)) потому, что ассет тянет webview без заголовков авторизации. Документ забирает само приложение, у которого токен уже есть, — подпись добавила бы отдельный секрет и TTL без единой выгоды. Правило «ассет отдаётся по подписи» на документы **не переносится**.

Изоляция владельца на каждом пути: чужая сессия и чужой документ → `404` (не `403` — существование чужого объекта не раскрывается).

### 5. Источник — и созданные моделью, и загруженные пользователем

Это один и тот же объект: `POST` создаёт его руками пользователя, `document.create` — руками модели. Дальше оба одинаково читаются, правятся и скачиваются. Отдельного «класса загруженных» нет — иначе половина инструментов работала бы с одним классом, половина с другим.

Признак `createdBy` (`user` | `assistant`) сохраняется как факт происхождения и отдаётся клиенту для UI, но **на права не влияет**.

### 6. Осведомлённость модели

Когда в сессии есть хотя бы один документ, к системному промту добавляется одна строка со списком `documentId` + `filename` (усечение — `DOCUMENT_CONTEXT_MAX_CHARS`). Без неё модель не знает, что документы существуют, и не догадается вызвать `document.list`.

Содержимое в промт **не** попадает: оно может быть большим и меняется — для чтения есть `document.read`.

### 7. Лимиты

| Ключ | Дефолт | Смысл |
|---|---|---|
| `DOCUMENT_MAX_BYTES` | `262144` (256 KiB) | размер одного документа |
| `DOCUMENT_MAX_COUNT` | `20` | документов на сессию |
| `DOCUMENT_TOTAL_BYTES` | `1048576` (1 MiB) | суммарно на сессию |
| `DOCUMENT_CONTEXT_MAX_CHARS` | `2000` | срез списка документов в системном промте |

Превышение → `422` с собственным `code` (`document_too_large`, `too_many_documents`, `documents_total_too_large`, `unsupported_media_type`) — по правилу разведения кодов из [ADR-089](ADR-089-attachment-limits-and-error-taxonomy.md), а не общим `validation_error`.

### 8. Модерация — не применяется

По предикату [ADR-086 §2](ADR-086-ugc-moderation.md) документ даёт **нет** по обоим критериям: он не отображается приложением как медиа (это текст) и не становится промптом или референсом платной генерации. Тот же вердикт и по той же причине, что у файлов-знаний workspace ([Q-086-3](../99-open-questions.md)).

Предикат применён симметрично: вложения чата модерируются потому, что рендерятся как медиа **и** авто-загружаются в fal; документы не делают ни того, ни другого. Если документ когда-нибудь начнёт уходить в генерацию — вердикт обязан пересматриваться вместе с этим изменением.

### 9. Персистентность

Таблица `chat_documents`: `id`, `user_id`, `session_id` (FK `chat_sessions` `ON DELETE CASCADE`), `filename`, `media_type`, `content` (TEXT), `size_bytes`, `version`, `created_by`, `created_at`, `updated_at`. Индекс по `(session_id, created_at)`.

Миграция аддитивная, бэкфилла нет.

## Альтернативы

1. **Расширить `site.*`.** Отвергнута: `site_files` — это сайт, отдаваемый preview-роутом с sandbox-заголовками ([ADR-010](ADR-010-preview-sandbox.md)). Документ — не веб-страница, и смешение сломало бы семантику обоих.
2. **Расширить файлы-знания workspace.** Отвергнута: они привязаны к проекту и переживают чаты; владелец выбрал привязку к чату. Кроме того, они read-only для модели по построению.
3. **Хранить в object storage.** Отвергнута: текст ≤256 KiB, а инфраструктуры object storage в проекте нет ([TD-009](../100-known-tech-debt.md) открыт с MVP). Колонка `TEXT` — тот же выбор, что уже сделан для `site_files` и `workspace_files`.
4. **Патч-семантика `update`.** Отвергнута: см. §3 — молча портит документ при расхождении модели с фактическим текстом.
5. **Подписанные URL для скачивания.** Отвергнута: см. §4 — нужны там, где нет заголовка авторизации; у приложения он есть.
6. **Бинарные форматы сразу (docx/pdf).** Отвергнута: см. §1 — конвертация в обе стороны и потеря форматирования при редактировании; вынесено в [Q-090-1](../99-open-questions.md).

## Последствия

- Модель получает возможность вести документ по ходу диалога: составить, показать, доработать по замечанию, отдать на скачивание.
- Клиенту нужен экран списка документов чата и кнопка скачивания; поле `version` позволяет показать, что документ изменился после правки.
- Размер сессии в БД растёт на объём документов (потолок — `DOCUMENT_TOTAL_BYTES` на сессию).
- Удаление чата удаляет документы: пользователь, которому документ дорог, обязан его скачать. Это следствие выбранного скоупа, и клиент должен предупреждать при удалении чата с документами.
- Открытый вопрос: [Q-090-1](../99-open-questions.md) (рендер в PDF/docx на выходе).
