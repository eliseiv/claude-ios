# ADR-086 — Модерация пользовательского контента (UGC) на входе и на выходе

- **Статус:** Accepted
- **Дата:** 2026-08-24
- **Тип:** feature-ADR; **расширяет** поток сабмита [ADR-060](ADR-060-media-generation-fal.md) (тело ADR-060 не переписано — immutability) и контракт вложений [ADR-020](ADR-020-inline-base64-attachments-mvp.md)
- **Связано:** [ADR-004](ADR-004-blocked-http-200.md) (blocked=200 — здесь **не** применяется, см. §2), [ADR-005](ADR-005-idempotency-ledger.md) (ключи возврата), [ADR-063](ADR-063-media-feed-edit-chains-and-job-deletion.md) (цепочки правок), [ADR-068](ADR-068-media-generate-chat-tools.md)/[ADR-070](ADR-070-media-choices-wizard.md) (сабмит из чата), [ADR-085](ADR-085-media-asset-download-proxy.md) (download-роут ассетов)
- **Реализуется в:** [modules/media-generation](../modules/media-generation/README.md), [modules/chat-orchestrator](../modules/chat-orchestrator/README.md), [modules/api-gateway](../modules/api-gateway/README.md)

## Контекст

Багрепорт QA (BUG-006, Critical, блокер App Store 1.1.4 / 1.2). `POST /v1/media/videos` и `/v1/media/images` принимают любой промпт и любое референсное фото, создают **платную** задачу и отдают результат. QA получил видео с наготой и видео с графическими травмами; оба открываются в чате и в History без блюра и без предупреждения. Ни в OpenAPI, ни в ответе задачи нет **ни одного** поля модерации — приложению нечем отличить безопасный результат от небезопасного, поэтому закрыть требование на клиенте физически невозможно.

Три отдельных дефекта:

1. вход не проверяется **до** списания кредитов — пользователь платит за заведомо отклоняемый запуск, а провайдер может и не отклонить;
2. выход не проверяется — сгенерированный небезопасный ассет попадает в чат и в ленту;
3. вердикта нет в контракте — клиент не может ни заглушить, ни заблюрить.

## Решение

### 1. Один провайдер модерации на все точки — OpenAI `omni-moderation-latest`

Принимает **и текст, и изображения** одним вызовом, бесплатен, уже покрыт зависимостью `openai` в стеке. Отдельный клиент модерации, ключ — `MODERATION_API_KEY` с фолбэком на `OPENAI_API_KEY`; хост фиксирован сервером (`MODERATION_BASE_URL`, дефолт `https://api.openai.com/v1`) — исходящий вызов никогда не строится из тела запроса (SSRF-guard, образец `FAL_QUEUE_BASE`).

**Инстансы `LLM_PROVIDER=anthropic` обслуживаются тем же провайдером модерации.** Модерация **не связана** с `LLM_PROVIDER`: на anthropic-инстансе `OPENAI_API_KEY` по clone-контракту не задан, поэтому там `MODERATION_API_KEY` — **обязательный** операторский ключ. Это осознанная плата за один провайдер на весь флот вместо двух разных политик.

### 2. Периметр: предикат отнесения, вычисленный для КАЖДОЙ поверхности

Правило формулируется по инварианту, а не по списку эндпоинтов, на которых QA споткнулся.

> **Инвариант М-1.** Путь обязан проходить модерацию, если выполняется хотя бы одно из:
> **(а)** пользовательский байт-контент этого пути **рендерится приложением как изображение/видео** (вложение чата в ленте сообщений; ассет генерации в чате и в History);
> **(б)** этот путь — **промпт или референс платной генерации** медиа.
>
> **Симметричный критерий против переоценки.** Путь **НЕ** модерируется, если его контент никогда не рендерится как медиа **И** не оплачивается генерацией: метаданные, имена файлов, tool-args, а также контент, который наружу отдаётся только метаданными.

Sweep по **всем** поверхностям, принимающим пользовательские байты или промпт (не только по тем, что названы в багрепорте):

| Поверхность | (а) рендерится как медиа? | (б) промпт/референс платной генерации? | Вердикт |
|---|---|---|---|
| `POST /v1/chat/run` — `attachments[]` | да (лента сообщений) | нет | **модерируется** |
| `POST /v1/chat/v2/run` — `attachments[]` | да | нет | **модерируется** |
| `POST /v1/chat/v2/run/stream` — `attachments[]` | да | нет | **модерируется** |
| `POST /v1/media/uploads` | да (референс виден в `inputImageUrls` ленты) | да (вход следующей генерации) | **модерируется** |
| `POST /v1/media/images` / `/videos` (`prompt`, `imageUrls`/`imageUrl`) | да (результат) | да | **модерируется** |
| chat-tools `media.generate_image`/`media.generate_video`, `mediaSelection` | да | да | **модерируется** тем же чеком в `MediaGenerationService.submit` |
| `POST /v1/workspaces/{id}/files` | нет — наружу отдаются только `filename`/`mediaType`/`size`, байты не возвращаются | нет | не модерируется → [Q-086-3](../99-open-questions.md) |
| `POST /v1/admin/media/templates` (обложка) | да, но контент **операторский**, не UGC | нет | не модерируется (не пользовательский контент) |
| `site_files` / `GET /v1/preview/*` | нет (HTML/JS, не медиа-UGC; sandbox-CSP [ADR-010](ADR-010-backend-hosted-preview.md)) | нет | не модерируется |
| `POST /v1/chat/*` **без** вложений (только текст) | нет (текст, а не медиа) | нет | **не модерируется** — см. §3 |

### 3. Что именно проверяется в чате

**Ход чата модерируется тогда и только тогда, когда в запросе есть непустой `attachments[]`.** Ход без вложений не порождает медиа и не оплачивает генерацию → критерий (б) против переоценки: модерация каждого текстового сообщения добавила бы сетевой round-trip на **каждый** ход ради контента, который приложение не показывает как медиа.

На модерируемом ходе в один вызов уходит:

- **текст** — `message` запроса (сырой, **до** склейки с context-блоком [ADR-037](ADR-037-chatrunrequest-context-allowlist-injection.md)) плюс декодированное содержимое вложений класса `text`, склейка через `\n`, срез до `MODERATION_TEXT_MAX_CHARS`;
- **изображения** — **все** вложения класса `image` как data-URI. Отдельного лимита «сколько картинок проверяем» **нет и не вводится**: любой такой лимит оставил бы часть контента непроверенной. Число уже ограничено `ATTACHMENT_MAX_COUNT`.
- **`document` (PDF) в модерацию не уходит** — omni-moderation не принимает PDF, а извлечение картинок из PDF в этот ADR не входит: [Q-086-1](../99-open-questions.md).

**Точка вызова:** после `prepare_attachments` (нужен валидированный вход; кривой файл дешевле отбить раньше) и **ДО** `repo.add_step()`. Нарушение → `422`, ни одного шага в БД, ни одного обращения к LLM, кредит не списан, только что созданная пустая сессия откатывается вместе с транзакцией запроса (тот же механизм, что у `404 message_not_found`, [ADR-040](ADR-040-edit-message-and-regenerate.md)).

### 4. Порядок в media: пре-модерация **до** списания, пост-модерация **после** — обе стороны помечены

Нормативный порядок `MediaGenerationService.submit` (расширяет поток [ADR-060](ADR-060-media-generation-fal.md)):

```
1. _resolve_model
2. sourceJobId → ассеты родителя (если задан)
3. валидация значений против варианта
4. МОДЕРАЦИЯ ВХОДА: prompt + КЛИЕНТСКИЕ imageUrls/imageUrl   ← ОБЯЗАНА стоять ДО шага 7
5. rehost референса (video)
6. resolve_values / build_fal_input / цена
7. wallet.consume(...)                                        ← первая точка, где пользователь платит
8. fal.submit + INSERT media_jobs (moderation = вердикт входа)
```

- **Шаг 4 обязан быть до шага 7.** Иначе повторяется ровно тот дефект, из-за которого написан багрепорт: за отклонённый контент уже списаны кредиты.
- **Контраст (обе стороны помечены):** пост-модерация (§5) идёт **после** списания по построению — вердикт о выходе физически невозможен раньше, — и поэтому **обязана вернуть кредиты**. Правило «проверяем до списания» на неё **не переносится**, правило «возвращаем кредиты» на пре-модерацию **не переносится** (там списания ещё не было).
- Изображения, подставленные из `sourceJobId`, — **наши** ассеты, уже прошедшие пост-модерацию, и повторно не проверяются. Проверяются только URL, пришедшие от клиента.

### 5. Пост-модерация результата и терминальный статус

В `_advance` на `FAL_COMPLETED`, **после** нормализации результата и **до** `mark_completed`:

- **`kind = image`** — модерируются URL всех ассетов результата.
- **`kind = video`** — пост-модерация **не выполняется**: провайдер модерации не принимает видео. У видео-задачи `moderation` отражает только вход (`stage: "input"`). Кадровая пост-модерация — [Q-086-2](../99-open-questions.md). Отклонение промпта самим fal приходит, как и раньше, обычным `failed` с текстом провайдера.

**Терминальный статус блокировки — существующий `failed`, новое значение статуса НЕ вводится.** `MediaJobResponse.status` — закрытый `Literal`; новое значение сломало бы декодеры уже выпущенных iOS-сборок. Различает исходы новое поле `moderation`, которое старые клиенты просто игнорируют.

| Вердикт выхода | `status` | `assets` | `moderation.status` | `error` | `creditsRefunded` |
|---|---|---|---|---|---|
| `blocked` | `failed` | **пуст** | `blocked` | человекочитаемый текст отказа | `true` |
| `flagged` | `completed` | ассеты как обычно | `flagged` | `null` | `false` |
| `passed` | `completed` | ассеты как обычно | `passed` | `null` | `false` |

- **`error` остаётся человекочитаемым.** Поле показывается пользователю выпущенными сборками как есть, поэтому машинный код в него не кладётся (`08-api-documentation.md` R9.4: внутренние идентификаторы не попадают в user-facing текст). Машинный признак блокировки несёт `moderation.status = "blocked"` — именно для этого поле и вводится.
- **`ChatResponse.mediaJobs` (`MediaJobRefSchema`) поля `moderation` НЕ получает.** В момент ответа чата задача только что создана (`queued`), вердикт по ней — исключительно входной, а терминальный вердикт появляется позже. Клиент берёт его опросом `GET /v1/media/jobs/{id}` / `GET /v1/media/jobs`, где поле есть. Класть в чат-ответ заведомо непоказательный вердикт значило бы дать клиенту повод отрисовать по нему UI.
- При `blocked` ассеты **не сохраняются** в `media_jobs.result` (`{"assets": []}`). Иначе заблокированный файл остался бы достижим через signed-URL download-роут ([ADR-085](ADR-085-media-asset-download-proxy.md)) — блокировка была бы декоративной. Push «media ready» ([ADR-067](ADR-067-media-ready-push-and-reconciler.md)) при `blocked` **не отправляется**.
- Возврат идёт тем же путём и тем же ключом идемпотентности `media-refund:{jobId}`, что и возврат при провале у провайдера ([ADR-005](ADR-005-idempotency-ledger.md)): один `jobId` ⇒ не более одного возврата, независимо от причины. Новый namespace ключей не вводится.
- При `flagged` кредиты **не** возвращаются: контент выдан, клиент его показывает (под блюром) — предикат «выдан ⇒ оплачен».

### 6. Классификация вердикта — предикат, а не суждение

Провайдер возвращает `flagged` (bool) и `categories` (bool по каждой категории). Вердикт вычисляется из них **детерминированно**, без порогов и без ручной оценки:

```
если сработала хотя бы одна категория из BLOCK   → blocked
иначе если flagged = true                         → flagged
иначе                                             → passed
```

- **BLOCK** = `MODERATION_BLOCK_CATEGORIES` (CSV, дефолт `sexual,sexual/minors,violence/graphic,self-harm,self-harm/intent,self-harm/instructions`). **`sexual/minors` входит в BLOCK всегда**, даже если оператор удалил её из env, — это не настраиваемая политика.
- Остальные сработавшие категории (`violence`, `hate`, `harassment`, `illicit`, …) дают `flagged`: контент выдаётся с пометкой, клиент блюрит с тапом «Показать».
- **Агрегация по частям запроса:** вердикт запроса = худший вердикт по его частям; `categories` вердикта = объединение сработавших категорий частей. Одна часть в `blocked` блокирует весь запрос.
- **Асимметрия вход/выход (намеренная, обе стороны помечены):** на **входе** блокирует только BLOCK-набор — `flagged` вход проходит дальше, иначе поток ложных отказов на безобидных формулировках. На **выходе** `flagged` тоже проходит, но помечается — там есть кому показать пометку.

### 7. Поведение при недоступности провайдера модерации — fail-closed

**Выбор: fail-closed.** Сбой модерации (таймаут, сеть, 5xx, некорректный ответ) → операция **отклоняется**: `503 moderation_unavailable`, кредиты не списаны, задача не создана, шаг чата не записан.

Обоснование: цена ошибки несимметрична. Fail-open означает, что во время любой недоступности провайдера через сервис проходит непроверенный UGC — то есть ровно то состояние, из-за которого приложение снимают с ревью; и узнать об этом можно только по факту жалобы. Fail-closed означает временную недоступность **двух** поверхностей (генерация медиа и чат с вложением) при живом текстовом чате, с явным retryable-кодом. Прецедент того же выбора в проекте — fail-closed дефолт `CHAT_ADVERTISED_GENERATION_MODES` ([ADR-065](ADR-065-study-learn-advertisement-gate-and-history-spoiler-strip.md)).

**Аварийный переключатель оператора:** `MODERATION_FAIL_OPEN` (дефолт `false`). При `true` сбой модерации не блокирует операцию, вердикт записывается как `unchecked`, пишется WARNING и инкрементируется `moderation_errors_total{reason="fail_open"}`. Это **осознанное снижение соответствия требованиям сторов** на время длительной аварии провайдера, а не штатный режим; включение и выключение — операторское решение, зафиксированное в `.env` инстанса.

`MODERATION_ENABLED=false` (per-instance выключение фичи целиком) — отдельная величина: тогда вызов модерации не делается вовсе, вердикт `unchecked`, 503 не возникает.

### 8. Контракт поля `moderation` (одинаковый в одиночной задаче и в ленте)

Поле добавляется в `MediaJobResponse`, а `MediaJobsListResponse.jobs[]` — это тот же тип, поэтому лента получает его автоматически (иначе History показал бы заблокированное).

```json
"moderation": {
  "status": "passed",
  "stage": "output",
  "categories": [],
  "checkedAt": "2026-08-24T11:20:48.117Z"
}
```

| Поле | Значение |
|---|---|
| `status` | `passed` \| `flagged` \| `blocked` \| `unchecked` |
| `stage` | стадия, на которой вынесен вердикт: `input` \| `output`; `null` при `unchecked` |
| `categories` | сработавшие категории провайдера; пуст при `passed`/`unchecked` |
| `checkedAt` | момент последней проверки; `null` при `unchecked` |

- **`unchecked` вместо «тихого `passed`»**: задачи, созданные до этого ADR (`media_jobs.moderation IS NULL`), и инстансы с `MODERATION_ENABLED=false` не проверялись — сообщать «passed» о непроверенном контенте значило бы врать клиенту. Клиентское правило: `unchecked` рендерится как `passed` (легаси-совместимость), но отличимо в диагностике.
- Поле **присутствует всегда** и не бывает `null` — клиенту не нужна ветка «поля нет».
- **Категории отдаются только в поле задачи, но НЕ в теле ошибки пре-модерации** (§9). Это намеренный контраст: вердикт о *показанном* контенте нужен клиенту для UI, а перечень сработавших категорий на *отклонённом входе* — подсказка, как переформулировать запрос до прохождения фильтра.

### 9. Taxonomy ошибок

| Код | HTTP | Когда | Кредиты |
|---|---|---|---|
| `content_policy_violation` | `422` | пре-модерация отклонила промпт / референс / вложение / текст хода | не списаны |
| `moderation_unavailable` | `503` | провайдер модерации недоступен, `MODERATION_FAIL_OPEN=false` (retryable) | не списаны |
| `moderation_not_configured` | `503` | `MODERATION_ENABLED=true`, но ключ не резолвится (проблема оператора) | не списаны |

- `422`, а не `400`/`403`: тело схемно валидно, отвергнут **контент** — тот же уровень, что прочие content-level отказы вложений ([ADR-089](ADR-089-attachment-limits-and-error-taxonomy.md)). Код **отличается** от `validation_error` — это и было требованием багрепорта.
- **ADR-004 (blocked=200) здесь НЕ применяется.** `status=blocked` + `blockReason` — это бизнес-блокировка **доступа** (подписка/баланс/trial), она описывает состояние пользователя. Отказ модерации описывает **содержимое запроса** и относится к семье технических отказов ввода (`4xx`). Смешение сделало бы `blockReason` двузначным.
- **Отказ модерации на пути chat-tools ход НЕ роняет:** `media.generate_*` / `mediaSelection` возвращают tool-result error `{"code":"content_policy_violation"}`, `serverTools[].status=errored`, `summary="content_policy_violation"`, ход продолжается — модель может переформулировать промпт (образец `invalid_quiz`, [ADR-064](ADR-064-study-learn-quiz-generation-mode.md) §5). **Контраст:** на REST-пути `/v1/media/*` тот же отказ — жёсткий `422`, потому что там нет модели, которая могла бы переформулировать, а есть клиент, которому нужен машиночитаемый отказ.

### 10. Персистентность вердикта и наблюдаемость

- **Media:** колонка `media_jobs.moderation JSONB NULL` — expand-only миграция (номер — следующий свободный на момент реализации, single head сохраняется). Содержимое: `{status, stage, categories, checkedAt, provider, model}`. `NULL` = не проверялось.
- **Chat:** отклонённый ход не создаёт шагов, поэтому персистенции вердикта нет по построению; след — структурный лог и метрика.
- **Лог** `moderation_outcome` (один на вызов модерации), allowlist полей: `surface` (`chat`\|`media_submit`\|`media_result`\|`media_upload`), `stage`, `decision`, `categories`, `userId`, `jobId` (если есть), `provider`, `model`, `latencyMs`. **Запрещено:** текст промпта, `message`, base64/байты вложений, URL ассета целиком, ключ модерации.
- **Метрики** (producer → consumer названы явно): `moderation_decisions_total{surface,stage,decision}` и `moderation_errors_total{reason}` инкрементируются **в местах вызова** (`ChatOrchestrator.run`, `MediaGenerationService.submit`, `MediaGenerationService._advance`, `MediaGenerationService.upload_reference_image`); потребитель — экспозиция `GET /metrics` (Prometheus, `docker-compose.observability.yml`). Правил алертинга этот ADR не вводит (alert-стека в проекте нет) — рост `moderation_errors_total` смотрит оператор.

### 11. Конфигурация

| Ключ | Дефолт | Смысл |
|---|---|---|
| `MODERATION_ENABLED` | `true` | выключатель фичи per-instance; `false` → вердикт `unchecked`, вызовов нет |
| `MODERATION_API_KEY` | `""` → фолбэк `OPENAI_API_KEY` | **секрет**, под redaction. На anthropic-инстансах обязателен явно |
| `MODERATION_MODEL` | `omni-moderation-latest` | модель модерации |
| `MODERATION_BASE_URL` | `https://api.openai.com/v1` | фиксированный хост исходящего вызова (SSRF-guard) |
| `MODERATION_TIMEOUT_SECONDS` | `10` | connect+read одного вызова |
| `MODERATION_MAX_RETRIES` | `1` | ретраи SDK |
| `MODERATION_BLOCK_CATEGORIES` | `sexual,sexual/minors,violence/graphic,self-harm,self-harm/intent,self-harm/instructions` | BLOCK-набор; `sexual/minors` неудаляем |
| `MODERATION_TEXT_MAX_CHARS` | `4000` | срез текста, уходящего в модерацию |
| `MODERATION_FAIL_OPEN` | `false` | аварийный переключатель (§7) |

### 12. Влияние на действующие инстансы

- Фича включена дефолтом ⇒ на инстансах, где ключ резолвится из `OPENAI_API_KEY`, она заработает сразу после деплоя.
- На инстансах `LLM_PROVIDER=anthropic` `OPENAI_API_KEY` по clone-контракту пуст ⇒ без `MODERATION_API_KEY` модерируемые поверхности отдадут `503 moderation_not_configured`.
- **Деплой на прод автоматический (CI push→deploy), поэтому порядок обязателен: сначала `MODERATION_API_KEY` в `.env` каждого инстанса, где ключ OpenAI отсутствует, — и только потом мерж кода.** Тот же порядок «env раньше кода», что применялся при раскатке `ANTHROPIC_MAX_TOKENS=16000` ([ADR-025](ADR-025-parallel-tool-calls-and-max-tokens-truncation.md)). Пункт внесён в [prod-readiness checklist](../07-deployment.md#prod-readiness-checklist-must-configure-before-launch).
- Ранее созданные задачи возвращают `moderation.status = "unchecked"`; backfill не выполняется (expand-only, как `byok_keys.provider` / [TD-029](../100-known-tech-debt.md)).

## Альтернативы

1. **Модерация на клиенте (iOS).** Отвергнута: клиент не видит промпт, который сформировала модель в chat-tools, и не может помешать платному сабмиту; обход тривиален подменой клиента.
2. **Полагаться на фильтры fal / Veo / Kling.** Отвергнута: они непрозрачны, различаются между моделями, не покрывают референсное фото и не дают машиночитаемого вердикта клиенту — а именно вердикт требовался багрепортом.
3. **Собственная классификация (локальная модель).** Отвергнута: инфраструктура под инференс отсутствует, качество ниже, стоимость выше нуля.
4. **Только пре-модерация, без пост-.** Отвергнута: QA получил небезопасное **видео** по безобидному промпту — вход не предсказывает выход.
5. **Только пост-модерация, без пре-.** Отвергнута: пользователь платит за запуск, который заведомо будет заблокирован.
6. **Новое значение `status = "blocked"` у задачи.** Отвергнута: `status` — закрытый `Literal`, ломает уже выпущенные клиенты; различие выражено новым игнорируемым полем.
7. **`200 {status:"blocked", blockReason:"content_policy"}` по образцу [ADR-004](ADR-004-blocked-http-200.md).** Отвергнута: `blockReason` описывает права пользователя, а не содержимое запроса (§9).
8. **Fail-open по умолчанию.** Отвергнута: см. §7 — несимметричная цена ошибки; оставлена как явный аварийный переключатель.

## Последствия

- Латентность модерируемых операций растёт на один round-trip к провайдеру модерации (десятки–сотни мс). Чат без вложений не затронут.
- Появляется новая внешняя зависимость на горячем пути платной генерации; её отказ = отказ операции (осознанно, §7).
- Клиент получает контракт, достаточный для заглушки (`blocked`), блюра (`flagged`) и обычного показа (`passed`/`unchecked`).
- Возможны ложные срабатывания на пограничном контенте — цена fail-closed-политики; калибровка BLOCK-набора возможна без релиза, через env.
- Открытые вопросы: [Q-086-1](../99-open-questions.md) (PDF), [Q-086-2](../99-open-questions.md) (видео-выход), [Q-086-3](../99-open-questions.md) (workspace-файлы), [Q-086-4](../99-open-questions.md) (пороги по `category_scores`).
