# ADR-103: `ChatResponse.mediaJobs` — условие второго производителя задано: восстановление безусловно, ключ `jobId`, `creditsCharged` — величина вызова

- **Статус:** Accepted. **Реализация не выполнена** — решение docs-only, правка кода и покрытие вынесены задачами `backend` и `qa` (см. §Последствия). На сегодняшних инстансах поле работает по прежнему, документами не заданному механизму.
- **Дата:** 2026-09-08
- **Уточняет:** [ADR-068 §2](ADR-068-media-generate-chat-tools.md) — там объявлены два производителя `mediaJobs`, но **условие срабатывания второго не задано вовсе**. Настоящее решение задаёт это условие, правило слияния источников и значение `creditsCharged` у восстановленной записи. Прочие разделы [ADR-068](ADR-068-media-generate-chat-tools.md) не меняются.
- **Связано:** [ADR-101 §4](ADR-101-chat-response-documents.md) (тот же класс дефекта, разрешён там для `documents[]`; свип соседей по форме, выполненный в той врезке, и предсказал настоящий дефект), [ADR-064 §7](ADR-064-study-learn-quiz-generation-mode.md) (сосед `quiz`, у которого тот же гейт безвреден), [ADR-070](ADR-070-media-choices-wizard.md) (визард — второй путь постановки задачи в ходе), [ADR-028](ADR-028-projectid-in-chat-list-and-server-tools-in-chat-response.md) (контраст с `serverTools[]`), [ADR-060](ADR-060-media-generation-fal.md) (биллинг задачи).

## Контекст

[ADR-068 §2](ADR-068-media-generate-chat-tools.md) объявляет `mediaJobs` **содержимым ХОДА** (`messageStepId`) и называет двух производителей:

1. аккумулятор текущего вызова (append, не last-wins);
2. «фолбэк — успешные tool-result шаги `media.generate_*` этого хода».

**Слово «фолбэк» подразумевает условие, но условия текст не задаёт.** Поэтому поведение существует только в реализации: его нельзя отревьюить по документам, нельзя воспроизвести тестом от спецификации и нельзя предъявить клиенту как контракт. Ровно этот пробел [ADR-101 §4](ADR-101-chat-response-documents.md) зафиксировал как отложенную задачу («текст ADR-068 §2 условия срабатывания фолбэка не задаёт вовсе, поэтому фактическое поведение соседа проверяется по коду backend'ом»). Настоящее решение закрывает пробел **нормой**, а не описанием кода.

### Находка, из которой вырос вопрос

Исполнитель [ADR-101](ADR-101-chat-response-documents.md) сообщает, проверив по коду, что второй производитель гейтится **пустотой аккумулятора** (`_resolve_turn_media_jobs`, ранний возврат при непустом накопителе). Здесь это приводится как **гипотеза о реализации**: настоящий ADR её не устанавливает, поведения кода не описывает и задаёт **требование**. Сверка требования с фактическим кодом — задача `backend` (§Последствия).

Достижимый сценарий при таком гейте — симметричен документному сценарию [ADR-101 §4](ADR-101-chat-response-documents.md):

1. виток хода ставит задачу **A** и одновременно зовёт client-side инструмент → ход уходит на hand-off, ответ этой ноги несёт `[A]`;
2. на `/chat/tool-result` того же хода ставится задача **B**;
3. аккумулятор ЭТОГО вызова непуст (`[B]`) → восстановление не запускается → финальная нога хода отдаёт `[B]`, и **A из неё выпадает**;
4. идемпотентный реплей **того же закрытого хода** имеет пустой аккумулятор → восстановление срабатывает → тот же ход отдаёт `[A, B]`.

Наблюдаемых следствия два, и оба противоречат уже принятой норме [ADR-068 §2](ADR-068-media-generate-chat-tools.md) «содержимое ХОДА»: финальная нога хода отдаёт **не** содержимое хода, и **один ход даёт разный ответ на разных ногах**.

### Цена дефекта названа

По уточнению того же исполнителя (тоже гипотеза о коде): сама задача не теряется — tool-шаг персистирован, задача остаётся в ленте `GET /v1/media/jobs`, к чату не привязанной. Теряется **привязка задачи к ходу и чату** на той ноге, где клиент реагирует. Отдельно: якорь истории `steps[].payload.mediaJobs` по действующей норме ([modules/chats/02-api-contracts.md §`GET /v1/chats/{id}`](../modules/chats/02-api-contracts.md)) строится **при отдаче** из трёх источников, включая tool-result `media.generate_*` этого хода, — то есть по норме холодный старт задачу **A** видит. Исполнитель сообщает, что код строит якорь из аккумулятора вызова. Настоящее решение это расхождение **не устанавливает и не описывает**: проверка вынесена задачей `backend` (§Последствия), и норма якоря здесь не меняется.

### Почему нельзя просто скопировать механизм `documents[]`

[ADR-101 §4](ADR-101-chat-response-documents.md) прямо запрещает такой перенос **без отдельного решения**, и запрет обоснован: у `mediaJobs` семантика append, а **ключа дедупликации [ADR-068](ADR-068-media-generate-chat-tools.md) не задавал**. Безусловное слияние двух источников без ключа дало бы **дубли** одной задачи в одном ответе — вторую карточку в UI и, дороже, второе сообщение о списании. Настоящий ADR **и есть** то отдельное решение: он вводит ключ, и только поэтому слияние становится безопасным.

## Решение

### 1. Второй производитель работает БЕЗУСЛОВНО

`mediaJobs` собирается на **каждой** терминальной ноге хода из двух источников:

1. **аккумулятор текущего вызова** — задачи, поставленные в этом обращении (порядок выполнения);
2. **восстановление по ходу** — задачи, поставленные в этом `messageStepId` и зафиксированные его шагами (порядок `seq ASC`).

**Восстановление выполняется всегда, когда `messageStepId` не `null`, — не только при пустом аккумуляторе.** `messageStepId = null` (policy-`blocked`, ход не создан) → восстанавливать не из чего → `null`.

**Перечень источников восстановления не может быть уже перечня, нормативно заданного для якоря истории** ([modules/chats/02-api-contracts.md §`GET /v1/chats/{id}`](../modules/chats/02-api-contracts.md): записанный `payload.mediaJobs`, tool-result `media.generate_*`, `user.payload.mediaWizard.jobId`). Причина — второй путь постановки: финальный сабмит визарда ([ADR-070 §3](ADR-070-media-choices-wizard.md)) идёт **до LLM** и tool-шага `media.generate_*` может не давать вовсе; восстановление, построенное только на `media.generate_*`, теряло бы визардные задачи ровно в том сценарии, ради которого вводится. Гарантия §4 распространяется на задачу **независимо от пути постановки**.

**Восстановленная запись обязана быть полной** (тот же состав, что у записи аккумулятора, — [ADR-068 §2](ADR-068-media-generate-chat-tools.md), кроме `creditsCharged` по §3). Если для какого-то пути постановки шаги хода полной записи не несут, это **не повод сузить гарантию**: `backend` возвращает вопрос архитектору (`blocking_questions`), а не теряет запись молча.

### 2. Ключ идентичности — `jobId`; одна запись на `jobId`

**Сборка:** сначала восстановленные записи (`seq ASC`), затем записи аккумулятора (порядок выполнения); к **объединённому** списку применяется свёртка: **одна запись на `jobId`**, позиция — по **первому** появлению, значения — по **последнему** (исключение — `creditsCharged`, §3). Пересечение источников ожидаемо и безвредно: задача, уже сохранённая шагом, придёт из обоих и схлопнется в одну запись.

**Это не отмена append, а его уточнение.** «Append, не last-wins» в [ADR-068 §2](ADR-068-media-generate-chat-tools.md) противопоставляет `mediaJobs` квизу: **разные** задачи одного хода **накапливаются**, а не вытесняют друг друга — это правило сохраняется целиком и никакая задача хода из списка не выпадает. Свёртка §2 схлопывает только записи с **одним и тем же** `jobId`, то есть одну задачу, увиденную через два источника. Две карточки одной задачи в UI — дефект того же рода, что две карточки одного документа ([ADR-101 §5](ADR-101-chat-response-documents.md)).

**Контраст с `documents[]` (обе стороны помечены).** У документов ключ нужен ещё и потому, что ход **законно** трогает один документ дважды (`create`, затем `update`), и свёртка выбирает финальную `version` — там last-wins несёт содержательный смысл. У media одна задача ставится один раз и в ходе не меняется, поэтому ключ нужен **только** для идемпотентности слияния. Правило «last-wins выбирает свежее состояние сущности» с `documents[]` на `mediaJobs` переносить нечего, а правило append с `mediaJobs` на `documents[]` по-прежнему **не переносить** ([ADR-101 §5](ADR-101-chat-response-documents.md)).

### 3. `creditsCharged` — величина ВЫЗОВА: у восстановленной записи `0`

Предикат (симметричный, вычисляется из наблюдаемых фактов ноги, а не из суждения):

- запись пришла из **аккумулятора этого вызова** (сабмит и списание произошли здесь) → `creditsCharged` = фактически списанное сабмитом;
- запись пришла **только из восстановления** (списание произошло на более ранней ноге хода либо не происходило вовсе — идемпотентный реплей) → **`creditsCharged = 0`**;
- запись пришла из **обоих** источников → побеждает значение аккумулятора (частный случай общей свёртки §2: аккумулятор идёт последним).

**Против недооценки:** ни одно фактическое списание не остаётся необъявленным — нога, на которой сабмит произошёл, сообщает его. **Против переоценки:** ни одна нога не сообщает о списании, которого в ней не было. Это ровно та семантика, которая уже нормативна для одноимённого поля соседней ручки, где `mediaJobs[].creditsCharged` назван образцом: «сколько кредитов реально списал **этот** вызов… клиент по нему обновляет баланс» ([modules/chat-orchestrator/02-api-contracts.md §`POST /v1/chat/speech`](../modules/chat-orchestrator/02-api-contracts.md)).

Без этого пункта §1 был бы не улучшением, а **регрессом биллингового сигнала**: безусловное восстановление повторяло бы каждую сумму на каждой последующей ноге хода, и клиент, обновляющий баланс суммой поля, списал бы одну задачу дважды.

**Правило `creditsCharged = 0` действует ТОЛЬКО в проекции ответа хода (`ChatResponse.mediaJobs`) и в историю НЕ переносится — контраст помечен с обеих сторон.** В якоре `steps[].payload.mediaJobs` ([modules/chats/02-api-contracts.md §`GET /v1/chats/{id}`](../modules/chats/02-api-contracts.md)) `creditsCharged` описывает **стоимость задачи**, а не эффект вызова, и берётся из сохранённого результата: обнуление там стёрло бы цену запуска у холодного старта. Правило проекции на историю **не переносить**, правило истории на проекцию — **тоже**.

`status`, `kind`, `model` восстановленной записи — снимок на момент постановки (у media-задачи это `queued`, [ADR-068 §1](ADR-068-media-generate-chat-tools.md)); восстановление их не освежает. Актуальное состояние клиент берёт опросом `GET /v1/media/jobs/{jobId}` и/или push'ем ([ADR-067](ADR-067-media-ready-push-and-reconciler.md)) — это не меняется.

### 4. Гарантия и её предикат

**Каждая** задача, успешно поставленная в ходе, присутствует в `mediaJobs` **каждой** терминальной ноги этого хода — включая задачи более ранних витков и **включая случай, когда в текущем вызове поставлена ещё одна задача**. Этот случай и есть носитель гарантии: именно он отказывал при гейте «только при пустом аккумуляторе».

**Против недооценки:** ни одна успешно поставленная задача хода не выпадает ни из одной ноги. **Против переоценки:** в список не попадает ничего, кроме успешных постановок — soft-отказы `invalid_media_request` / `insufficient_credits` / `media_not_configured` / `media_upstream_error` ([ADR-068 §1](ADR-068-media-generate-chat-tools.md)) задачи не создают и в списке не появляются; ход при них не падает, факт отказа виден в `serverTools[]`.

Следствие, наблюдаемое клиентом: **все ноги одного хода отдают один и тот же список** — идемпотентный реплей перестаёт быть отдельным случаем.

### 5. Клиент трактует `mediaJobs` как содержимое ХОДА, а не дельту

Один и тот же `jobId` может прийти в нескольких ответах одного `messageStepId` — это **ожидаемо**. Список одного хода клиент **заменяет**, а не накапливает; ключ склейки — `jobId`. Это то же правило, что уже сформулировано у `quiz` ([ADR-064 §7](ADR-064-study-learn-quiz-generation-mode.md): «карточки заменяются (идемпотентно), не накапливаются»); для media оно записывается здесь впервые.

**Названная цена совместимости.** Клиент, накапливающий записи по ногам **одного** хода без склейки по `jobId`, покажет вторую карточку задачи **A** на финальной ноге. Сегодня он этого не видит **только потому, что финальная нога A теряет**, — то есть нынешняя совместимость обеспечена самим дефектом. Правка на стороне iOS разовая и данных не требует: `jobId` в ответе уже есть. Вариант «сохранить дефект ради клиента» отвергнут (§Альтернативы п.1).

### 6. Присутствие по ногам и `null`

Поле выставляется на **каждой** терминальной ноге хода: незакрытый барьер `tool_call`, hand-off на client-side инструмент, идемпотентный реплей закрытого хода, `blocked`+`max_tokens`, финальный `assistant_message` (перечень ног — тот же, что у [ADR-101 §4](ADR-101-chat-response-documents.md)). Ни одной задачи в ходе → **`null`, не `[]`** ([ADR-068 §2](ADR-068-media-generate-chat-tools.md) не меняется). policy-`blocked` → `messageStepId = null` → `null`.

**Контраст с `serverTools[]` (обе стороны помечены):** `serverTools[]` — индикатор **ЗА ВЫЗОВ** и на идемпотентном реплее приходит пустым ([ADR-028](ADR-028-projectid-in-chat-list-and-server-tools-in-chat-response.md)); `mediaJobs` — содержимое **ХОДА** и на реплее **восстанавливается**. Правило одного поля на другое не переносить ни в одну сторону. (Тот же контраст уже помечен у `quiz` и у `documents[]`; для media он записывается здесь.)

### 7. Что не меняется

Состав элемента `{ jobId, kind, status, model, creditsCharged }`; предикат наполнения — только **успешные** `media.generate_image` / `media.generate_video` и финальный сабмит визарда; биллинг media (`media-gen:{jobId}`, [ADR-060](ADR-060-media-generation-fal.md), [ADR-068 §3](ADR-068-media-generate-chat-tools.md)) и его независимость от дебита хода; контракт `/v1/media/*`; поток визарда ([ADR-070](ADR-070-media-choices-wizard.md)); норма якоря истории (§3 ограничивает только значение `creditsCharged` в проекции ответа, самого якоря не касается); отсутствие поля `moderation` в элементе ([ADR-086](ADR-086-ugc-moderation.md)); поведение `mediaJobs` в SSE — только в `done` ([ADR-069](ADR-069-sse-text-streaming.md)). Миграций нет, схема БД не меняется.

### 8. Стоимость решения

Одно дополнительное чтение шагов хода по паре `(session_id, message_step_id)` на терминальную ногу — **то же чтение и тот же ключ**, что [ADR-101 §4](ADR-101-chat-response-documents.md) уже предписал для `documents[]`, на пути, который и без того пишет шаги. Вариант «восстанавливать только на continuation-ногах» рассмотрен и отвергнут (§Альтернативы п.3).

**Побочный положительный эффект:** названная в [ADR-101 §4](ADR-101-chat-response-documents.md) цена «два соседних поля одного ответа расходятся механизмом» настоящим решением **снимается** — оба поля собираются одинаково (безусловное восстановление, слияние источников, свёртка по ключу идентичности), а различие остаётся только там, где различаются сами сущности: ключ (`jobId` против `documentId`), смысл last-wins и правило `creditsCharged`.

## Альтернативы

1. **Оставить гейт «только при пустом аккумуляторе» и записать ограничение нормой явно.** Отвергнута. Гарантию [ADR-068 §2](ADR-068-media-generate-chat-tools.md) «содержимое ХОДА» пришлось бы ослабить до «содержимое вызова плюс более ранние витки, **если в этом вызове задач не ставили**». [ADR-101 §4](ADR-101-chat-response-documents.md) уже назвал, почему такая форма правила хуже отсутствия гарантии: клиент применить её не может — ему пришлось бы самому склеивать ноги хода, ради избавления от чего поле и объявлено turn-scoped; правило не наблюдаемо на типовом ходе и отказывает на редком. Сверх того осталось бы наблюдаемое расхождение ног одного хода (реплей отдаёт больше, чем исходная финальная нога), а норма «содержимое хода» осталась бы ложной на той ноге, где клиент реагирует.
2. **Безусловное слияние БЕЗ ключа дедупликации** (буквальный перенос механизма `documents[]`). Отвергнута: дубли одной задачи — вторая карточка в UI и, дороже, повторное сообщение о списании. Ровно эту цену [ADR-101 §4](ADR-101-chat-response-documents.md) назвал причиной не переносить своё правило на media **без отдельного решения**.
3. **Восстанавливать только на continuation-ногах.** Отвергнута по той же причине, что в [ADR-101 §4](ADR-101-chat-response-documents.md): корректность поля снова зависела бы от второго, отдельно выводимого признака — а именно от такой зависимости и произошёл исправляемый дефект.
4. **Ключ ввести, но `creditsCharged` восстановленной записи оставить сохранённым значением.** Отвергнута: см. §3 — на многоножном ходе одна и та же сумма приходит клиенту дважды, и поле перестаёт быть правдой о балансе; это переоценка списания, симметричная потере задачи.
5. **Ввести в элемент отдельный признак «восстановлена, а не поставлена в этом вызове».** Отвергнута: клиенту он не нужен ни для одной задачи — список является содержимым хода (§5), а баланс обновляется суммой `creditsCharged` этого ответа (§3). Лишнее поле пришлось бы завести в схеме ответа и согласовать с якорем истории ради информации, которой никто не пользуется.
6. **Восстанавливать только по tool-результатам `media.generate_*`** (буква прежней формулировки [ADR-068 §2](ADR-068-media-generate-chat-tools.md)). Отвергнута: см. §1 — визардный сабмит ([ADR-070 §3](ADR-070-media-choices-wizard.md)) идёт до LLM и такого tool-шага может не давать, то есть гарантия отказывала бы на целом пути постановки.

## Последствия

- **Поведение живого поля меняется — правка НЕ аддитивная.** На многоножных ходах финальная нога начинает нести задачи ранних витков, а `creditsCharged` восстановленных записей становится `0`. Требуются реализация (`backend`) и покрытие (`qa`) **до** выката; на сегодняшних инстансах поле работает по прежнему механизму.
- **Требование к клиенту (iOS):** список `mediaJobs` одного `messageStepId` **заменять**, склейка по `jobId`; повтор той же задачи в нескольких ответах одного хода — штатен (§5).
- **Открытая проверка, вынесенная `backend`:** фактическое условие срабатывания второго производителя и фактический источник якоря `steps[].payload.mediaJobs` — **гипотезы исполнителя**, настоящим ADR не установленные. Если якорь действительно строится из аккумулятора вызова, это расхождение с действующей нормой [modules/chats/02-api-contracts.md §`GET /v1/chats/{id}`](../modules/chats/02-api-contracts.md) (три источника при отдаче) — и тогда `architect` заводит долг с cross-ref на настоящий ADR; молча приводить норму к коду **нельзя**.
- Каталог `GET /v1/tools`, коды ошибок, биллинг, схема БД и контракт `/v1/media/*` не затрагиваются.
- Реализация — `backend`: снять ранний возврат при непустом аккумуляторе, слить источники, свернуть по `jobId`, обнулить `creditsCharged` у восстановленных записей, покрыть визардный путь постановки. Тесты — `qa`, по [modules/chat-orchestrator/09-testing.md](../modules/chat-orchestrator/09-testing.md).
