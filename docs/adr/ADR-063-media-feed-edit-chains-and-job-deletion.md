# ADR-063 — Лента генераций: цепочки правок, курсорная пагинация и удаление задачи

- Статус: Accepted
- Дата: 2026-08-05
- Тип: feature-ADR, **расширяет [ADR-060](ADR-060-media-generation-fal.md)** (`GET /v1/media/jobs` и объект задачи); асинхронный контракт, биллинг и карта ошибок ADR-060 не меняются
- Связано: [ADR-036 §8](ADR-036-workspaces-implementation.md) (курсорная пагинация — та же форма), [ADR-062](ADR-062-media-upload-via-fal-storage.md) (откуда берётся первая картинка в цепочке), [ADR-061 §5](ADR-061-fal-price-calibration-and-priced-defaults.md) (срок жизни ссылок, без которого лента протухает), [ADR-005](ADR-005-idempotency-ledger.md) (возврат кредитов при провале)
- Модуль: [media-generation](../modules/media-generation/README.md)

## Context

Запрос от iOS-разработчика: «чтоб они в чат как бы складывались… я сгенерировал фото, и потом сразу же выбрал правку чтобы по этой фотке её отредактировать».

Технически правка уже возможна: `assets[].url` — обычный https-URL, его можно положить обратно в `imageUrls`. Но собрать из этого ленту нельзя по трём причинам.

1. **Ленты нет.** `GET /v1/media/jobs` принимает только `limit` (1–100). Дальше первой страницы не уйти: курсора нет, `offset` нет, а `limit` упирается в потолок. Экран истории после сотни генераций перестаёт работать.
2. **Связи нет.** Задача-правка ничем не отличается от независимой генерации: в ответе нет ни ссылки на исходную задачу, ни того, какие картинки пошли на вход. Нарисовать «вот исходник → вот результат правки» не из чего.
3. **Ошибку не убрать.** Удаления задачи нет вовсе. Неудачная генерация остаётся в списке навсегда.

Отдельно стоит решить, что такое «в чат». Буквальная интеграция — писать синтетические шаги в `chat_steps` — отвергается: сегодня туда пишет **только** оркестратор (семь мест в `chat/orchestrator.py`), `payload` там имеет провайдерную форму и читается нормализацией [ADR-024](ADR-024-history-payload-domain-normalization.md)/[ADR-058](ADR-058-provider-agnostic-assistant-payload-in-chats-reads.md), а [ADR-060](ADR-060-media-generation-fal.md) прямо провёл границу «генерация идёт мимо chat-оркестратора». Заводить второго писателя в чужой формат ради визуального сходства значит покупать риск в самом нагруженном месте системы за косметику. Нужна не общая таблица, а **данные, из которых клиент нарисует ленту**: страницы, связь и удаление.

## Decision

### 1. Цепочка: `sourceJobId` вместо URL, который клиент носит сам

`POST /v1/media/images` и `/videos` получают необязательное поле **`sourceJobId`** — «сделай это из результата вон той задачи». Сервер сам достаёт ссылки на ассеты родителя.

Поле взаимоисключимо с `imageUrls`/`imageUrl` (иначе `422`): два способа задать одно и то же на одном запросе — это вопрос «какой из них главнее», на который у контракта не должно быть ответа.

Почему id, а не «клиент подставит URL сам» — тот же довод, по которому клиент не присылает endpoint fal и цену ([ADR-060 §2](ADR-060-media-generation-fal.md)). Правка «этой фотки» — отношение между **нашими** задачами, а URL провайдера живёт по чужой политике и однажды перестанет открываться ([ADR-061 §5](ADR-061-fal-price-calibration-and-priced-defaults.md)). Когда клиент присылает id, связь в БД остаётся верной, даже если ссылка умерла.

Родитель обязан быть: **чужим не быть** (иначе `404` — существование чужих задач не раскрываем), **`completed`**, **`kind: image`** и иметь непустые `assets`. Каждое условие — `422` **до** списания. Требование «родитель — изображение» не ограничение ради ограничения: и режим редактирования, и image-to-video берут на вход картинку, а кадр из видео мы не извлекаем.

Ассеты родителя обрезаются по `maxInputImages` модели — та же граница, что и для присланных вручную `imageUrls`.

### 2. Что появляется в объекте задачи

Два поля, оба аддитивные: **`parentJobId`** (из чего сделано, `null` у корня цепочки) и **`inputImageUrls[]`** (что реально ушло на вход — и при `sourceJobId`, и при явных `imageUrls`).

`inputImageUrls` персистится, а не вычисляется из родителя: родителя могли удалить (§4), а показать «из чего это сделано» лента должна и после этого. Хранится то, что фактически ушло провайдеру, — это же и делает поле честным свидетельством, а не реконструкцией.

Миграция **`0019`** (down_revision `0018_media_jobs`, single head, expand-only): `parent_job_id UUID NULL REFERENCES media_jobs(id) ON DELETE SET NULL` и `input_image_urls JSONB NULL`. `ON DELETE SET NULL`, а не `CASCADE`: удаление исходника — «убрать неудачный кадр из ленты», а не «стереть всё, что из него выросло». Потомок остаётся, просто теряет родителя.

### 3. Лента: курсорная пагинация

`GET /v1/media/jobs` получает `cursor` и возвращает `nextCursor` — по образцу [ADR-036 §8](ADR-036-workspaces-implementation.md), чтобы в API не появилось второй конвенции пагинации. Курсор непрозрачный, кодирует `(created_at, id)` последней отданной строки; порядок `created_at DESC, id DESC` — тот же, что уже есть, плюс стабильный тай-брейк по id. Невалидный курсор — `422`.

Ключевая пагинация, а не `offset`: лента растёт с головы, и при `offset` вставка новой задачи между запросами сдвигает окно — пользователь видит дубли и пропуски. Индекс `(user_id, created_at)` из [ADR-060](ADR-060-media-generation-fal.md) под этот порядок уже есть.

Свойство ADR-060 «листинг read-only, провайдера не опрашивает» сохраняется: N задач на странице не должны превращаться в N исходящих вызовов.

### 4. Удаление задачи

**`DELETE /v1/media/jobs/{jobId}`** → `200` с `{"deleted": true}`, по конвенции проекта (`DELETE /v1/chats/{id}`, `DELETE /v1/workspaces/{id}`); `204` в этом API не используется нигде. Чужая или несуществующая задача — `404`.

**Незавершённую задачу удалить нельзя — `409 job_not_terminal`.** Возврат кредитов при провале у провайдера привязан к строке `media_jobs`: он идемпотентен ключом `media-refund:{jobId}` и флагом `credits_refunded` ([ADR-060 §4](ADR-060-media-generation-fal.md)) и срабатывает при опросе. Удалив `queued`/`running`, пользователь уничтожил бы единственное место, по которому этот возврат может произойти, — и заплатил бы за генерацию, исход которой уже никто не узнает. Поэтому сначала опрос до терминального статуса, потом удаление. Обратная сторона — задача, которую провайдер бросил и которую никто не опрашивает, не удаляется тоже; это тот же зазор, что описан в [Q-060-2](../99-open-questions.md), и закрывается он там же, фоновой доводкой, а не разрешением терять деньги.

Удаляется **только наша строка**. Файл остаётся у провайдера до истечения его retention — мы им не владеем ([ADR-060](ADR-060-media-generation-fal.md): ассеты через нас не проходят). Это сказано в контракте прямо, иначе выглядит как утечка.

Гейт активации остаётся общим для префикса: без `FAL_API_KEY` `DELETE` тоже отвечает `503` ([ADR-060 §5](ADR-060-media-generation-fal.md)). Заводить исключение ради одного метода значит разрушить свойство «раздел генерации скрывается по одному вызову».

### Границы

Чат (`chat_sessions`/`chat_steps`) не затронут: ни новой записи, ни нового читателя, ни изменения формы `payload`. Биллинг не меняется — `sourceJobId` не влияет на цену (режим text/image её и раньше не менял, [ADR-060 §4](ADR-060-media-generation-fal.md)). Ассеты по-прежнему не перекладываются в наше хранилище.

## Consequences

- (+) Лента листается: история генераций перестаёт обрываться на первой сотне.
- (+) «Отредактировать эту фотку» — одно поле, а не забота клиента о том, где лежит URL и жив ли он.
- (+) Связь «из чего сделано» переживает смерть ссылки провайдера и удаление родителя.
- (+) Неудачную генерацию можно убрать из ленты.
- (+) Чат не получил второго писателя — самое нагруженное место системы не тронуто.
- (−) Задачу в `queued`/`running` удалить нельзя. Для пользователя это «кнопка не работает прямо сейчас»; альтернатива — молча терять его кредиты.
- (−) Удаление не удаляет файл у провайдера. Полное удаление требует владения байтами, то есть собственного хранилища — [Q-062-1](../99-open-questions.md).
- (−) Цепочка хранит ссылки, а не байты: если ассет родителя истёк, повторная правка вернётся как `failed` от провайдера (недоступная картинка), хотя связь в ленте останется видимой. Смягчается `FAL_ASSET_RETENTION_SECONDS` ([ADR-061 §5](ADR-061-fal-price-calibration-and-priced-defaults.md)).
- Миграция `0019`. Новых env нет. Ответ задачи расширяется аддитивно (`parentJobId`, `inputImageUrls`), листинг — `nextCursor`; существующие поля не меняются.

## Тесты

- `tests/unit/test_media_cursor_adr063.py` — round-trip курсора, устойчивость к мусору (`InvalidCursorError`), naive-datetime приводится к UTC.
- `tests/integration/test_media_feed_adr063.py` — HTTP-путь с фейком на границе httpx: `sourceJobId` подставляет ассеты родителя в запрос к провайдеру и проставляет `parentJobId`/`inputImageUrls`; `422` при одновременных `sourceJobId` и `imageUrls`; `404` на чужого родителя; `422` на незавершённого, на видео-родителя и на родителя без ассетов; обрезка по `maxInputImages`; `inputImageUrls` заполняется и при явных `imageUrls`; пагинация листает всю ленту без дублей и пропусков, `nextCursor` пуст на последней странице, фильтр `kind` работает вместе с курсором, битый курсор → `422`; `DELETE` → `200` для `completed`/`failed`, `404` для чужой и повторной, `409` для `queued`/`running`; удаление родителя не уносит потомка и обнуляет его `parentJobId`.
