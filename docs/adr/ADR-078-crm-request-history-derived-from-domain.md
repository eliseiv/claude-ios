# ADR-078 — История запросов CRM выводится из доменных таблиц (исправление ADR-077)

- **Статус:** accepted
- **Дата:** 2026-08-14
- **Область:** CRM Admin API, data model
- **Пересматривает:** [ADR-077](ADR-077-crm-request-logs.md) — только модель ЧТЕНИЯ

## Контекст

[ADR-077](ADR-077-crm-request-logs.md) заменил ошибочное чтение `audit_logs`
новой таблицей `request_logs` и оставил решение «старый audit не
backfill-ится». Журнал заполняется только со своего появления, поэтому на
следующий же день после деплоя CRM показывала **пустую** историю всем, кто
пользовался сервисом раньше.

Прод-факт (инстанс `ravelumi`, пользователь `d80034dc`): в `request_logs`
**0 строк**, при этом в доменных таблицах — 15 оплаченных ходов чата
(`chat_steps` + списания в `ledger_transactions`) и 13 `media_jobs`. Оператор
вместо мусорных значений получил отсутствие данных, то есть исправление
оказалось хуже исходного дефекта: `billing_debit` в колонке «Запрос» хотя бы
подтверждал, что пользователь активен.

Ключевое наблюдение, пропущенное в ADR-077: **историю не нужно накапливать —
она уже есть**. Соседний сервис `232-claude-backend` отдаёт
`GET /users/{id}/requests` из доменной таблицы `generations`, а не из журнала
событий, и потому его история ретроактивна по построению. `audit_logs` для этой
цели непригоден и вторично: токены в его `payload` **редактируются**
(`"inputTokens": "***REDACTED***"` на проде), то есть экономику из него
восстановить нельзя в принципе.

## Решение

`CrmAdminService.list_requests` читает **объединение трёх источников**, а не
один журнал.

### 1. Чат: единица истории — ход, а не шаг

Строка = `message_step_id` (`chat_steps` с `role='assistant'`, сгруппированные).
В server-side tool-loop один ход пишет несколько `assistant`-шагов, а списание
по нему **ровно одно** — `orchestrator._debit` идемпотентен по
`message_step_id`. Строка на шаг показала бы одно списание дважды-трижды
(прод: 18 шагов против 15 оплаченных ходов).

- `endpoint` = `chat:<model>`, модель — из `usage` последнего шага хода
  (`ORDER BY seq DESC`), как `type:model` в 232;
- `tokens_spent` — сумма из `ledger_transactions` по
  `idempotency_key = message_step_id::text`, `type='debit'`. Это **точная**
  списанная величина, а не оценка по usage;
- `duration_sec` — из `request_logs`, если ход был залогирован, иначе `NULL`
  («не измерено»): у прошлых ходов замера начала запроса не существует.

### 2. Media: `media_jobs`

`endpoint` = `<kind>:<model_id>` (`video:veo-3.1`), длительность —
`updated_at - created_at` у терминальных задач, `tokens_spent` =
`credits_charged`, `refunded` = `credits_refunded`. Возврат — отдельный факт и
не обнуляет списание (правило ADR-077 сохранено).

### 3. `request_logs` — только то, чего в доменных таблицах нет

Берутся строки с `message_step_id IS NULL AND media_job_id IS NULL`: упавшие и
ещё выполняющиеся запросы. Успешный запрос всегда проставляет одну из двух
корреляций, поэтому **дедупликация обеспечена условием, а не сверкой ключей** —
двойного показа не возникает по построению.

### 4. Единые правила отображения

`provider_cost_usd` остаётся `NULL` = «не измерено» (`NULL ≠ 0`): себестоимость
провайдера сервис не сохраняет. Порог `slow` — 30 с, тот же, что в 232:
операторская страница объединяет бэки, и разъезд порогов дал бы две несравнимые
шкалы. Следствие принято осознанно — генерация видео (300–400 с) помечается
`slow` штатно.

## Последствия

- история существующих пользователей появляется **немедленно и задним числом**,
  без миграции данных;
- `request_logs` и его writer **не меняются**: таблица остаётся единственным
  источником по упавшим и незавершённым запросам и по длительности новых ходов;
- запрос читает `chat_steps`/`media_jobs`/`request_logs` по индексам
  `ix_sessions_user_updated`, `ix_media_jobs_user_created`,
  `ix_request_logs_user_started` и уникальному `(user_id, idempotency_key)`
  ledger'а; страница ограничена контрактным `limit ≤ 100`;
- `tokens_spent` для хода без строки ledger — `NULL`, а не `0`: бесплатный
  (BYOK) ход и потерянное списание внешне неразличимы, и `0` был бы утверждением
  факта, которого нет.

## Альтернативы

- **Backfill-миграция `audit_logs`/домена в `request_logs`.** Отклонено:
  одноразовый перенос дублирует данные, требует ручного соответствия событий
  запросам и не защищает от следующего расхождения журнала с доменом. Вывод при
  чтении верен всегда.
- **Оставить чтение только `request_logs` и подождать накопления.** Отклонено:
  это и есть регрессия — оператор теряет историю активных пользователей,
  включая тех, по кому идёт разбор обращений.
- **Вернуть чтение `audit_logs`.** Отклонено: мусорные `endpoint` и
  отредактированные токены в `payload`.
