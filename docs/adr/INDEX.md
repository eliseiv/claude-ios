Своё хранилище отвергнуто по трём независимым причинам: (а) объектного хранилища у нас нет вообще — всё бинарное лежит в Postgres BYTEA, и это уже признанный долг (TD-009 `site_files`, TD-027 `workspace_files`), складывать туда пользовательские фото значит усугублять ровно тот долг, который предстоит отдавать; (б) ссылку обязан скачать fal ⇒ это была бы **вторая** публичная неаутентифицированная поверхность после `/v1/preview` ([ADR-010](ADR-010-backend-hosted-preview.md)) — новый предмет аудита ради задачи, решаемой без него; (в) наш хост стал бы лишним звеном «телефон → мы → fal», чья недоступность ломает генерацию **после** списания кредитов. **Форма тела** повторяет `WorkspaceFileUploadRequest` ([ADR-036 §4](ADR-036-workspaces-implementation.md)) — `type`/`mediaType`/`filename`/`data` — не ради единообразия, а чтобы iOS обошёлся **одним** нормалайзером; `type` принимает только `image` (документ или текст как референс генерации смысла не имеют). Валидация переиспользуется целиком ([ADR-020](ADR-020-inline-base64-attachments-mvp.md)): allowlist `mediaType`, оценка размера **до** декодирования base64, точная проверка после, сверка magic bytes (анти-MIME-spoof) — расходиться этим проверкам между тремя точками загрузки нельзя. **Лимиты:** свои `MEDIA_UPLOAD_MAX_BYTES` (10 МБ на файл) и `MEDIA_UPLOAD_REQUEST_BODY_LIMIT` (16 МБ на тело) с отдельной веткой в `SizeLimitMiddleware` по образцу [ADR-045](ADR-045-per-path-body-limit-workspace-files.md) и с тем же инвариантом `транспортный >= ceil(файл × 4/3) + JSON-обвязка`; общий `SIZE_LIMIT_BODY` не поднимается — он защищает все остальные маршруты. 10 МБ, а не 5 МБ как у картинок чата: чат отдаёт картинку **модели** и платит токенами, здесь картинка определяет качество результата, за который уже заплачено кредитами. **SSRF:** `initiate` возвращает `upload_url` на CDN/бакете — **другом хосте**, чем `FAL_REST_BASE`, поэтому проверка префикса (которой защищены `status_url`/`response_url`, [ADR-060 §3](ADR-060-media-generation-fal.md)) здесь неприменима; вводится allowlist суффиксов хоста `FAL_UPLOAD_HOST_SUFFIXES` (fail-closed при пустом значении), обязателен `https`, проверяются **оба** URL — и `upload_url`, и `file_url`. Не прошедший проверку URL → `502`, а не «сходим и посмотрим»: PUT туда отправляет файл пользователя. Наш ключ на чужой хост не уходит — слот несёт собственную авторизацию. Карта ошибок общая с ADR-060 (`401`/`403` → `503 media_generation_not_configured`, недоступность → `502 upstream_error`), гейт активации общий для префикса. **Границы:** загрузка **бесплатна** (кредиты за генерацию, а не за подготовку к ней; иначе неудачный подбор референса стал бы платным), защита — общий per-user rate limit и лимиты размера; учёта загруженных файлов **нет** (ни таблицы, ни привязки к пользователю) ⇒ удалить конкретный файл по требованию нельзя — [Q-062-2](../99-open-questions.md). Срок жизни — тот же `FAL_ASSET_RETENTION_SECONDS`, что у результатов ([ADR-061 §5](ADR-061-fal-price-calibration-and-priced-defaults.md)); ответ несёт `expiresAt` (`null` = не ограничен либо политика провайдера). Файл у провайдера **публичен по URL** — иначе модель его не скачает; свойство то же, что у ссылок на результаты. Без миграции; существующие эндпоинты не меняются. Новые env `FAL_REST_BASE`/`FAL_UPLOAD_HOST_SUFFIXES`/`MEDIA_UPLOAD_MAX_BYTES`/`MEDIA_UPLOAD_REQUEST_BODY_LIMIT`. Открыты [Q-062-1](../99-open-questions.md) (возврат к своему хранилищу), [Q-062-2](../99-open-questions.md).
