## Часть A. Вход вызова LLM — в форме провайдера клиента, который его отправляет

### A. Контекст

**Прод-наблюдение (снято владельцем волны 2026-09-11 около 08:10 UTC, velunixa):** у аккаунта Anthropic кончился баланс; ходы Claude-сессий переключаются на OpenAI (`chat_provider_failover`, `reason=credentials` — 3325 событий за 72 ч), и картинка из вложения до `gpt-4o` не доходит: модель отвечает «не могу видеть изображения».

**Механизм (по коду, `f8f4b37`):**

- `ChatOrchestrator._run_turn` (`src/app/chat/orchestrator.py`) вычисляет `session_provider` — для credits `Settings.credits_provider_for_model(sess.model)`, для BYOK `_active_provider()` (то есть `LLM_PROVIDER`), — и **один раз** собирает блоки вложений `prepare_attachments(attachments, get_settings(), session_provider)`; у `prepare_attachments` (`src/app/chat/attachments.py`) параметр `provider` с дефолтом `PROVIDER_ANTHROPIC`, ветвление формы — в `_content_block` (`_anthropic_content_block` / `_openai_content_block`).
- Тем же `session_provider` собираются файлы-знания workspace: `WorkspacesService.context_for_session(..., provider=session_provider)` → `_build_file_attachments` → `_image_block` (`src/app/workspaces/service.py`) — **вторая, независимая копия** того же маппинга картинки.
- `_merge_attachments` склеивает оба набора в один `PreparedAttachments`, он уходит в `_generate_loop` как `first_turn_attachments` → `"attachments": turn0_attachments` в `llm_kwargs` → `_credits_llm_with_failover`, где **каждая** попытка `build_attempt_chain` получает те же готовые блоки без пересборки (`attempt_kwargs = {**llm_kwargs, ...}` меняет только `api_key`, `model`, `provider_state`).
- Что с чужими блоками делает каждый клиент:
  - `OpenAIResponsesClient._inject_responses_attachments` пропускает блоки через `_responses_content_part` и **молча отбрасывает** нераспознанные; картинку тот распознаёт только в форме `image_url`, PDF — только в форме `file`. Anthropic-блоки `image`/`document` исчезают без ошибки — **это прод-наблюдение**;
  - `OpenAIClient._inject_attachments` (Chat Completions) добавляет блоки в content как есть — Anthropic-блок `{"type":"image",...}` уходит в Chat Completions без преобразования;
  - `AnthropicClient.create_message` / `stream_message` вставляют `attachments.content_blocks` в последний user-turn как есть — **гипотеза владельца об обратном направлении подтверждена кодом**: блок `image_url` / `file` уходит в Anthropic без преобразования.
  - Реакция апстрима на чужой блок в двух последних случаях по коду не видна и **живьём не измерялась**; блок в любом случае не той формы, какую провайдер определяет в своей входной схеме. Если апстрим отказывает, отказ — `UpstreamError`: у OpenAI-попытки после неё кандидатов нет (ход падает `502`), у Anthropic-попытки `next_attempt_index` уводит на OpenAI (см. [TD-051](../100-known-tech-debt.md)).

**Свип по признаку «данные, заранее собранные под одного провайдера, уходят в вызов другого».** Единица свипа — параметры `LLMClient.create_message` / `stream_message` (`src/app/chat/llm_client.py`, восемь параметров; единственное место вызова — `_invoke_llm`); проверены все восемь:

| Параметр | Зависит от провайдера | Кто задаёт форму сегодня | Итог |
|---|---|---|---|
| `system_prompt` | нет (строка) | — | ✓ |
| `messages` — user-шаги | нет: текстовые блоки и плейсхолдеры ([ADR-020 §3](ADR-020-inline-base64-attachments-mvp.md)) | — | ✓ |
| `messages` — tool-шаги | нет: доменная запись, каждый клиент рендерит сам | клиент | ✓ |
| `messages` — assistant-шаги | **да**: `LLMResult.content_blocks` — wire-форма провайдера, **ответившего** на тот виток | ответивший клиент | ✗ → §A3 |
| `tools` | нет: нейтральные определения, сериализует клиент ([ADR-033 §4](ADR-033-llm-provider-abstraction.md)) | клиент | ✓ |
| `attachments` | **да** | вызывающий (`session_provider`) | ✗ → §A2 (**названный дефект**) |
| `api_key` | да | на каждую попытку (`Attempt.api_key`) | ✓ |
| `model` | да | на каждую попытку (`Attempt.model` / `_model_for_provider`) | ✓ |
| `generation_mode` | нет: ручки режима у каждого клиента свои | клиент | ✓ |
| `provider_state` | да | на каждую попытку (`_provider_state_for_attempt`, сверка по имени провайдера) | ✓ (пробел по слоту ключа — [TD-032](../100-known-tech-debt.md), вне этого решения) |

Производителей провайдер-зависимых блоков вложений **два**: `prepare_attachments` и `WorkspacesService._image_block`. Путей, по которым провайдер вызова расходится с провайдером, под который собран вход, — **три**, и лишь первый связан с отказом:

1. **кросс-обход credits** ([ADR-074](ADR-074-provider-key-failover.md)) — в обе стороны;
2. **BYOK с ключом не того провайдера, что `LLM_PROVIDER`** ([ADR-044](ADR-044-multi-provider-byok.md)): блоки собраны под `_active_provider()`, а вызов идёт клиентом `llm_client_for(byok_provider)`; `byok_provider` вычисляется `_resolve_api_key` уже **после** `prepare_attachments`. Anthropic-ключ на OpenAI-инстансе получает блоки `image_url` на **каждом** ходе с картинкой, без всякого отказа поставщика;
3. **операторский дефолт модели другого провайдера** ([ADR-099 §8](ADR-099-crm-admin-economics-and-instance-settings.md)): у сессии с `model IS NULL` `session_provider` = `LLM_PROVIDER`, а `_generate_loop` подставляет `instance_config.instance_default_model()` (выбирается из `Settings.allowed_models_union()`, то есть может быть моделью соседнего провайдера) и строит цепочку от **её** провайдера.

Для истории (assistant-шаги) те же пути плюс ещё два: **замена BYOK-ключа** на ключ другого провайдера (`BYOKService.set_key` определяет провайдера по новому ключу; сессия продолжается новым провайдером поверх истории старого) и **смена операторского дефолта** со временем. Что с чужой формой истории делает каждый клиент (по коду):

- `OpenAIResponsesClient._responses_assistant_items_from_blocks` — **терпим уже сегодня**: читает и Chat-Completions-сообщение `{role:"assistant", content, tool_calls}`, и Anthropic-блоки `text`/`tool_use`; прочее (`thinking`, `server_tool_use`, …) отбрасывает;
- `OpenAIClient._assistant_message_from_blocks` → `_anthropic_blocks_to_openai_content` берёт из чужих блоков **только текст**, `tool_use` отбрасывает (докстринг: «not used in production — one provider per instance» — неверно с [ADR-073](ADR-073-dual-credits-llm-providers.md)/[ADR-074](ADR-074-provider-key-failover.md)). Следом в историю идёт `role=tool` с `tool_call_id`, у которого больше нет вызова, — такое сообщение Chat Completions по своей схеме не принимает;
- `AnthropicClient._build_provider_messages` отдаёт `content_blocks` assistant-шага **дословно**: Chat-Completions-сообщение уходит как «блок» с ключом `role`, Responses-блоки `reasoning` / `web_search_call` и `text` с ключом `annotations` — как есть.

Смягчение [ADR-074 §3](ADR-074-provider-key-failover.md) исходило из того, что обход «на одном ходе — аварийный». Прод-наблюдение выше опровергает посылку: мёртвый баланс держит обход **сутками**, и за это время Claude-сессии копят assistant-шаги в форме OpenAI. После пополнения баланса Anthropic получает эту историю дословно.

### A. Решение

#### §A1. Инвариант

**Форму любого провайдер-зависимого входа вызова LLM определяет клиент, который этот вызов выполняет, в момент вызова** — а не тот, кто вход собирал, и не провайдер сессии. Всё, что до клиента, — нейтрально. Инвариант задан по ФОРМЕ «вход, форма которого зависит от провайдера», поэтому он действует на любой будущий параметр `LLMClient` того же рода и на любой будущий путь, где провайдер вызова отличается от провайдера сборки (четвёртый путь в перечне выше не нужно дописывать — он подпадает автоматически).

Следствие для каждого прохода по коду: **передать клиенту провайдер-специфичный блок ЗАПРЕЩЕНО**; вызывающий передаёт нейтральные данные, клиент рендерит их своим провайдером.

#### §A2. Вложения и файлы-знания — нейтральный носитель, рендер в клиенте

1. **`PreparedAttachments` несёт нейтральные части, а не провайдерные блоки.** Поле `content_blocks` заменяется полем `parts: list[AttachmentPart]`; `AttachmentPart` (`src/app/chat/attachments.py`) — `kind ∈ {image, document, text}`, `media_type`, `filename`, `data` (base64 — у `image`/`document`), `text` (готовый текст — у `text`). Поля `placeholders` и `images` не меняются.
2. **Производители отдают только нейтральные части.** Параметр `provider` снимается с `prepare_attachments` и с `WorkspacesService.context_for_session`; `WorkspacesService._image_block` удаляется — отдельной копии маппинга картинки больше нет. Валидация `prepare_attachments` (allowlist, лимиты до декодирования, base64, magic bytes, PDF page-guard, отказ для `audio`) не меняется и по-прежнему выполняется **до** записи шага (`422` без записи в БД).
3. **Рендер — одна функция в одном месте:** `render_attachment_blocks(parts, provider)` в `src/app/chat/attachments.py` содержит оба маппинга, которые сегодня живут в `_anthropic_content_block` / `_openai_content_block` (формы блоков не меняются — [ADR-033 §5](ADR-033-llm-provider-abstraction.md), [ADR-041](ADR-041-openai-native-pdf-attachment.md)). **Вызывает её только клиент**, передавая **собственного** провайдера: `AnthropicClient` — `anthropic`, `OpenAIClient` и `OpenAIResponsesClient` — `openai` (последний затем переводит блоки в `input_*` своим `_responses_content_part`). Вызывающий провайдера не передаёт — значит, не может передать неверного.
4. **Рендер тотален:** на каждую нейтральную часть — ровно одна wire-часть. Молча отбросить часть ЗАПРЕЩЕНО, в том числе в `OpenAIResponsesClient._inject_responses_attachments`: часть, которую клиент не может отрендерить, — исключение **до** вызова апстрима, а не пропуск.
5. **Инвариант набора классов.** Классы, которые принимает `prepare_attachments`, обязаны рендериться **каждым** клиентом. Сегодня это верно для всех трёх (`image`, `document`, `text`; `audio` до сборки не доходит — [ADR-095](ADR-095-voice-messages.md)), поэтому поведение приёма не меняется. Появится класс, который какой-то провайдер не принимает, — это решение нового ADR, а не тихий пропуск в одном клиенте.
6. **Что не меняется:** блоки подаются только на первом витке хода и затем потребляются ([ADR-088](ADR-088-attachments-per-turn-contract.md)); base64 живёт в памяти в **одном** экземпляре (рендер на попытку строит список ссылок на ту же строку, а не копию данных); в `chat_steps` — только плейсхолдеры ([ADR-020 §3](ADR-020-inline-base64-attachments-mvp.md)); модерация хода ([ADR-086](ADR-086-ugc-moderation.md)) читает исходные вложения, как сейчас.

#### §A3. История — терпимое чтение assistant-шага любой формы

1. **Норма.** Каждый клиент строит свои провайдер-сообщения из assistant-шага **любой формы, которую пишет любой клиент этого кода** (признак — «форма, которую возвращает какая-либо реализация `LLMClient` в `LLMResult.content_blocks»`; на 2026-09-11 таких форм три: Anthropic-блоки `AnthropicClient`, Chat-Completions-сообщение `OpenAIClient`, компактные блоки `OpenAIResponsesClient._parse_responses_result` — перечень форм снимок, форма, появившаяся позже, подпадает под норму автоматически).
2. **Форма распознаётся по структуре блока, а не по провайдеру сессии**: одна сессия законно несёт несколько форм.
3. **Своя форма — дословно.** Шаг формы клиента-читателя реплеится так же, как сегодня, **бит-в-бит**. Сессии без смены провайдера не меняются никак.
4. **Чужая форма — перевод по трём правилам:**
   - видимый текст ассистента — текст в форме читателя;
   - вызов инструмента (Anthropic `tool_use`, Chat-Completions `tool_calls[]`, Responses-компактный `tool_use`) — вызов в форме читателя; **id — дословно** ([ADR-008](ADR-008-provider-tool-use-id.md)), имя — wire-имя с подчёркиваниями дословно ([ADR-033 §4](ADR-033-llm-provider-abstraction.md)), аргументы — объект ↔ JSON-строка;
   - блок, который провайдер-читатель не определяет во входной схеме и который не несёт ни видимого текста, ни вызова инструмента (`thinking`/`redacted_thinking`, `reasoning`, служебные блоки хостового поиска, поле `annotations` у текста), — отбрасывается.
5. **Инвариант парности:** реплеенный вызов инструмента ⇔ реплеенный результат этого инструмента. Отбросить вызов, оставив результат, ЗАПРЕЩЕНО — именно так сегодня ломается `OpenAIClient._anthropic_blocks_to_openai_content`.
6. **Разбор чужой формы — одно место, и оно уже существует:** `to_domain_blocks` (`src/app/chats/provider_blocks.py`, [ADR-058](ADR-058-provider-agnostic-assistant-payload-in-chats-reads.md)) распознаёт Chat-Completions-сообщение по признаку «`role == "assistant"` и нет `type`» и переводит его в доменные блоки `text` / `tool_use` (id — сырой, имя — wire, аргументы — объект); блоки с `type` возвращает как есть. Им уже пользуются чтения истории (`app.chats.service`, `app.chats.repository`), озвучка (`app.chat.speech`) и память (`app.memory.text`). Клиенты при реплее пользуются **им же**; второй распознаватель тех же форм (в том числе в `src/app/chat/llm_client.py`) заводить ЗАПРЕЩЕНО — два списка об одном факте разошлись бы молча, и чтение истории перестало бы совпадать с реплеем. После `to_domain_blocks` каждый клиент отбрасывает блоки, чей `type` его входная схема не определяет, и снимает поля вне своего wire-перечня (для Anthropic — `_BLOCK_WIRE_FIELDS` [ADR-021](ADR-021-deterministic-step-order-and-block-normalization.md)). Если слоистость потребует перенести функцию из `app.chats` в модуль, общий для `app.chat` и `app.chats`, — переносится она целиком, копия не остаётся. `OpenAIResponsesClient._responses_assistant_items_from_blocks` уже терпим и собственный разбор Chat-Completions-сообщения держит — его переводят на `to_domain_blocks` без изменения поведения.
7. **Расширенное мышление Anthropic.** Anthropic требует, чтобы при включённом `thinking` последнее assistant-сообщение, за которым в истории идут только `tool_result`, начиналось с thinking-блока (требование входной схемы провайдера; живьём не измерялось). Если такой шаг — чужой формы (виток ответил другой провайдер), thinking-блока у него нет и быть не может, поэтому **эта попытка к Anthropic выполняется без `thinking`**. Обе стороны: шаг своей формы с thinking-блоком ⇒ `thinking` включается, как сегодня.
8. **Что остаётся долгом:** перевод теряет то, что другой провайдер понять не может (рассуждение, цитаты-аннотации, служебные записи поиска). Хранение нейтральной формы в `chat_steps` по-прежнему не вводится — [TD-024](../100-known-tech-debt.md) (строка приведена к факту этим решением).

#### §A4. Что не меняется

Цепочка кандидатов и поводы ротации [ADR-074 §1/§2](ADR-074-provider-key-failover.md); BYOK не ротируется; подмена модели на попытку; фильтр `provider_state` по провайдеру; биллинг; формат `chat_steps.payload` (wire-форма ответившего провайдера); контракт `/v1/chat/*`.

### A. Альтернативы

- **Пересобирать блоки в цикле попыток под `attempt.provider`.** Отклонено: чинит только путь 1. Пути 2 и 3 проходят мимо `_credits_llm_with_failover`, и каждый потребовал бы своей пересборки; инвариант держался бы на том, что каждый будущий вызывающий не забудет передать верного провайдера, — ровно на этом он сегодня и сломан.
- **Переводить чужие блоки вложений внутри клиента** (как `_responses_content_part` переводит Chat-Completions-форму в Responses). Отклонено для вложений: у них есть нейтральный источник в памяти, и перевод wire→wire — это N² адаптеров вместо N рендеров. Для истории (§A3) выбран именно перевод, потому что нейтрального источника у неё нет — только сохранённая wire-форма.
- **Собирать блоки сразу под обоих провайдеров.** Отклонено: вдвое больше base64 в памяти хода (до `ATTACHMENT_TOTAL_BYTES` на копию) и всё равно нужен выбор на стороне клиента.
- **Не делать кросс-обход, когда в ходе есть вложения.** Отклонено: вместо картинки, потерянной молча, пользователь терял бы ход целиком — при живом соседе.
- **Нейтральное хранение `chat_steps` сейчас** ([Q-033-1](../99-open-questions.md), [TD-024](../100-known-tech-debt.md)). Отклонено для этой волны: миграция формата всей истории всех инстансов ради пути, который терпимое чтение закрывает без миграции.

## Часть B. Оплаченная медиа-задача достигает конечного состояния за конечное время

### B. Контекст

**Прод-наблюдение (снято владельцем волны 2026-09-11 около 08:10 UTC, velunixa):** в `media_jobs` 19 задач в статусе `running`, созданных с 2026-08-30 по 2026-09-08 (прочие — `completed` 26434, `failed` 4189); за 24 ч 81950 событий `fal_call_outcome` с ошибкой, почти все `upstreamStatus` `504`/`500`, на `fal-ai/kling-video/v2.5-turbo/pro/text-to-video`, `fal-ai/nano-banana-pro`, `fal-ai/nano-banana-pro/edit`. Связь этих событий с 19 задачами **согласуется по порядку величины и не доказана**: в `fal_call_outcome` нет `jobId`. Доказуема она по уже существующему событию: `reconcile_once` (`src/app/media_generation/reconciler.py`) пишет `media_reconcile_job_error` с `jobId` на **каждый** провал продвижения — счёт этих событий по `jobId` за 24 ч (не выполнялся) и даёт атрибуцию.

**Механизм (по коду, `f8f4b37`):**

- `FalClient._raise_for_status` (`src/app/media_generation/fal_client.py`) превращает в терминальный класс только два ответа: `404` → `UpstreamJobGoneError` (комментарий там же: «чтобы согласователь закрыл задачу и вернул кредиты, а не опрашивал её вечно», инцидент selquro 2026-08-27, коммит `5ebf963`) и `422` → `ValidationFailedError`. Всё прочее — `401`/`403` → `MediaGenerationNotConfiguredError`, `429` → `RateLimitedError`, `402` и любой иной статус → `UpstreamError`; таймаут, обрыв соединения, битый JSON — `UpstreamError` из `FalClient._request`.
- `MediaGenerationService._advance` (`src/app/media_generation/service.py`; общий путь `get_job` и `advance`) ловит только `ValidationFailedError` и `UpstreamJobGoneError`; прочее всплывает. `reconcile_once` глотает его (`except Exception` → `media_reconcile_job_error`), строка остаётся как была и попадает в следующий тик.
- Норма, которую это реализует, — [ADR-060 §3](ADR-060-media-generation-fal.md): «транзиентные ошибки (`429`/`502`) на опросе пробрасываются… следующий опрос доберёт исход». Предела у неё нет: ответ, который не транзиентен, опрашивается бесконечно.

**Следствия** (все — по коду): бесконечная нагрузка на fal; задача, которая для пользователя никогда не завершится (клиентский `GET` на каждом опросе получает `502`); кредиты не возвращаются (`_fail` не вызывается); задачу нельзя удалить (`delete_job` отказывает незавершённой, [ADR-063 §4](ADR-063-media-feed-edit-chains-and-job-deletion.md)); `MediaJobsRepository.list_non_terminal` берёт **старейшие** незавершённые, поэтому застрявшие навсегда занимают голову пачки `MEDIA_RECONCILE_BATCH_SIZE` (дефолт 50), а продвижение в тике **последовательно** — каждая застрявшая задача добавляет к тику до `FAL_TIMEOUT_SECONDS` (дефолт 30), и обнаружение готовности здоровых задач (push, [ADR-067](ADR-067-media-ready-push-and-reconciler.md)) отстаёт вместе с ним; когда застрявших наберётся `MEDIA_RECONCILE_BATCH_SIZE`, согласователь перестанет продвигать новые задачи вовсе.

**Свип по признаку «задача, за которую заплачено, остаётся незавершённой навсегда» — сверх названного экземпляра (`5xx` на опросе):**

| # | Носитель | По коду | Итог |
|---|---|---|---|
| 1 | любой не-`404`, не-`422` ответ fal, таймаут, обрыв, битый JSON — на `status` **или** на `result` после `COMPLETED` | всплывает из `_advance` | ✗ **названный экземпляр и его класс** |
| 2 | fal бессрочно отвечает `IN_QUEUE`/`IN_PROGRESS` | `_advance` → `mark_running`, ошибки нет вовсе | ✗ (та же форма без ошибки) |
| 3 | результат готов, а пост-модерация недоступна ([ADR-086 §7](ADR-086-ugc-moderation.md), fail-closed) | исключение из `_moderate_output` всплывает | ✗ |
| 4 | `FAL_API_KEY` снят с инстанса при живых незавершённых задачах | `reconcile_once` возвращает `0` до выборки | ✗ |
| 5 | строка `request_logs` задачи, доведённой согласователем | `reconcile_once` собирает `MediaGenerationService` **без** `request_logs` → `finish_media` не зовётся, строка остаётся `queued` навсегда. Оператор этого сегодня не видит: история CRM берёт media из `media_jobs`, а строки `request_logs` с `media_job_id` не читает ([ADR-078 §3](ADR-078-crm-request-history-derived-from-domain.md)) — норма [ADR-077 §3](ADR-077-crm-request-logs.md) нарушена молча | ✗ (та же форма в соседней сущности) |
| 6 | `MEDIA_RECONCILE_INTERVAL_SECONDS <= 0` | цикл не стартует; задачу продвигает только клиентский опрос | осознанно: значение — для тестов (`Settings.media_reconcile_interval_seconds`), на проде `15` (`.env.prod.example`) |

И одна находка **другой формы**, обнаруженная тем же чтением: тот же `reconcile_once` собирает сервис **без** `moderation`, поэтому `MediaGenerationService._moderate_output` возвращает `None`, и картинка, чью готовность обнаружил согласователь (приложение свёрнуто — штатный случай), выдаётся **без пост-модерации** [ADR-086 §5](ADR-086-ugc-moderation.md), а поле `moderation` остаётся вердиктом **входа**. Причина у строки 5 и у этой находки одна — две сборки одного сервиса разошлись, когда [ADR-077](ADR-077-crm-request-logs.md) и [ADR-086](ADR-086-ugc-moderation.md) добавили зависимость в `deps.get_media_generation_service`, но не в согласователь (согласователь старше обоих: коммит `10e78c6`). Закрывает обе §B6.

### B. Решение

#### §B1. Инвариант

**Любая строка `media_jobs` достигает конечного состояния (`completed` | `failed`) не позже `created_at + MEDIA_JOB_DEADLINE_SECONDS`** (плюс не более одного тика согласователя). Инвариант задан по следствию («оплаченная задача завершается»), а не по причине: ни перечень статусов fal, ни перечень исключений клиента в его формулировку не входят, поэтому новый вид отказа подпадает под него без правки текста.

#### §B2. Предикат — в `MediaGenerationService._advance`, общем пути опроса и согласователя

Порядок одного продвижения:

1. **Опрос выполняется всегда, в том числе после дедлайна** (последний шанс): терминальные исходы применяются как сегодня — `COMPLETED` с ассетами → пост-модерация → `completed`; `FAILED`/`CANCELED`, `422`, `404`, `COMPLETED` без ассетов, `blocked` → `failed` с возвратом.
2. **Опрос НЕ дал конечного состояния** — по **любой** причине: исключение клиента fal (строка 1), нетерминальный статус (строка 2), недоступная пост-модерация (строка 3), незаданный ключ (строка 4), исключение нашего собственного кода между опросом и записью исхода (например, в нормализации результата):
   - `now − created_at > MEDIA_JOB_DEADLINE_SECONDS` ⇒ `_fail(job, error="generation did not complete in time")`: возврат кредитов (ключ `media-refund:{jobId}`), `mark_failed`, `request_logs.finish_media(failed=True, refunded=…)`, событие §B5. Исключение наружу не всплывает: клиентский `GET` получает `200` со `status: "failed"`;
   - иначе — как сегодня: исключение всплывает (клиент получает свой `502`/`503`/`429`, согласователь пишет `media_reconcile_job_error`), нетерминальный статус → `mark_running`.

**Предикат двусторонний, и обе стороны проверяются тестом на ОДНОМ И ТОМ ЖЕ наблюдении:**

- **(а) против недооценки** (оплаченная задача навсегда незавершена): задача старше дедлайна и опрос не дал конечного состояния ⇒ `failed` + возврат; **никакой** вид наблюдения не оставляет её незавершённой;
- **(б) против переоценки** (живая задача провалена): задача не старше дедлайна ⇒ правило её **не трогает**, какой бы ни была ошибка; задача старше дедлайна, но опрос дал `COMPLETED` с ассетами ⇒ `completed`, а не `failed`; дал `FAILED` ⇒ `failed` с текстом fal, а не текстом дедлайна.

Правило не меняет ни смысла ошибок при опросе, ни маппинга [ADR-060 §3](ADR-060-media-generation-fal.md) — оно только ограничивает сверху время, в течение которого «транзиентное» остаётся транзиентным.

#### §B3. Величина: `MEDIA_JOB_DEADLINE_SECONDS`, дефолт `21600` (6 ч)

- **Новая переменная** (`Settings`, `src/app/config.py`), public, per-instance. **Класс по [ADR-099 §8.2](ADR-099-crm-admin-economics-and-instance-settings.md) — (б)** «политика обращения к апстриму», в поверхность настроек панели не входит: это соседка `MEDIA_RECONCILE_INTERVAL_SECONDS`/`MEDIA_RECONCILE_BATCH_SIZE` из того же класса и определяет, как долго сервис опрашивает поставщика. По правилу §8.2 отнесение вносится в перечень той волной, которая вводит поле в код; здесь оно предложено, чтобы волне не пришлось решать заново. Значение `<= 0` приводится к дефолту — тот же приём, что у `Settings._positive_tts_credit_cost`: опечатка в `.env` не может выключить правило и вернуть бесконечный опрос.
- **Цепочка разрешения:** переменной нет ни в `src/`, ни в `.env.example`, ни в `.env.prod.example`, ни в `infra/` (`grep -rn "MEDIA_JOB_DEADLINE" src/ infra/ .env.example .env.prod.example` на `f8f4b37` — пусто), поэтому **дефолт кода действует на всех живых инстансах** с первого выката. В `.env.prod.example` она добавляется **закомментированной** строкой рядом с `MEDIA_RECONCILE_*` — для обнаружимости, не перекрывая дефолт кода (зона `devops`).
- **Почему возраст, а не число попыток.** Число опросов зависит от их частоты, а частота — от клиента (изображения — раз в 2 с по [02-api-contracts](../modules/media-generation/02-api-contracts.md)), от `MEDIA_RECONCILE_INTERVAL_SECONDS` и от числа реплик с согласователем ([ADR-067](ADR-067-media-ready-push-and-reconciler.md)): один и тот же кратковременный сбой fal исчерпал бы счётчик у активно опрашиваемой задачи и не исчерпал у забытой. Возраст от частоты не зависит, колонка `created_at` уже есть и обслуживается частичным индексом `ix_media_jobs_non_terminal` — миграция не нужна.
- **Почему 6 ч.** Живой прогон [ADR-060 §Тесты](ADR-060-media-generation-fal.md) (2026-08-04) дал 13–20 с на изображение и 90–100 с на видео — дедлайн выше максимума в 216 раз и оставляет запас на очередь fal под нагрузкой и на аварию fal длиной в часы. Цена дедлайна сверху — не более `21600 / MEDIA_RECONCILE_INTERVAL_SECONDS` = 1440 опросов согласователя (при дефолтном интервале `15`) на мёртвую задачу вместо бесконечности.
- ⚠️ **Утверждение «6 ч больше любой законной генерации» по реальным данным НЕ проверено** — выборки завершённых задач прода нет в этом дереве. Проверка до выката, по каждому инстансу, только агрегаты: `SELECT max(updated_at - created_at), percentile_cont(0.999) WITHIN GROUP (ORDER BY updated_at - created_at) FROM media_jobs WHERE status = 'completed';` (`updated_at` у `completed` — момент `mark_completed`, то есть длительность генерации плюс не более одного опроса). Максимум больше `MEDIA_JOB_DEADLINE_SECONDS / 2` хоть на одном инстансе — дефолт поднимается до выката.

#### §B4. Что видит клиент

Контракт не расширяется: `status: "failed"`, `error: "generation did not complete in time"`, `creditsRefunded: true`, `assets: []`; `moderation` не меняется (текст не совпадает ни с одним маркером `_FAL_CONTENT_POLICY_MARKERS`, поэтому `_fail` не классифицирует его как отказ по контент-политике). Push на `failed` не шлётся ([ADR-067 §2](ADR-067-media-ready-push-and-reconciler.md)). После `failed` задачу можно удалить из ленты.

#### §B5. Наблюдаемость

- **`media_generation_deadline_exceeded`** (WARNING) — пишет ветка дедлайна `_advance` перед `_fail`: `jobId`, `model`, `ageSeconds`, `lastObservation`, `upstreamStatus`. Затем, как у любого провала, `media_generation_failed`. **Источник `upstreamStatus`:** сегодня HTTP-статус fal живёт только в поле события `fal_call_outcome`, а поднятое исключение его не несёт (`FalClient._upstream_error` возвращает голый `UpstreamError`), — поэтому `FalClient._raise_for_status` прикрепляет статус к исключению, которое поднимает, а ветка дедлайна читает его оттуда. Статуса нет (таймаут, обрыв, битый JSON, нетерминальный статус, пустой ключ) — поле в событие не пишется.
- **`lastObservation` — измерение ПРИЧИНЫ, отдельное от следствия** (следствие у всех одно: `failed` + возврат). Значения и предикаты, вычисляемые из фактов опроса:

  | Значение | Предикат |
  |---|---|
  | `upstream_error` | `FAL_API_KEY` непуст, и вызов `FalClient.status` или `FalClient.result` завершился исключением |
  | `upstream_pending` | `FalClient.status` ответил нетерминальным статусом |
  | `moderation_unavailable` | fal отдал ассеты, `_moderate_output` завершился исключением |
  | `not_configured` | `FAL_API_KEY` пуст — запроса наверх не было: на пути `GET` `FalClient` отказывает до запроса (`FalClient._headers`), согласователь не опрашивает вовсе (§B7) |
  | `internal_error` | исключение возникло вне вызовов `FalClient` и `_moderate_output` (наш код между опросом и записью исхода) |

  Предикаты взаимоисключающие и вместе покрывают все исходы шага 2 §B2: каждое продвижение, дошедшее до дедлайна, отвечает ровно одному; ни одна строка не зависит от суждения. Отказ ключа (`401`/`403` → `MediaGenerationNotConfiguredError`) — это исключение `FalClient`, то есть `upstream_error` с `upstreamStatus`, а не `not_configured`: последнее означает, что ключа нет и запроса наверх не было вовсе.
- **`media_reconcile_job_error`** дополняется полем `exceptionClass` (имя класса исключения, не текст): вместе с существующим `jobId` это даёт атрибуцию «какая задача чем падает» без чтения строк `fal_call_outcome`.
- **Producer → consumer:** `_advance` (ветка дедлайна) → лог → дежурный; `reconcile_once` (ветка исключения) → лог. Метрики не вводятся — у media их нет и сейчас ([modules/media-generation/03-architecture.md §Наблюдаемость](../modules/media-generation/03-architecture.md#наблюдаемость)).

#### §B6. Одна сборка сервиса на оба пути

`MediaGenerationService` для согласователя собирается **той же функцией**, что и для request-пути, с тем же набором зависимостей (`repo`, `fal`, `wallet`, `settings`, `push`, `request_logs`, `moderation`). Две ручные сборки одного сервиса ЗАПРЕЩЕНЫ: следующая зависимость снова попала бы только в одну из них. Отсюда: строка `request_logs` задачи, доведённой согласователем, закрывается ([ADR-077 §3](ADR-077-crm-request-logs.md) начинает выполняться и для согласователя); картинка, готовность которой обнаружил согласователь, проходит пост-модерацию ([ADR-086 §5](ADR-086-ugc-moderation.md)).

#### §B7. Пустой ключ fal

При пустом `FAL_API_KEY` согласователь не опрашивает (опрашивать нечем), но задачи старше дедлайна доводит до `failed` с возвратом (`lastObservation = not_configured`); задачи моложе дедлайна не трогает. Выборка — те же незавершённые, отфильтрованные по возрасту.

#### §B8. Согласователь обязателен на проде

Инвариант §B1 для задачи, которую клиент больше не опрашивает, держится только согласователем. `MEDIA_RECONCILE_INTERVAL_SECONDS <= 0` допустим только в тестах (как и сейчас по `Settings.media_reconcile_interval_seconds`); на проде значение `15` задано в `.env.prod.example`.

#### §B9. Эффект выката

Первый тик согласователя после выката доводит до `failed` с возвратом **все** незавершённые задачи старше дедлайна: на velunixa это 19 задач (созданы не позже 2026-09-08, то есть на 2026-09-11 старше дедлайна каждая). По остальным инстансам число **не измерено**; счёт до выката, только агрегаты: `SELECT count(*), sum(credits_charged), min(created_at) FROM media_jobs WHERE status IN ('queued','running') AND created_at < now() - interval '6 hours';`. Возврат идёт обычным путём (`wallet.grant` с ключом `media-refund:{jobId}`) и повторного возврата не даёт.

### B. Альтернативы

- **Счётчик попыток** (колонка + миграция). Отклонено: мерило зависит от частоты опроса (§B3).
- **Считать `5xx` на опросе терминальным сразу.** Отклонено: `500`/`504` бывают кратковременными, правило провалило бы задачу, которая ещё генерируется, — это переоценка, запрещённая предикатом (б).
- **Два дедлайна — для ошибок и для `IN_PROGRESS`.** Отклонено: данных, которые различали бы эти два случая по законной длительности, нет; одно правило, заданное по следствию, покрывает оба, а второе число — это второе суждение без измерения.
- **Вебхук fal.** Отклонено ещё [ADR-060](ADR-060-media-generation-fal.md) (публичная callback-поверхность) и не решает задачи без ответа.
- **Разовая чистка 19 строк скриптом.** Отклонено как единственная мера: чинит экземпляры, класс остаётся; следующая авария fal вырастит новые.

## Последствия

- (+) Картинка, PDF и файлы-знания доходят до модели на **любом** пути, где провайдер вызова отличается от провайдера сборки, включая BYOK и операторский дефолт — без отказа поставщика в этих путях.
- (+) История, накопленная за время обхода, остаётся валидной для обоих провайдеров после восстановления основного.
- (+) Оплаченная медиа-задача завершается не позже 6 ч; кредиты возвращаются; нагрузка на fal от мёртвых задач ограничена; голова пачки согласователя освобождается.
- (+) Строка `request_logs` задачи, доведённой согласователем, закрывается; картинка, доведённая согласователем, проходит пост-модерацию.
- (−) Перевод чужой истории теряет рассуждение и цитаты другого провайдера ([TD-024](../100-known-tech-debt.md)).
- (−) Результат, пришедший у fal **после** дедлайна, теряется, а закупка у fal оплачена; такой приход не наблюдается ([TD-050](../100-known-tech-debt.md)).
- (−) Кросс-обход Anthropic → OpenAI по-прежнему срабатывает и на отказ формы **нашего** запроса, маскируя дефекты сборки запроса успешным ответом соседа ([TD-051](../100-known-tech-debt.md)); этим решением не меняется.
- **Меняются контракты кода** (`PreparedAttachments`, `prepare_attachments`, `WorkspacesService.context_for_session`) — тесты, собирающие `PreparedAttachments(content_blocks=…)` или зовущие эти функции с `provider`, падают по сигнатуре; это сопровождение стражей, а не новое покрытие.
