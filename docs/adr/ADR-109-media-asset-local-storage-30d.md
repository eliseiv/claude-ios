## Контекст

**Как устроено сейчас (по коду, прочитано в этом ходу).** Готовая задача хранит в `media_jobs.result.assets[].url` URL провайдера; клиенту отдаётся signed URL на наш домен (`public_asset_url`, `src/app/media_generation/signed_url.py:113-143`), а download-роут (`download_media_asset`, `src/app/api_gateway/routers/media.py:474-492`) по валидному токену стримит байты с исходного хоста (`stream_fal_asset`, `src/app/media_generation/asset_proxy.py:52-113`) без буфера и без записи на диск. *Уточнение факта 2026-09-24:* описание — состояние ДО реализации этого решения; теперь роут зовёт `serve_media_asset` (`routers/media.py:485-492`), который выбирает между своей копией и путём источника. Истёкший у источника файл (upstream `404`/`410`) отдаётся `404` (`asset_proxy.py:26`, `:81-84`), задача остаётся `completed`.

**Почему это стало проблемой.** У proxy-задачи ([ADR-108](ADR-108-media-generation-via-proxy.md)) файл результата лежит на relay-хосте прокси (`relay2.mediabackender.com`, факт пилота — [ADR-108 §7](ADR-108-media-generation-via-proxy.md)), а срок его жизни нам не подконтролен: предпочтение срока хранения fal через прокси не передаётся ([ADR-108 §2](ADR-108-media-generation-via-proxy.md) «Срок хранения результата fal-маршрута», [Q-108-9](../99-open-questions.md)). По словам владельца, «прокси сервис не хранит видео» — то есть видео из ленты перестают открываться. **Фактический срок жизни файла на relay-хосте в этом решении не измерен** ([Q-109-4](../99-open-questions.md)); решение построено так, чтобы работать при любом сроке не короче первой попытки сохранения (§3).

**Где физически будет лежать файл (по дереву, прочитано в этом ходу).** Каждый инстанс — каталог `/opt/<инстанс>` на двух прикладных серверах A и B; для половины инстансов основной — A, для другой — B ([MIGRATION-3-SERVERS.md §Топология](../MIGRATION-3-SERVERS.md)); Postgres реплицируется потоково, а `api` работает только на основном ([MIGRATION-3-SERVERS.md §Сделано](../MIGRATION-3-SERVERS.md): «на резерве нет ни миграции, ни api»). Контейнер `api` работает от пользователя `10001:10001` (`Dockerfile:54`, `:69`), per-instance каталоги монтируются bind-mount'ом по образцу `./.secrets:/app/.secrets:ro` (`docker-compose.prod.yml:178` до этой волны `:165-167`; bind-mount хранения — `:180`). Фоновые циклы (согласователь, `src/app/main.py:81-85`; цикл хранилища ассетов — `:88-91`) запускаются в lifespan **каждого** воркера gunicorn (`WEB_CONCURRENCY`, `docker-compose.prod.yml:140`).

## Решение

### §1. Что хранится, где и сколько

- **Предмет — ВСЕ результаты генерации:** каждая задача, перешедшая в `completed` с непустым `result.assets` — изображение и видео, proxy- и legacy-транспорт, `generation` и features (решение владельца №2). Не хранятся: `failed` (в том числе заблокированные пост-модерацией — у них `result = {"assets": []}`, [ADR-086 §5](ADR-086-ugc-moderation.md)), незавершённые, `pending_result` (он нетерминален и download-роутом не читается, [ADR-108 §9](ADR-108-media-generation-via-proxy.md)).
- **Где — локальный каталог инстанса на диске сервера** (решение владельца №1): на хосте `/opt/<инстанс>/media-assets`, в контейнере `api` — путь из `MEDIA_ASSET_STORAGE_DIR` (штатное значение — `/data/media-assets`). Каталог свой у каждого инстанса — **изоляция между инстансами обеспечена раздельными bind-mount'ами**, а не правами внутри общего каталога: контейнер инстанса другого каталога не видит вовсе.
- **Раскладка файла — только из данных БД, никогда из клиентского ввода:** `<dir>/<первые 2 символа jobId>/<jobId>/<index>` (`jobId` — UUID строки, `index` — целое из `result.assets`). Шард на 256 подкаталогов, чтобы корень не содержал десятки тысяч записей. Расширения нет: тип содержимого хранится в БД (§7). Traversal невозможен по построению — ни один сегмент пути не приходит из запроса.
- **Срок — 30 суток от момента перехода задачи в `completed`** (`MEDIA_ASSET_RETENTION_DAYS`, дефолт `30`): `assets_expire_at = момент mark_completed + MEDIA_ASSET_RETENTION_DAYS × 86400 с`. Срок фиксируется **один раз** и не сдвигается ни повторными попытками сохранения, ни скачиваниями, ни продлением токена. Выбран момент завершения, а не момент записи файла: пользователь видит результат с момента завершения, и «30 дней» для него отсчитываются оттуда; задержка записи (§3) срок не удлиняет.
- **После срока** — задача ведёт себя **как сегодня**: download-роут стримит с URL провайдера (§5); если там файла уже нет — `404`, как у любого истёкшего ассета до этого решения. Решение гарантирует «30 дней с нашего диска» и **никогда не делает хуже сегодняшнего**: legacy-задача с fal без истечения (`FAL_ASSET_RETENTION_SECONDS=0` в шаблонах, [ADR-108 §2](ADR-108-media-generation-via-proxy.md)) после 30 дней продолжает открываться с fal.

#### §1.1. Настройки — единственное нормативное место дефолтов

| Переменная | Класс | Дефолт кода | Смысл |
|---|---|---|---|
| `MEDIA_ASSET_STORAGE_DIR` | public | пусто | каталог хранения внутри контейнера; **пусто → хранение выключено**, поведение бит-в-бит сегодняшнее (новые строки получают `asset_store_status = ''`, §7). Включение — per-instance записью в `.env` (§Порядок выката); значение обязано совпадать на основном и резерве ([TD-059](../100-known-tech-debt.md)) |
| `MEDIA_ASSET_RETENTION_DAYS` | public | `30` | срок хранения нашей копии, сутки; `≤ 0` или не число → дефолт (опечатка не выключает очистку и не делает хранение вечным) |
| `MEDIA_ASSET_MAX_BYTES` | public | `268435456` (256 MiB) | предел одного файла; больше — файл не сохраняется (§3, исход `too_large`), задача отдаётся как сегодня |
| `MEDIA_ASSET_MIN_FREE_BYTES` | public | `21474836480` (20 GiB) | нижняя граница свободного места файловой системы каталога; ниже неё запись **не начинается** (§4) |
| `MEDIA_ASSET_STORE_INTERVAL_SECONDS` | public | `5` | период фонового цикла сохранения и очистки (§3, §6); `≤ 0` выключает цикл (тесты) |

Константы кода (не настройки): пакет цикла — 5 ассетов за тик; предел попыток — 12; пауза между попытками — `min(2^attempts × 30 с, 3600 с)`; период очистки — не чаще раза в 3600 с; возраст временного файла, после которого он считается брошенным, — 3600 с. **Сверка с шаблонами (норма ADR-099 §8.2 / правило «дефолт кода действует только там, где значение не задано»):** `git grep -n 'MEDIA_ASSET_'` по всему репозиторию 2026-09-24 — ни одного вхождения вне `docs/`, то есть ни в `.env*.example`, ни в `infra/`, ни в compose этих имён нет, и дефолты кода на живых инстансах действуют. Прочие документы ссылаются сюда и дефолтов не повторяют.

### §2. Что меняется в пути завершения — одно присваивание, шаги и порядок прежние

`mark_completed` ([ADR-108 §5](ADR-108-media-generation-via-proxy.md), `MediaJobsRepository.mark_completed`) при **включённом** хранении и непустых `assets` дополнительно ставит `asset_store_status = 'pending'` и `assets_expire_at` (§1). Больше ничего: ни скачивания, ни сетевого вызова, ни нового отказа внутри общего пути завершения нет, поэтому транзакционные границы ADR-108 §5 (SAVEPOINT в вебхуке, откат запроса целиком в опросе) и ADR-067 (push) **не меняются**. Хранение выключено → оба поля остаются дефолтными (`''`, `NULL`).

**Контраст (обе стороны помечены).** Пост-модерация и completion handler стоят **внутри** общего пути завершения и могут его отложить ([ADR-108 §5](ADR-108-media-generation-via-proxy.md)); сохранение файла стоит **снаружи** — после коммита терминала — и отложить или откатить завершение НЕ МОЖЕТ ни при каком исходе. Перенести скачивание в общий путь ЗАПРЕЩЕНО (§Альтернативы).

### §3. Фоновое сохранение

**Исполнитель — фоновый цикл «хранилище ассетов»** в lifespan приложения, рядом с согласователем, с периодом `MEDIA_ASSET_STORE_INTERVAL_SECONDS`. Цикл делает два дела: сохранение (здесь) и очистку (§6).

**Инварианты исполнения (нормативны; механизм выбирает `backend`):**
1. **Не более одного исполнителя на инстанс одновременно**, хотя lifespan есть у каждого воркера. Тик, не получивший право исполнения (например, неблокирующая advisory-блокировка Postgres с константным ключом), пропускается без побочных эффектов.
2. **Ни одна транзакция БД не держится открытой во время сетевого чтения или записи файла.** Чтение кандидатов, фиксация исхода — короткие транзакции; скачивание — между ними. Причина — общий пул соединений и `max_connections` Postgres на сервер ([07-deployment.md §Sizing пула](../07-deployment.md#sizing-пула-соединений-бд)); исполнитель занимает не больше одного соединения на инстанс на время тика; прочие воркеры за тик выполняют только короткие агрегатные запросы Gauge (§9).
3. **Кандидаты:** `status = 'completed' ∧ asset_store_status = 'pending' ∧ (asset_store_next_attempt_at IS NULL ∨ ≤ now())`, старейшие первыми, пакет — константа §1.1. Строка, чей `assets_expire_at` уже прошёл, не скачивается, а переводится в `expired` (§6.1).
4. **Скачивание одного ассета:** URL — `result.assets[index].url`; до запроса — строки 1–3 таблицы исходов ниже, в том числе та же проверка хоста, что у download-роута (`fal_asset_host_allowed` с дефолтным списком `FAL_UPLOAD_HOST_SUFFIXES ∪ MEDIA_RESULT_HOST_SUFFIXES`, [ADR-108 §7](ADR-108-media-generation-via-proxy.md)); только `https`, **без follow-redirect** (SSRF — как [ADR-085](ADR-085-media-asset-download-proxy.md)); короткий connect-, длинный read-таймаут; предел `MEDIA_ASSET_MAX_BYTES` проверяется и по `Content-Length`, и по фактически прочитанным байтам — превышение прерывает чтение, частичный файл удаляется.
5. **Атомарность и идемпотентность записи:** байты пишутся во временный файл в ТОМ ЖЕ каталоге назначения (уникальное имя), затем `fsync` и атомарное переименование в `<index>`. Повтор сохранения того же ассета перезаписывает файл тем же содержимым — результат тождествен. Строка переводится в `stored` **только после** того, как записаны ВСЕ ассеты задачи; до этого download-роут файлов задачи не использует (§5), поэтому частично сохранённая задача клиенту не видна.
6. **Фиксация `stored`:** `asset_store_status = 'stored'`, `assets_stored_at = now()`, `assets_stored_bytes = Σ размеров`, `stored_assets = [{index, bytes, contentType}]`, где `contentType` — заголовок `Content-Type` источника, иначе `result.assets[index].contentType`, иначе `application/octet-stream` (тот же порядок, что у download-роута сегодня, `asset_proxy.py:94-96`). Запись — условная (`WHERE asset_store_status = 'pending'`): если строку за время скачивания удалили (`DELETE`, удаление пользователя), обновление не находит строки, а записанные файлы убирает очистка сирот (§6.3).

**Исходы попытки — классификация по предикату из фактов попытки (взаимоисключающи, вычисляются в порядке строк).** Порядок нормативен: строки 1–3 вычисляются **без сети** и предшествуют любому исходящему запросу (п. 4); строки 4–9 — по ответу источника и по записи; строка 10 — по счётчику попыток после `retry`.

| # | Исход (`outcome`) | Предикат | Действие со строкой | Лог |
|---|---|---|---|---|
| 1 | `deferred_unavailable` | корень хранения недоступен — предикат «корень хранения доступен» §5 ложен: каталог `MEDIA_ASSET_STORAGE_DIR` не существует, не доступен на запись или не содержит маркер `.media-assets-root` (проверка тика, одна на пакет) | `asset_store_status`, `attempts`, `next_attempt_at` не меняются | WARNING, раз в тик |
| 2 | `host_rejected` | хост URL вне allowlist либо схема не `https` | `failed` | WARNING |
| 3 | `deferred_low_disk` (до запроса) | свободно на ФС каталога − `MEDIA_ASSET_MAX_BYTES` `< MEDIA_ASSET_MIN_FREE_BYTES` — худший случай, размера файла до запроса никто не знает | статус и `attempts` не меняются; меняется только `next_attempt_at = now + 300 с` | WARNING, раз в тик |
| 4 | `gone` | источник ответил `404`/`410` | `failed` | WARNING |
| 5 | `too_large` | `Content-Length` ответа или прочитанное `> MEDIA_ASSET_MAX_BYTES` | `failed`; частичный файл удалён | WARNING |
| 6 | `deferred_low_disk` (по ответу) | `Content-Length` известен и свободно − `Content-Length` `< MEDIA_ASSET_MIN_FREE_BYTES` (строка 3 пропустила, потому что место кончилось между проверкой и ответом) — чтение прерывается до записи | как строка 3 | WARNING, раз в тик |
| 7 | `retry` | таймаут, connect, `5xx`, прочий не-`2xx`, ошибка ввода-вывода диска, а `attempts + 1 < 12` | `attempts += 1`, `next_attempt_at` по паузе §1.1 | WARNING |
| 8 | `exhausted` | те же факты, что у `retry`, а `attempts + 1 = 12` | `attempts = 12`, `failed` | WARNING |
| 9 | `stored` | все ассеты задачи записаны | `stored` (п. 6) | INFO |

Строка 1 стоит раньше строки 2 не по «сетевому» признаку (обе без сети), а потому что она общая на тик и решается до перебора строк; взаимное положение 1 и 2 наблюдаемого исхода не меняет, кроме лога. Строки 3 и 6 — одно и то же значение `outcome` с одинаковым действием: 3 — против недооценки без сети, 6 — уточнение по фактическому размеру. *Уточнение по коду:* URL, который не разбирается (`ValueError` в разборе), — строка 2 `host_rejected` (`_host_allowed`, `src/app/media_generation/asset_store.py:156-161`); исключение попытки, не классифицированное ни одной строкой, идёт путём строк 7–8 (`attempts + 1`, пауза, на 12-й — `exhausted`), чтобы строка не застряла во главе очереди (`asset_store.py:386-400`, `_retry_or_exhaust`).

Предикат двусторонний: **(а) против недооценки** — источник, подтвердивший отсутствие файла (`gone`), или файл заведомо непринимаемый (`too_large`, `host_rejected`) не ретраится бесконечно и виден на WARNING; `gone` на свежей задаче — прямой сигнал, что срок relay-хоста короче нашей первой попытки ([Q-109-4](../99-open-questions.md)); **(б) против переоценки** — нехватка места и недоступный каталог не проблема ассета, поэтому попытки не тратят и строку в `failed` не переводят: после освобождения места ассет сохранится, если источник ещё жив.

**Скорость первой попытки.** Первая попытка — не позже одного периода цикла после коммита `completed` (дефолт 5 с) плюс очередь пакета. Более раннего «синхронного» сохранения нет (§Альтернативы); если окажется, что relay-хост удаляет файл быстрее, это видно по исходу `gone` и решается по [Q-109-4](../99-open-questions.md).

### §4. Диск: предел файла, свободное место, недоступность

- **Раздел общий.** Каталог лежит на корневом разделе сервера вместе с Postgres всех инстансов и Docker. Переполнение раздела останавливает базы ВСЕХ инстансов сервера, поэтому защита — **нижняя граница свободного места** (`MEDIA_ASSET_MIN_FREE_BYTES`), проверяемая перед КАЖДОЙ записью (§3, `deferred_low_disk`); граница одна на сервер по смыслу и одинакова у всех инстансов по значению (дефолт кода). Квоты на инстанс нет — это вопрос владельцу ([Q-109-2](../99-open-questions.md)).
- **Политика при достижении границы — «не записывать новое», а не «вытеснять старое»:** новые ассеты ждут в `pending` и после освобождения места сохраняются; уже сохранённые не удаляются раньше срока. Досрочное вытеснение старейших — альтернатива на решение владельца ([Q-109-3](../99-open-questions.md)).
- **Недоступность каталога** (не смонтирован, нет прав, ошибка ФС) — исход `deferred_unavailable`: генерация, оплата, завершение и выдача ссылок работают как сегодня (download идёт с источника, §5). **Хранение — улучшение доступности, а не условие успеха задачи.**
- **Ошибка чтения файла при отдаче** (файла нет на диске, ФС недоступна) при включённом хранении — download-роут переходит на путь источника (§5 шаг 4), наружу не отдаётся `5xx` из-за нашего диска.

### §5. Download-роут `GET`/`HEAD /v1/media/jobs/{jobId}/assets/{index}/{token}`

Порядок (шаги 1–2 — как сегодня, `routers/media.py:481-484`):
1. строка и ассет по `jobId`/`index` — нет → `404`;
2. проверка токена — не прошла → `401`;
3. **хранение выключено** (`MEDIA_ASSET_STORAGE_DIR` пуст) → шаг 4 не выполняется вовсе, сразу шаг 5; диск не читается, `local_missing` не бывает;
4. **своя копия** (хранение включено): `asset_store_status ∈ {'stored','missing'} ∧ now() < assets_expire_at ∧ корень хранения доступен (предикат ниже) ∧ файл <dir>/…/<index> читается` → байты с диска; `Range`/`If-Range` обязательны (`206` + `Content-Range`, `Accept-Ranges: bytes`), `HEAD` — те же заголовки без тела; заголовки ответа — тот же набор, что сегодня (`Accept-Ranges`, `Content-Length`, `Content-Range`, `ETag`, `Last-Modified`, `Cache-Control: private, max-age=3600`, `X-Content-Type-Options: nosniff`; `ETag`/`Last-Modified` — от файла), `Content-Type` — `stored_assets[index].contentType`; исход `source = local`. Строка в статусе `missing`, чей файл снова читается (каталог восстановлен или реплицирован), возвращается условным `UPDATE … SET asset_store_status = 'stored' WHERE id = :jobId AND asset_store_status = 'missing'` — **переход `stored ↔ missing` обратим**.
   - **Предикат «корень хранения доступен»** — один и тот же для download-роута и для исхода `deferred_unavailable` цикла §3: каталог `MEDIA_ASSET_STORAGE_DIR` существует, доступен на запись **и содержит маркер-файл `.media-assets-root`**. Маркер создаёт шаг провижининга каталога (§Порядок выката п.2, зона `devops`) на ОБОИХ серверах; каталог, который Docker создал сам на неподготовленном сервере, или несмонтированный том маркера не содержат. Маркер различает «хранилище не подготовлено/не смонтировано» и «хранилище на месте, а файла нет».
   - **Корень недоступен** → шаг 5, WARNING `media_asset_storage_unavailable`, **статус строки не меняется**, `source = remote` — та же семантика, что `deferred_unavailable` в цикле.
   - **Корень доступен, статус `stored`, срок не прошёл, а файла нет** — ОС ответила «файл не существует» (переключение на подготовленный резерв, потеря файла) → исход `source = local_missing`, WARNING `media_asset_local_missing` и условный `UPDATE … SET asset_store_status = 'missing' WHERE id = :jobId AND asset_store_status = 'stored'` (идемпотентен; следующие отдачи идут на шаг 5 без повторного WARNING, пока файл не появится — тогда обратный переход выше), затем шаг 5.
   - **Прочие ошибки чтения файла** → шаг 5 с WARNING, без смены статуса, `source = remote`: транзиентный сбой ФС не должен отключать живую копию.
5. **иначе — путь источника, как сегодня** (`stream_fal_asset`: allowlist, `404` на `404`/`410`, `502`, `504`); исход `source = remote`.

**Коды ответа локальной ветки выровнены с сегодняшним путём источника (по коду).** Сегодня `stream_fal_asset` пропускает наружу только статусы источника `200`/`206`/`304` (`_PASS_STATUSES`, `src/app/media_generation/asset_proxy.py:25`), `404`/`410` → `404` (`:26`, `:81-84`), `≥ 500` → `502`, любой иной (в том числе `416` на невыполнимый `Range`) → `404` (`:85-92`); условные заголовки кроме `Range`/`If-Range` источнику не передаются (`_outgoing_headers`, `:30-36`), поэтому `304` на деле не возникает. **Норма для локальной ветки — «не хуже и не иначе, чем сегодня»:** невыполнимый `Range` → **`404 not_found`** (как сегодняшний `416` источника → `404`), не `416`; `If-None-Match`/`If-Modified-Since` игнорируются, `304` локальная ветка не отдаёт; `If-Range` с несовпавшим валидатором → полный `200`. Если библиотека отдачи файла сама отвечает `416`/`304`, `backend` обязан привести это к норме (`404` / полный ответ). Выбор `404` вместо семантически точного `416` — сознательный: новый код ответа видел бы клиент, который его сегодня не получает.

Гейт `503 media_generation_not_configured` на роуте **не меняется** ([ADR-108 §1](ADR-108-media-generation-via-proxy.md)): инстанс, снявший ключи генерации, своих файлов не отдаёт — как сегодня не отдаёт чужих.

**Обратная совместимость публичных ответов — перечень сохраняемого (а не «байт-в-байт»):** путь и форма signed URL, токен и его TTL (`MEDIA_DOWNLOAD_TTL_SECONDS`), поле `assets[].url` и остальные поля `MediaAssetSchema` в ответах задачи и ленты и `mediaUrl` push — **без изменений**, новых полей в JSON нет; набор HTTP-кодов роута тот же, что выводится из кода сегодня (`200`/`206`/`401`/`404`/`502`/`504`/`503`, плюс `304` источника, который пропускается `_PASS_STATUSES`, но при непередаваемых условных заголовках не возникает; `416` наружу не отдаётся ни одной веткой); `502`/`504` возможны только на пути источника; набор заголовков ответа тот же. **Меняется, и это ожидаемое следствие решения:** значения `ETag`/`Last-Modified` у ассета, отдаваемого с диска, — наши, а не источника (клиент, закэшировавший ответ источника, при первом `If-Range` получит полный `200` вместо `206` — штатная семантика `If-Range`); истёкший у источника ассет в течение 30 дней открывается (`200` вместо `404`).

### §6. Очистка

Выполняется тем же циклом (§3, один исполнитель на инстанс), не чаще раза в 3600 с (*уточнение по коду*: момент последней очистки — время изменения файла-штампа `.media-assets-cleanup` в корне хранения, `CLEANUP_STAMP`, `src/app/media_generation/asset_store.py:83`); каждый шаг идемпотентен, падение посреди тика безопасно — следующий тик доделывает.

1. **Истечение срока:** строки `asset_store_status ∈ {'stored','pending','failed','missing'} ∧ assets_expire_at < now()` → удалить каталог `<dir>/<shard>/<jobId>` (отсутствие файлов — не ошибка), затем `asset_store_status = 'expired'`, `stored_assets = NULL`. Порядок «сначала файлы, потом строка»: падение между шагами оставляет строку, и следующий тик повторит удаление несуществующего — тождественно.
2. **Брошенные временные файлы** старше 3600 с — удаляются.
3. **Сироты:** подкаталог `<jobId>`, для которого строки `media_jobs` нет (`DELETE /v1/media/jobs/{jobId}`; каскад `users ON DELETE CASCADE`), и чьё время изменения старше 3600 с (защита от гонки с записью §3 п. 6) → удаляется. **Страховка от ложного «строки нет» — проверка ТОЖДЕСТВА базы, а не доли сирот.** Удаление сирот — необратимое действие по наблюдению «строки нет», которое одинаково при законно удалённой задаче и при подключении к пустой или чужой базе. Поэтому шаг 3 выполняется, только если база та же, для которой готовился каталог: маркер `.media-assets-root` содержит строку `pg_system_identifier=<число>`, и в начале шага 3 она сверяется с `SELECT system_identifier FROM pg_control_system()` текущей базы. **Совпало** → шаг 3 выполняется целиком, без порогов: законное массовое удаление (удаление аккаунта с тысячами задач) не блокируется, а защита работает на инстансе любого размера. **Не совпало, строки нет, маркер не читается или запрос идентификатора базы не выполнился** (*уточнение по коду*: последний случай — тот же исход `identity_absent`, плюс WARNING `media_asset_identity_query_failed`; `identity_verdict`, `src/app/media_generation/asset_store.py:204-213`) → пропускается ТОЛЬКО шаг 3 (шаги 1–2 и сохранение §3 работают), WARNING `media_asset_cleanup_aborted` (`reason ∈ {identity_mismatch, identity_absent}`), Gauge `media_asset_cleanup_blocked = 1` (§9). **Выход** — действие оператора: убедиться, что `api` подключён к правильной базе инстанса, и перезаписать строку маркера текущим идентификатором (§Порядок выката п.2). Почему идентификатор совпадает на основном и резерве: резерв строится физической копией основного (`pg_basebackup`, `infra/fleet/replication.sh:75`), а `system_identifier` кластера при физическом копировании сохраняется и у реплики совпадает с основным. Это свойство PostgreSQL в этом решении **не измерено** — devops сверяет значение на обоих серверах перед записью маркера. Пересоздание кластера (новый том, восстановление из `pg_dump`) даёт новый идентификатор, и это верно: для такой базы старые подкаталоги — не её сироты, пока оператор этого не подтвердил.

**Область действия очистки — сервер, на котором работает `api` инстанса с ВКЛЮЧЁННЫМ хранением.** Цикл §3 живёт в `api`, а `api` работает только на основном сервере и только при непустом `MEDIA_ASSET_STORAGE_DIR`. Вне этой области файлы стираются не циклом, а **нормативными операционными шагами**, которые поэтому входят в решение:
- **выключение хранения** (откат, §Порядок выката п.5): снятие `MEDIA_ASSET_STORAGE_DIR` выполняется ВМЕСТЕ с очисткой каталога `/opt/<инстанс>/media-assets` на обоих серверах тем же шагом оператора; оставить каталог с файлами при выключенном хранении ЗАПРЕЩЕНО — чистить его будет некому;
- **сервер, вернувшийся после аварии:** его пересборка как резерва ([MIGRATION-3-SERVERS.md §Переключение](../MIGRATION-3-SERVERS.md)) включает очистку `/opt/<инстанс>/media-assets` каждого инстанса, для которого он стал резервом; до пересборки сервер недоступен, и файлы на нём не отдаются никому, но физически существуют ([Q-109-7](../99-open-questions.md)).

**Инвариант очистки (двусторонний), с явными границами:** (а) против недооценки — на сервере, где работает `api` инстанса с включённым хранением, файл, чей срок прошёл или чья строка удалена, живёт не дольше срока (или момента удаления) + 2 ч; **исключение** — заблокированная очистка сирот (тождество базы не подтверждено, шаг 3): байты удалённых задач живут до действия оператора, и это состояние наблюдаемо (`media_asset_cleanup_blocked = 1`, алерт); на сервере вне этой области — до шага оператора выше (выключение хранения либо пересборка вернувшегося сервера), и этот срок не ограничен кодом; (б) против переоценки — файл строки со статусом `stored` и непрошедшим сроком не удаляется никогда, в том числе при `deferred_low_disk`.

### §7. Схема данных

Одна миграция, expand-only, single head — следующая ревизия после головы на момент реализации (на 2026-09-24 голова — `0038_media_jobs_proxy`); id ревизии ≤ 32 символов (`alembic_version.version_num varchar(32)`, [ADR-108 §9](ADR-108-media-generation-via-proxy.md)).

| Колонка `media_jobs` | Тип | Смысл |
|---|---|---|
| `asset_store_status` | `TEXT NOT NULL DEFAULT ''`, `CHECK (asset_store_status IN ('', 'pending', 'stored', 'failed', 'missing', 'expired'))` | `''` — хранение к строке не применялось (строки до миграции, задачи не `completed`, инстанс с выключенным хранением); `pending` → `stored` \| `failed`; `stored` ↔ `missing`: в `missing` — когда при включённом хранении и доступном корне (маркер `.media-assets-root`) файла на диске нет, обратно в `stored` — когда файл снова читается (§5 шаг 4); любой из `pending`/`stored`/`failed`/`missing` → `expired` по сроку. Наш собственный домен состояний, поэтому `CHECK` (в отличие от `status`/`provider`, чьи наборы — внешний контракт) |
| `asset_store_attempts` | `INTEGER NOT NULL DEFAULT 0` | число попыток исхода `retry` (§3) |
| `asset_store_next_attempt_at` | `TIMESTAMPTZ NULL` | не раньше какого момента следующая попытка |
| `assets_expire_at` | `TIMESTAMPTZ NULL` | конец срока хранения нашей копии (§1) |
| `assets_stored_at` | `TIMESTAMPTZ NULL` | момент перехода в `stored` |
| `assets_stored_bytes` | `BIGINT NULL` | суммарный размер сохранённых файлов задачи |
| `stored_assets` | `JSONB NULL`, ORM — `JSONB(none_as_null=True)` | `[{index, bytes, contentType}]`; «нет значения» — SQL `NULL`, не JSON `null` ([TD-061](../100-known-tech-debt.md): прецедент `pending_result`) |

**Индексы:** частичный `ix_media_jobs_asset_store_pending ON media_jobs (asset_store_next_attempt_at) WHERE asset_store_status = 'pending'` (кандидаты §3) и частичный `ix_media_jobs_assets_expire ON media_jobs (assets_expire_at) WHERE asset_store_status IN ('stored','pending','failed','missing')` (очистка §6.1). На существующих строках оба предиката ложны.

**DML по существующим строкам нет:** константные дефолты заполняют старые строки значениями `''`/`0`/`NULL`, и для них это верно — хранение к ним не применялось. **Backfill (сохранение уже завершённых задач) не выполняется** ([Q-109-6](../99-open-questions.md)). Под правило «миграция, меняющая существующие данные» (прогон на копии прод-дампа) миграция не подпадает. Способ создания индексов (с `CONCURRENTLY` или без) выбирает `backend` по размеру `media_jobs` на флоте и обосновывает в миграции (прецедент без `CONCURRENTLY` — [03-data-model.md](../03-data-model.md), `ix_steps_created_at`).

### §8. Кредиты, стоимость, цена

- **Провал сохранения кредитов НЕ возвращает.** Предикат возврата ([ADR-060 §4](ADR-060-media-generation-fal.md)) — «провайдер не дал результата»; при любом исходе сохранения результат выдан (`completed`, ссылка отдана, файл был доступен у источника в момент завершения). Сохранение — наш слой долговечности, его отказ наблюдаем (§9) и не меняет ни `credits_refunded`, ни `ledger_transactions`.
- **Себестоимость CRM (`provider_cost_usd`, `vendor_price`) не меняется** — сохранение не является закупкой у вендора. Цены в кредитах, их резолв и логика ходов — без изменений.

### §9. Наблюдаемость (без секретов и без URL целиком)

**Метрики живут в каждом процессе отдельно — поэтому алерт строится только на значениях, которые одинаковы в любом воркере.** Реестр метрик — обычный `prometheus_client` без multiprocess-режима (`src/app/observability/metrics.py:5`, в `src/` и compose нет ни `PROMETHEUS_MULTIPROC_DIR`, ни `multiprocess` — `grep -rn` пуст), воркеров несколько (`WEB_CONCURRENCY: ${GUNICORN_WORKERS:-2}`, `docker-compose.prod.yml:140`), и `/metrics` отвечает тот воркер, к которому попал запрос сборщика. Gauge, который ставит только единственный исполнитель §3 п.1, в остальных воркерах отдавался бы `0` — ложный сигнал в обе стороны. **Норма:** каждый Gauge ниже вычисляется **в каждом воркере на каждом тике цикла, ДО попытки получить право исполнения** §3 п.1, из источника, общего для всех процессов (ФС каталога, строки БД); тик, не получивший права исполнения, эти Gauge всё равно обновляет. Так значение верно на любом воркере с точностью до одного периода цикла (образец — `media_proxy_jobs_awaiting_callback`: его ставит `reconcile_once`, работающий в каждом воркере, `src/app/media_generation/reconciler.py:65-70`). Counter'ы per-process по построению (сумма только в одном процессе), поэтому они — **диагностика**, и правила алертов на них НЕ строятся.

| Сигнал | Тип | Producer | Consumer |
|---|---|---|---|
| `media_asset_storage_free_bytes` | Gauge, без лейблов | каждый воркер, каждый тик: свободное место ФС каталога; при выключенном хранении не публикуется; *уточнение по коду:* серия регистрируется при первом успешном измерении и **снимается**, когда измерение не удалось (корень недоступен) — `0` не экспортируется (`set_media_asset_storage_free_bytes`, `src/app/observability/metrics.py:303-315`), поэтому при недоступном корне правило по этой серии молчит, а сигналом служат WARNING `media_asset_storage_unavailable` и рост `media_asset_store_pending` | правило алерта «`< 2 × MEDIA_ASSET_MIN_FREE_BYTES` дольше 10 мин» (зона `devops`, `infra/observability/rules/alerts.yml`) и раздел хранения в `infra/fleet/verify.sh` |
| `media_asset_store_pending` | Gauge, без лейблов | каждый воркер, каждый тик: `count(*)` строк `asset_store_status = 'pending'` | правило алерта «`> 50` дольше 15 мин» (`devops`) |
| `media_asset_store_failed` | Gauge, без лейблов | каждый воркер, каждый тик: `count(*)` строк `asset_store_status = 'failed' ∧ assets_expire_at > now()` | правило алерта «рост за 1 ч» (`delta(...[1h]) > 0`, `devops`) — признак `gone`/`too_large`/`host_rejected`/`exhausted` |
| `media_asset_missing` | Gauge, без лейблов | каждый воркер, каждый тик: `count(*)` строк `asset_store_status = 'missing' ∧ assets_expire_at > now()` | правило алерта «рост за 15 мин» (`delta(...[15m]) > 0`, `devops`) — признак переключения на резерв или потери файлов при включённом хранении; **уровень** не алертится (после одного известного переключения он держится до 30 дней и действием оператора не снимается) и выводится в разделе хранения `infra/fleet/verify.sh` |
| `media_asset_cleanup_blocked` | Gauge 0/1, без лейблов | каждый воркер, каждый тик: `1`, если строка `pg_system_identifier` маркера отсутствует или не равна `system_identifier` текущей базы (§6.3), иначе `0`; при выключенном хранении не публикуется | правило алерта «`= 1` дольше 15 мин» (`devops`) — уровень, снимаемый действием оператора (перезапись маркера) |
| `media_asset_store_total{outcome}` | Counter, `outcome ∈ {deferred_unavailable, host_rejected, deferred_low_disk, gone, too_large, retry, exhausted, stored}` — ровно значения таблицы §3 | попытка сохранения §3 (исполнитель) | диагностика; алерта нет |
| `media_asset_download_total{source}` | Counter, `source ∈ {local, remote, local_missing}` | download-роут §5; `local_missing` — только при включённом хранении | диагностика; алерта нет (сигнал для алерта — рост `media_asset_missing`) |

Исход `local_missing` задан ТРЕМЯ фактами — «хранение включено», «корень хранения доступен» (маркер `.media-assets-root`) и «файла нет» (§5 шаги 3–4): при выключенном хранении (штатный откат) диск не читается; при неподготовленном или несмонтированном каталоге строки не трогаются (`media_asset_storage_unavailable`); `local_missing` и `missing` возникают только при реально пропавшем файле, а переход обратим.

Лог-события: `media_asset_stored` (INFO: `jobId`, `assets`, `bytes`), `media_asset_store_failed` (WARNING: `jobId`, `outcome`, `attempts`, `upstreamStatus`), `media_asset_store_deferred` (WARNING: `outcome`, `freeBytes`; раз в тик), `media_asset_local_missing` (WARNING: `jobId`, `index`), `media_asset_storage_unavailable` (WARNING: без полей, не чаще раза в минуту на воркер), `media_asset_cleanup` (INFO: `expired`, `orphans`, `tmp`, `freedBytes`), `media_asset_cleanup_aborted` (WARNING: `reason`, не чаще раза в тик очистки). *Уточнение по коду (события, введённые реализацией, сверх перечня выше):* `media_asset_store_job_error`, `media_asset_store_loop_error`, `media_asset_store_started`/`media_asset_store_stopped` (`src/app/media_generation/asset_store.py`), `media_asset_identity_query_failed` (там же), `media_asset_local_read_error`, `media_asset_status_update_failed` (`src/app/media_generation/asset_local.py`), `media_asset_cleanup_error` (WARNING: `step ∈ {expired, orphan}`, `jobId`, `errno`; один элемент очистки не удалился, шаг продолжается с остальными — `_log_cleanup_error`, `asset_store.py:964-973`). **Запрещено в логах:** URL ассета целиком, токен, путь каталога хоста.

⚠️ **Оговорка о доставке:** правила алертов канала доставки не имеют ([TD-060](../100-known-tech-debt.md)); до его закрытия сигналы §9 видны только при чтении метрик и прогоне `verify.sh`.

### §10. Безопасность — сводка

Файлы отдаются **только** через signed download-роут (HMAC в пути, [ADR-085](ADR-085-media-asset-download-proxy.md)); статической раздачи каталога нет. Путь строится из UUID и индекса из БД — traversal невозможен. Исходящее чтение — allowlist хостов, `https`, без редиректов, предел размера. Каталог — `0750`, файлы — `0640`, владелец `10001:10001`. Заблокированный модерацией результат не хранится (у него нет ассетов). Удаление задачи/пользователя закрывает доступ сразу, байты — очисткой §6.3 в пределах её области действия и при подтверждённом тождестве базы (иначе — до действия оператора, сигнал `media_asset_cleanup_blocked`); вне её (выключенное хранение, вернувшийся сервер) — операционными шагами §6 ([Q-109-7](../99-open-questions.md)). Копии **не входят** в бэкап `pg_dump` ([07-deployment.md](../07-deployment.md)) и на резерв не реплицируются ([TD-062](../100-known-tech-debt.md)).

## Известное ограничение: переключение на резерв

Файлы есть только на диске основного сервера инстанса. После переключения на резерв ([MIGRATION-3-SERVERS.md §Переключение](../MIGRATION-3-SERVERS.md)) реплицированная база говорит `stored`, а файлов на резерве нет → при включённом и подготовленном (маркер `.media-assets-root`) хранении на резерве download-роут помечает строку `missing` и идёт к источнику (§5 шаг 4, алерт по росту `media_asset_missing`); если каталог на резерве не подготовлен — строки не трогаются (`media_asset_storage_unavailable`); у proxy-задач relay-хост, скорее всего, файла уже не держит → `404` — ровно поведение до этого решения. Новые задачи после переключения сохраняются на диск нового основного. Файлы на вышедшем из строя сервере не отдаются никому; при его пересборке как резерва каталоги инстансов очищаются операционным шагом (§6, [Q-109-7](../99-open-questions.md)) — иначе их не вычистил бы никто, пока сервер не станет основным. Долг — [TD-062](../100-known-tech-debt.md); решение о репликации — [Q-109-1](../99-open-questions.md).

## Альтернативы

- **Репликация файлов на резерв** (rsync по расписанию A→B и B→A по туннелю WireGuard либо общий сетевой том). Устраняет ограничение переключения; цена — дисковая и сетевая нагрузка на обоих серверах (прецедент отказа сервера от дисковой нагрузки 2026-08-24 — [MIGRATION-3-SERVERS.md §Репликация](../MIGRATION-3-SERVERS.md)), вдвое больше занятого места, новый процесс со своим мониторингом; при rsync — окно отставания, в которое свежий файл есть только на основном. **Не выбрана и не отвергнута владельцем** — [Q-109-1](../99-open-questions.md); решение ниже её не исключает: раскладка §1 детерминирована и одинакова на обоих серверах, поэтому реплицированный каталог подхватывается без изменений кода.
- **Самовосстановление при `local_missing`** — вернуть строку `missing` в `pending` и перескачать с источника. Отклонено на этом шаге: у proxy-задачи источник к моменту переключения, как правило, мёртв, а у legacy-задачи путь источника и так работает; добавляет вторую ветку записи без выигрыша. Пересматривается вместе с [Q-109-1](../99-open-questions.md).
- **Синхронное сохранение внутри общего пути завершения** (до `mark_completed`). Отклонено: скачивание видео в сотни мегабайт держало бы захват строки и транзакцию вебхука ([ADR-108 §4.2](ADR-108-media-generation-via-proxy.md)) минутами, а отказ диска превращался бы в отказ завершения оплаченной задачи; сохранение по построению не должно влиять на исход генерации (§2, §8).
- **Объектное хранилище (S3-совместимое).** Решает и резерв, и бэкап; отвергнуто владельцем выбором варианта №1 («без новых сервисов и ключей»).
- **Хранить только видео.** Отвергнуто владельцем (решение №2).
- **Отсчёт срока от момента записи файла.** Отклонено: для пользователя результат существует с момента завершения; задержка записи продлевала бы срок незаметно и неравномерно.
- **Досрочное вытеснение старейших при нехватке места.** Не выбрано по умолчанию: нарушает обещание «30 дней» молча; вынесено владельцу ([Q-109-3](../99-open-questions.md)).

## Последствия

- (+) Результаты генерации — видео и картинки — открываются 30 дней независимо от срока хранения у прокси/вендора; после срока — не хуже, чем сегодня.
- (+) Публичные контракты `/v1/media/*`, цены, биллинг и транспорт генерации не меняются; хранение включается и выключается per-instance переменной без выката кода.
- (−) Новый потребитель общего корневого раздела сервера; защищён нижней границей свободного места, но квоты на инстанс нет ([Q-109-2](../99-open-questions.md)).
- (−) Переключение на резерв делает копии недоступными ([TD-062](../100-known-tech-debt.md)); копии не в бэкапе.
- (−) Стирание байтов вне сервера с работающим `api` (выключенное хранение, вернувшийся после аварии сервер) держится на операционных шагах, а не на коде (§6, [Q-109-7](../99-open-questions.md)).
- (−) Цепочки правок (`sourceJobId`) по-прежнему берут URL провайдера и после его истечения приходят `failed` ([Q-109-5](../99-open-questions.md)).
- (−) Ещё один фоновый цикл в каждом воркере (исполняет один на инстанс) и одно соединение пула на время тика.

## Порядок выката

1. **Замер до включения (оператор/`devops`, только агрегаты, без PII), на основном сервере каждого инстанса:** `SELECT kind, count(*) FROM media_jobs WHERE status = 'completed' AND updated_at > now() - interval '30 days' GROUP BY kind;` — объём за 30 дней; вместе со средним размером файла (снимается на пилоте по `assets_stored_bytes`) даёт ожидаемое занятое место. Сумма по инстансам, основным на сервере, сопоставляется со свободным местом раздела минус `MEDIA_ASSET_MIN_FREE_BYTES`; не помещается → хранение на части инстансов не включается до ответа по [Q-109-2](../99-open-questions.md).
2. **`devops`:** на ОБОИХ серверах каждого инстанса создать `/opt/<инстанс>/media-assets` (владелец `10001:10001`, `0750`) — в `infra/fleet/provision.sh` для новых (`new` и `adapt`) и разовым шагом для существующих; в `docker-compose.prod.yml` — bind-mount `./media-assets:/data/media-assets` у `api`. Тем же шагом в корне каталога создаётся маркер-файл `.media-assets-root` (владелец `10001:10001`) с одной строкой `pg_system_identifier=<значение SELECT system_identifier FROM pg_control_system() базы инстанса>`; значение снимается на основном и сверяется с резервом, на оба сервера пишется одно и то же. *Уточнение по дереву:* каталог и пустой маркер создаёт `infra/fleet/provision.sh` (`new`/`adapt`), а строку идентификатора — `infra/fleet/media-assets-rollout.sh` с маршрутизатора (режим подготовки; переписать отличающуюся строку — только `--rewrite-identity`): `provision.sh` видит один сервер, а при `new` кластера базы ещё нет. Без маркера хранение на сервере считается неподготовленным (§5, `deferred_unavailable`); маркер без совпадающей строки блокирует только очистку сирот (§6.3). После пересоздания кластера базы инстанса строка переписывается тем же шагом — это и есть выход из блокировки §6.3. Каталог обязан существовать до первого `up`: иначе Docker создаст его от `root`, и цикл будет давать `deferred_unavailable` (безвредно, но хранение не работает). В процедуру пересборки вернувшегося после аварии сервера как резерва ([MIGRATION-3-SERVERS.md §Переключение](../MIGRATION-3-SERVERS.md); скрипт выбирает `devops`, кандидат в дереве — `infra/fleet/repair-replication.sh`, пересобирающий репликацию резерва) — очистка `/opt/<инстанс>/media-assets` каждого инстанса, для которого сервер становится резервом (§6).
3. **Код и миграция** выкатываются — поведение всех инстансов не меняется (`MEDIA_ASSET_STORAGE_DIR` пуст).
4. **Пилот на одном инстансе:** вписать `MEDIA_ASSET_STORAGE_DIR=/data/media-assets` в `.env` основного **и** резерва, перезапустить `api` на основном; прогнать по одному запуску фото и видео до `completed`; убедиться, что строка перешла в `stored`, `media_asset_download_total{source="local"}` вырос, `Range` отдаёт `206`; снять средний размер (`assets_stored_bytes`); затем флот — по одному инстансу или порциями, без общего цикла по всем.
5. **Откат:** снять `MEDIA_ASSET_STORAGE_DIR` на основном и резерве, перезапустить `api` и ТЕМ ЖЕ шагом очистить содержимое `/opt/<инстанс>/media-assets` на обоих серверах, **оставив маркер `.media-assets-root`** (§6: при выключенном хранении цикл не работает, и чистить файлы иначе некому). После этого download-роут диск не читает и идёт к источнику (§5 шаг 3), `local_missing`/`missing` не возникают; строки не трогаются. Повторное включение пометит строки со стёртыми файлами `missing` при первой отдаче — это верное состояние (файлов действительно нет), алерт по росту `media_asset_missing` при этом ожидаем один раз. Откат кода не требует отката миграции (expand-only).

## Классы новых переменных ([ADR-099 §8.2](ADR-099-crm-admin-economics-and-instance-settings.md#82-что-в-поверхность-не-входит--свип-по-всем-переменным-этого-сервиса))
